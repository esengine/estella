The Estella editor is a **Model Context Protocol (MCP)** server. An MCP-capable AI tool — Claude Code, Cursor, or a
custom agent — drives the editor through the same pipelines as the UI: creating and opening projects and scenes,
spawning entities from the Create-menu catalog, editing component fields, inspecting the live engine World, running
Play mode, taking screenshots and exporting builds. The editor provides more than 180 tools.

<Aside type="tip">
Agent actions go through the editor's command layer: edits are undoable, Play mode does not modify the edit scene,
and saving is the toolbar Save. The agent's work is visible in the editor window, which can be used alongside it.
</Aside>

## Connecting an AI tool

**Window → Connect AI Tools…** (also the AI agent mark in the status bar, and the *Connect an AI tool* button in
Settings) opens the connect dialog. It lists the installed Claude Code, Cursor, Claude Desktop and VS Code, each with a
**Connect** / **Disconnect** button.
- **Connect** writes an `estella` entry into the tool's own MCP config (other entries in the file are kept) and turns
  on *Allow AI agents to connect*. The entry runs the bundled MCP script with the editor's own executable
  (`ELECTRON_RUN_AS_NODE`), so Node.js need not be installed, and attaches to the open editor (`--attach`). The
  connection state is read from the config, so an entry removed by hand shows as disconnected. A config file that
  cannot be parsed is not modified.
- **Permission** — *Read only* or *Can edit* — is set in the dialog. It belongs to the editor window it is set in, is
  not saved (every editor starts read-only), and does not affect other open editors. The editor decides it at call
  time and the config entries carry no permission, so a change applies to every connected tool immediately.
- **Last call** (for example "Last call: Claude Code, 12 s ago") confirms that a tool is actually using the
  connection.
- **Other tools** lists the entry as JSON, TOML or a command, with paths filled in, for tools the dialog cannot write
  (Windsurf, Zed, Codex and others).

### Manual configuration

The MCP server is a Node script inside the editor. It speaks MCP over stdio to the AI tool and drives an editor
instance, launching one or attaching to one already open. Its path in an installed editor:

- **Windows** — `%LOCALAPPDATA%\Programs\@estellaeditor\resources\app.asar.unpacked\dist-electron\mcp\editor-mcp.mjs`
- **macOS** — `/Applications/Estella Editor.app/Contents/Resources/app.asar.unpacked/dist-electron/mcp/editor-mcp.mjs`

<Tabs>
<TabItem label="Claude Code">

```sh
claude mcp add estella --env ESTELLA_MCP_ALLOW_WRITES=1 -- \
  node "<path-to>/editor-mcp.mjs" --editor
```

</TabItem>
<TabItem label="Any MCP client">

```json
{
  "mcpServers": {
    "estella": {
      "command": "node",
      "args": ["<path-to>/editor-mcp.mjs", "--editor"],
      "env": { "ESTELLA_MCP_ALLOW_WRITES": "1" }
    }
  }
}
```

</TabItem>
</Tabs>

A manually configured server requires Node.js 20 or later on `PATH`.

| Option | Effect |
|---|---|
| `--editor` | Launches the installed editor with the MCP endpoint enabled. |
| `--attach` | Attaches to an editor that is already open ([Attaching to an open editor](#attaching-to-an-open-editor)). |
| `--eager` | Starts the editor in the background as soon as the client connects, instead of on the first tool call. |
| `--hidden` | With `--editor`, drives the editor without a window. |
| `--all-tools` | Lists every tool from the start, for clients that do not follow tool-list changes. |
| `--instance <pid \| project name>` | Fixes which open editor the session drives (also `ESTELLA_MCP_INSTANCE`). |

| Environment variable | Effect |
|---|---|
| `ESTELLA_MCP_ALLOW_WRITES=1` | Allows the tools that change the project regardless of the editor's *Read only* / *Can edit* setting. Required for a host that has no permission setting. Without it, the editor's setting decides. |
| `ESTELLA_MCP_INSTANCE` | As `--instance`. |
| `ESTELLA_MCP_CALL_LOG=0` | Disables the local call log ([Call log](#call-log)). |

The editor starts on the first tool call, not when the AI tool starts the server: the server answers the handshake
immediately, and a session that calls no tool never starts an editor.

<Aside type="caution">
When writes are not allowed, every tool that changes the project (creating entities, editing fields, saving,
exporting) is hidden from the tool list and refused. Grant writes deliberately.
</Aside>

## Attaching to an open editor

`--attach` drives an editor session that is already open:

<Steps>

1. Configure the AI tool with `--attach`:

   ```json
   "args": ["<path-to>/editor-mcp.mjs", "--attach"]
   ```

2. Make sure **Settings → Editor → Tools and AI → AI Agents → Allow AI agents to connect** is on (the default). The
   editor listens on a local-only port and writes the discovery file `mcp-endpoint.json` into its user-data folder,
   which `--attach` finds; pass an explicit path only if the file was moved. The setting row shows the listening port.

   Launching the editor with `--mcp` (`estella-editor --mcp`) enables the endpoint for that session and overrides the
   setting while it runs.

3. The agent drives the same window — selection, edits and Play mode — while the user watches and intervenes.

</Steps>

The server resolves the editor for each call, so the AI tool can start before the editor, and an editor restart
mid-session reconnects automatically.

### Multiple editors

Each editor advertises itself in `mcp-instances/<pid>.json` in the user-data folder, with its process id, project,
port and permission. With one editor open, the session drives it. With two or more, every tool except `list_editors`
and `select_editor` answers with the list of editors until one is selected.

| Tool | Description |
|---|---|
| `list_editors` | Lists open editors: pid, project, port, and whether it lets agents change the project. |
| `select_editor` | Takes a pid, a port, or part of a project name or path. The session then drives only that editor; an editor opened later does not take over. If the selected editor closes, the session asks again. |

`--instance` or `ESTELLA_MCP_INSTANCE` fixes the choice in the tool's configuration. The permission belongs to each
editor window and starts read-only. The connect dialog identifies its editor by project, process id and port.

## Tool groups

About fifty everyday tools (the scene, Play, opening and saving, screenshots, logs) are listed from the start. The
others are in groups the agent enables with `enable_tools`:

`look`, `assets`, `timeline`, `prefab`, `authoring`, `view`, `play`, `render`, `project`, `code`, `image`, `rig`, `vfx`,
`sound`, `terrain`, `modeling`, `tripo`, `device`, and `plugins` (tools added by the project's editor plugins).

Any tool can be called by name without being listed. `--all-tools` lists all of them from the start. At connection the
agent receives the operating rules: tool groups, the open scene versus the running game, `step` instead of waiting,
and one call per undo step.

| Area | Tools (excerpt) |
| --- | --- |
| Observe | `get_scene_tree`, `get_inspector`, `get_stats`, `get_diagnostics`, `capture_viewport` (PNG), `screenshot` (whole window, includes Play), `world_component` (live-World probe), `capture_frame` / `frame_draws` / `replay_draw` (the frame debugger: each draw call, why it started, the entities it drew) |
| Edit scenes | `apply_scene_ops` (batch authoring), `create_entity` (the Create-menu catalog via `list_entity_templates`), `set_field`, `set_entity_xy`, `set_parent`, `duplicate_entity`, `undo` / `redo` |
| Projects and assets | `create_project` / `open_project` / `close_project` / `reopen_project`, `open_scene`, `open_asset` (any asset in its own editor), `get_document`, `save_scene`, `create_scene_file`, `create_asset`, `import_assets`, `list_assets`, `get_import_settings` / `set_import_settings` |
| Prefabs | `create_prefab_from_entity`, `edit_prefab` / `exit_prefab_mode` (Prefab Mode), `apply_prefab`, `revert_prefab`, `unpack_prefab`, `create_prefab_variant` |
| Behaviour without code | `get_event_bindings` / `set_event_bindings`, `add_component` / `remove_component` |
| Game code | `read_project_file`, `write_project_file`, `list_project_files` |
| Run and ship | `set_play` (playing / paused / stopped) and `get_play_state`, `step`, `play_input`, `export_game` (any Package Project target: web, desktop, wechat, playable, android, …) |

A typical sequence: `open_project` → `open_scene` → `list_entity_templates` → `apply_scene_ops` → `get_diagnostics` →
`screenshot` → `save_scene` → `set_play` → `screenshot` → `export_game`.

### Tool conventions

- **Descriptions** are short enough that clients pass them whole. Tools with extended guidance (`model_write`,
  `image_write`, `music_write`, and others) name topics at the end of their description; the agent reads them with
  `tool_guide`, which is answered from the catalog and starts no editor.
- **Argument names** are uniform: an entity is `entity` (a number in the open scene or the running game), a component
  field `field`, search text `query`, a result cap `limit`. Older names (`id`, `key`, `match`, `maxResults`) are
  still accepted.
- **Entities by name.** `entity` also accepts a name, looked up in the world the tool acts on (the open scene, or the
  running game for `inspect_entity`), since the two number entities differently. A name shared by two entities is
  refused with their numbers; in the scene, a path such as `"HUD/ScoreText"` selects one.

## 2D skeletal characters

The `rig` group lets an agent build a 2D skeletal character and animate it. It works from a picture of the character's
separate parts, which can be drawn with `image_write`. `rig_write` takes bones from joint to tip and the box each part was
drawn in, and writes the `.esrig` with its `.esmesh` and `.esprefab`. Its answer is a sheet with the pose, which bones move
each part, and every joint bent both ways, so a joint that opens or a part that follows the wrong bone shows before any
animation. `rig_clip_write` writes a motion as an `.estimeline`. It shows the frames side by side and laid over each other,
with the paths of the hands and feet, and measures how far a planted foot slides. `rig_read` and `rig_clip_read` return the
same descriptions, ready to change and write again. The rig opens in the Rig editor and the clip in the Sequencer.

## Visual effects

The `vfx` group builds effects such as fire, smoke, sparks, explosions, magic and hits. `vfx_write` takes an effect
described in metres and seconds and writes it as a prefab: one particle emitter per layer, plus a light. It draws the
textures the layers name. A light that flickers or fades is played from a timeline on the prefab's root. The answer shows
the effect drawn by the engine at chosen moments without starting Play, with the number of live particles in each layer.
`vfx_read` gives the description back. The tool's topics include working numbers for common effects.

## Tripo AI

The `tripo` group generates textured 3D models from text or images with [Tripo AI](https://www.tripo3d.ai/) and
imports them like a dropped `.glb`; the result names a prefab the agent can place, with Tripo's preview image.

| Setting (Settings → Editor → Tools and AI → AI Agents) | Description |
|---|---|
| **Tripo site** | International (tripo3d.ai) or China (tripo3d.com). The sites have separate accounts, keys and credits. A running generation stays on the site that started it. |
| **Tripo API key (international)** | Key from developers.tripo3d.ai. |
| **Tripo API key (China)** | Key from developers.tripo3d.com, used when the site is China. |

Keys are stored in the machine's keychain, never in the project, and the editor window never reads them back. Every
generation spends account credits; `tripo_balance` reports the balance.

| Tool | Description |
|---|---|
| `tripo_generate` | Starts a generation from text or images (`images` accepts the four views from `tripo_image`) and returns a task id immediately. |
| `tripo_task` | Waits for a task and returns its prefab, without spending credits again. Also restores a listed result whose file is missing. |
| `tripo_process` | Creates a new model beside an existing one: retexture, reduce to a face count, unwrap UVs, split into parts and close them, check whether it can be rigged (free), rig, apply preset animations, or convert format. Also smart-segments a model or image into named parts, and converts an image to a Gaussian splat (`.splat`, not yet rendered by the engine). |
| `tripo_image` | Generates images from text or images, including four views of a subject. |
| `tripo_history` | Lists the project's Tripo jobs (request, result location, cost) and the project models Tripo made (from their `.meta`); `remote_days: 31` adds everything the account made in the last month. |
| `tripo_balance` | Reports the remaining credits. |

- A generation takes two to five minutes. The editor polls Tripo and imports the model when it is ready, whether or
  not the agent is still waiting. A notice in the corner shows running generations (one by name and percentage,
  several as a count with **Details**), and the Content Browser shows a placeholder with progress where each model
  will land. A generation still running when the editor closes resumes when the project is next opened.
- A model made by Tripo stores its task id in its `.meta`, so later operations reference the task instead of
  uploading the file; other models are uploaded.
- Each tool's description states its credit cost; every operation except the rig check spends credits.
- The import happens outside the agent's undo step: Undo does not remove a generated model. Delete it from the Content
  Browser.

## Editing a prefab

`open_asset` on a `.esprefab`, or `edit_prefab` on an instance, enters **Prefab Mode**: every scene tool then acts on
the prefab, and `save_scene` writes the prefab asset for every instance. `get_document` reports which document is
open; check it after opening and before assuming a save writes a scene. `exit_prefab_mode` returns to the scene.

Where a user receives a confirmation dialog, the agent receives a refusal it can act on: opening something that would
discard unsaved work is refused unless `discardChanges` is passed, and `apply_prefab`, which rewrites the prefab for
every instance, requires `confirm: true`.

## Batch scene programs

`set_field` writes one field per call. `apply_scene_ops` takes a **program** — creates, re-parents, component adds and
field writes — executed in order as **one undoable step**. Ops address entities they create by `ref`, so a subtree
lands in one call:

```json
{
  "label": "Build HUD",
  "ops": [
    { "op": "create", "ref": "hud", "name": "HUD", "template": "ui-container" },
    { "op": "create", "ref": "coins", "name": "Coins", "template": "ui-text", "parent": "$hud",
      "fields": { "Text.content": "1440", "Text.fontSize": 28 } }
  ]
}
```

The program is atomic: if an op fails, the error names it (`op[7] set: …`) and the whole batch rolls back, including
entities already created.

A field path may name one member of a structured field (`"Transform.position.x"`, `"FlexContainer.gap.y"`,
`"UINode.width.value"`); the other members are preserved.

A large program can be written to a file with `write_project_file` and passed by path:

```json
{ "opsPath": "assets/scenes/shop.ops.json", "label": "Build the shop" }
```

## Event bindings

An [Event Binding](/docs/scripting/events/) row runs a named action when an event fires, giving a button behaviour
without game code. `set_event_bindings` replaces an entity's rows in one undo step (an empty list removes them), and
`get_event_bindings` reads them:

```json
{ "entity": 42, "rows": [
  { "event": "click", "action": "panel.open",
    "params": { "prefab": "assets/prefabs/Shop.esprefab" } }
] }
```

`action` is any name in the action registry — an engine built-in (`property.set`, `ui.setVisible`, `fsm.fire`, …) or
one the project registered. `target` names another entity to run it on, resolved nearest-first from this one.

<Aside type="caution">
`EventBinding` has no Add Component entry (the Details panel adds it with the first binding), so `add_component`
cannot create it; use `set_event_bindings`. `add_component` refuses unknown component names.
</Aside>

<Aside type="note">
Some properties are **import settings**, not component fields. A `UIVisual` in NineSlice mode reads its border from the
texture's metadata, so a frame authored without `set_import_settings` stretches its corners. `get_import_settings`
lists every setting with its default. `set_import_settings` accepts an **array** of paths to apply one patch to many
assets; each asset keeps the settings the patch does not name.
</Aside>

## Undo, permissions and progress

- **One call is one undo step.** Everything a call changes — scene edits and the project files it writes — is undone
  with one **Ctrl/⌘ + Z** and redone with Redo. The step appears in **History** as **AI · *tool***. A call that only
  wrote files does not mark the scene unsaved. The agent's `undo` / `redo` tools return once the files are restored.
  Saving, exporting, creating a project and actions on the running game are not undo steps.
- **Agent runs in History.** History draws a rule at the start of each agent run (**AI run · *client* · *time***);
  clicking the row just above it undoes the whole run. Copies of written files are kept up to 512 MB; a step whose
  copies were discarded is marked **files kept**, and undoing it restores only the scene part.
- **Tool annotations.** Every tool carries MCP annotations: reading tools are marked read-only, and only tools that
  leave the project or run arbitrary code (an editor command, a probe in the running game) are marked destructive.
- **Progress.** A client that requests progress receives a notice every five seconds naming the running tool and its
  duration. A call cancelled before it starts does not run; a composite call stops at its next step; an editor
  operation already running (an export, a bake) finishes.
- **Startup failures.** If the editor cannot start, the call returns the editor's reason and the next call retries;
  the connection stays open.

### Call log

The server records each call — tool, client, outcome, time and the start of any error, never the arguments — in
`~/.estella/mcp-calls.jsonl`. `node desktop/scripts/mcp-call-stats.mjs` lists the tools that fail most often and how.
Nothing is sent anywhere. `ESTELLA_MCP_CALL_LOG=0` disables the log.

## From a source checkout

In a source checkout, `pnpm --filter @estella/editor editor:mcp` serves the tool registry against a headless fixtures
host (scene tools only); `editor:mcp -- --editor` boots the development editor (`--hidden` keeps its window hidden).
The `editor:mcp:e2e` and `editor:mcp:editor-e2e` suites test the full loop.
