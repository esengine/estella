A texture is an image on the GPU. You reference one by project path, load it into a
**handle**, and put that handle on a component — `Sprite.texture`, a material sampler,
a bitmap font page. This page is about the image itself: what it can be, what you can
set on it, and how to find out how big it is.

For sprites — the component that draws a texture — see [Sprites](/docs/graphics/sprites/).
For the general asset system (refs, groups, the manifest), see [Assets](/docs/assets/overview/).

## Supported formats

| Extension | Notes |
|---|---|
| `.png` | The default for art with transparency. |
| `.jpg` / `.jpeg` | No alpha channel; smaller for photographic art. |
| `.webp` | Alpha + good compression. Decoded by the browser/runtime. |
| `.gif` | First frame only — this is a still image, not an animation. |
| `.bmp` | Uncompressed; works, but rarely what you want to ship. |
| `.ktx2` | Basis Universal, already GPU-compressed. What the cook step **produces** — you can also author one directly. |

An `.aseprite` / `.ase` file is not a texture — importing one **produces** a sheet
`.png` (plus a clip per tag) and that is what a scene references. See
[Sprite animation](/docs/animation/overview/#from-an-aseprite-file).

`.png`, `.jpg` and `.webp` are the ones to author in. A build's cook step turns them
into `.ktx2` when compression is on (see [Import settings](#import-settings)).

## Loading a texture

`assets.loadTexture(ref)` resolves the ref, uploads the image, and returns the handle
**with the image's pixel dimensions** — this is the answer to "how do I get the width
and height":

```typescript
import { defineSystem, Res, Assets } from 'esengine';

const measure = defineSystem([Res(Assets)], async (assets) => {
  const tex = await assets.loadTexture('assets/textures/player.png');
  tex.handle;   // TextureHandle — what a component field takes
  tex.width;    // the image's pixel width
  tex.height;   // the image's pixel height
});
```

The width and height are the **source image's** pixels, not the size anything draws
at. A `Sprite` drawing that texture has its own `size` in world units, which is a
separate number you can set to anything (it starts out matching — see
[Sizing a sprite to its texture](#sizing-a-sprite-to-its-texture)).

Putting one on a sprite at its own pixel size:

```typescript
import { defineSystem, Query, Mut, Res, Sprite, Assets } from 'esengine';

const showArt = defineSystem([Query(Mut(Sprite)), Res(Assets)], async (q, assets) => {
  const tex = await assets.loadTexture('assets/textures/player.png');
  for (const [entity, sprite] of q) {
    sprite.texture = tex.handle;
    sprite.size = { x: tex.width, y: tex.height };   // 1 image pixel = 1 world unit
  }
});
```

<Aside type="note">
  `loadTexture` is cached and reference-counted by resolved path: loading the same
  image twice returns the same handle and does not upload it twice. Release with
  `assets.releaseTexture(ref)` — it takes the same **ref you loaded**, not the
  handle. Assets a scene references are released with the scene. See
  [Lifetime & reference counting](/docs/assets/overview/#lifetime--reference-counting).
</Aside>

### From a handle you did not load

A sprite placed in the editor already has its texture: the scene file named it, the
loader resolved it, and your code never saw a `TextureResult`. To measure that one,
ask the resource manager for the handle's dimensions:

```typescript
import { defineSystem, Query, Sprite } from 'esengine';
import { getTextureDimensions } from 'esengine/tilemap';

const measurePlaced = defineSystem([Query(Sprite)], (q) => {
  for (const [entity, sprite] of q) {
    const dims = getTextureDimensions(sprite.texture);   // { width, height } | null
    if (dims) { /* … */ }
  }
});
```

It returns `null` until the texture is actually uploaded — a scene's textures load
asynchronously, so a system running on the first frame can legitimately see nothing.

<Aside type="caution">
  `getTextureDimensions` is **`@experimental`**: no compatibility claim, and it may
  change or disappear in any release (see [API stability](/docs/reference/api-stability/)).
  `loadTexture`'s `{ width, height }` is the settled way to learn an image's size.
</Aside>

### Two loads, one image

`loadTextureRaw(ref)` uploads the image **without the vertical flip** `loadTexture`
applies. Flipped and unflipped are genuinely different GPU objects, so they are cached
separately. You want `loadTexture` unless you are feeding a pipeline that already
expects bottom-up rows.

## Import settings

Import settings belong to the **image**, not to any entity using it. They are stored
in the `.meta` file next to it and edited by selecting the image in the Content
Browser — every sprite that uses the texture inherits them.

| Setting | Default | What it does |
|---|---|---|
| **Use** | `Colour` | What the image holds. **Colour** is a picture: a build may shrink it to Max Size, compress it and fill the colour under its clear texels. **Data** is numbers a texel, read as they are (a heightmap, a mask of measured values, a lookup table): a build keeps its depth (a 16-bit PNG stays 16 bits), never compresses it or decodes it as sRGB, and shrinks it only when Max Size says so, at that depth. A PNG of 16 bits a sample is imported as Data, a texture given to a `Terrain` as its heightmap is marked Data when it is, and Project Health lists any that are read as numbers and still set up as pictures, with a one-click fix. |
| **Max Size** | `2048` | Downscale cap applied at cook (256 to 8192, a power of two). A source larger than this on its longest side is box-filtered down; a smaller source is untouched. **Source size** never shrinks it, and is what a Data texture starts at. |
| **Compression** | `Auto` | **GPU compressed** ships a KTX2 (Basis Universal) that stays compressed in video memory — about a quarter of the decoded image — and transcodes per device. **Original image** ships the file as it is: exact, and for flat art far smaller to download, but decoded in full on the GPU. **Auto** is GPU compressed for a texture a mesh draws (directly or through its material) and the original image for sprites and UI. A build does what this row says; it never swaps one for the other because a file came out smaller. |
| **Compress Format** | `uastc` | `uastc` — high quality, larger. `etc1s` — much smaller, lower quality (good for photographic art). Only used when the texture is GPU compressed. |
| **Mip Maps** | on | Keep a chain of half-size copies so a texture drawn small samples a filtered image instead of shimmering; costs a third more memory. Turn it off for pixel art and UI that is always drawn at its own size. |
| **Filter** | `linear` | Sampling filter. `nearest` keeps pixel art crisp; `linear` smooths. |
| **Wrap** | `repeat` | How UVs outside `[0,1]` are addressed: `repeat`, `clamp`, `mirror`. |
| **sRGB Color** | `true` | The image stores sRGB-encoded color (albedo, UI). Disable for authored-linear data — normal maps, masks. Only meaningful when the project renders in linear color. |
| **Alpha Is Transparency** | `true` | When the texture is cooked (for a build and for the editor alike), fully clear texels take the colour of their solid neighbours, so filtering and mip maps at a transparent edge — a rounded panel's corner — no longer average in the black under alpha 0 as a dark fringe. Partly clear and solid texels keep their colour; premultiplied art is left alone. Turn off for an image whose RGB under alpha 0 a shader reads as data. |
| **Mip Coverage Cutoff** | `0` | For a cutout (leaves, grass, fences): the alpha cutoff its material tests. Each mip level keeps the share of texels above it that the full image has, so the cutout does not thin out with distance. `0` = off (0 to 1); applies to UASTC-compressed textures. |
| **9-Slice Border** | `0,0,0,0` | Left/right/top/bottom border in **texture pixels**: where the image's corners end. Authored once here, inherited by every `UIVisual` set to Sliced. |
| **Cell Width / Cell Height** | `0` | The size of one cell of a sprite sheet, in pixels. `0` means the image is not a sheet; setting it lets a `Sprite` pick a frame of the image instead of showing all of it. |
| **Margin** | `0` | Padding before the first cell, on both axes. |
| **Spacing** | `0` | Gap between neighbouring cells, paid between cells only, never after the last one. |

<Aside type="tip">
  **Pixel art**: set Filter to `nearest` and Compression to **Original image** (Auto already
  ships a sprite that way). Linear filtering
  blurs the pixels you drew, and block compression puts artefacts exactly where hard
  colour edges are.
</Aside>

### Editing a whole folder at once

Select several images (ctrl/cmd-click, shift-click, or Select All) and the inspector
edits **all of them**. A setting they already agree on shows its value; one they
disagree on shows a dash — type into it and every selected image takes that value.
Save writes only the settings you touched, so the ones each image had its own answer
for are left alone. Sprites and textures share a schema and batch together; a
selection that mixes in an audio clip or a model says so instead, since there is no
field they all have.

The 9-slice border editor stays on a single selection — it draws one image, and there
is no honest picture of forty.

### Per-platform overrides

Max Size, Compression and Compress Format can be overridden **per platform** — the tabs
beside Default in Import Settings. This is the "encode once, transcode per GPU"
pipeline: ship the desktop build a 2048 UASTC texture and the WeChat build a 1024
ETC1S one from the same source file. See
[Cooking & compression](/docs/assets/overview/#cooking-compression--content-addressing).

## Sizing a sprite to its texture

`Sprite.size` is in **world units** and deliberately independent of the image — that
is what lets you scale art without touching the file. But nobody wants to type the
image's dimensions, so the editor fills them in:

- **Dragging an image** from the Content Browser into the viewport spawns a sprite
  already sized to the image's pixels.
- **Assigning a texture** to an existing sprite sizes it to that texture too, and a
  later swap follows the new image.

It stops as soon as the number is yours: once you set `size` by hand, changing the
texture leaves it alone. (Undo history shows the fit as its own **Fit Sprite To
Texture** step, so you can keep a size and drop only the fit.)

In code there is no such helper: a `Sprite` given only a texture keeps its default
`size`, so pass `tex.width`/`tex.height` yourself as shown above.

## Sub-rectangles and atlases

A sprite can draw part of a texture with `uvOffset` / `uvScale`, both normalized
fractions of the whole image:

```typescript
// The 32×32 frame at column 2, row 1 of a 256×256 sheet.
sprite.uvOffset = { x: 64 / 256, y: 32 / 256 };
sprite.uvScale  = { x: 32 / 256, y: 32 / 256 };
```

For sheet animation, author a flipbook instead of computing these by hand — see
[Animation](/docs/animation/overview/). For tile art, see
[Tilemaps](/docs/world/tilemaps/).

## Texture recipes

A texture can be shipped as how it is drawn and not as its pixels. An **`.esimage`** is a picture's source: layers of shapes, gradients,
noise and grids, the file the image tools write and draw a `.png` from. Name the `.esimage` itself where a texture goes (a sprite, a
material) and the package carries the source; the picture is drawn on the device when the texture is first loaded, to the very pixels
its `.png` has.

```json
{ "type": "Sprite", "data": { "texture": "assets/tex/plate.esimage", "size": { "x": 512, "y": 512 } } }
```

A 512 pixel plate of noise, rust, a stripe and rivets is 691 bytes as a recipe and 351 KB as a PNG. What draws recipes is the
`esengine/image` module, about 172 KB of a web package before compression (62 KB gzipped): an export adds it when a recipe ships, and a script that
loads one by code imports it where the game starts. A package with no recipe does not carry it.

What a recipe costs is time, once. It is drawn on a worker thread, so the game keeps running while it draws, and the pixels are
kept in the device's content cache: the next run reads them and draws nothing. A 2048 pixel plate took 4.1 s on a desktop worker
the first visit, with the main thread never held longer than its usual start-up; the second visit drew nothing. The kept pixels are
uncompressed (16 MB for that plate) and nothing removes them unasked: `assets.cleanDiskCache(budget, true)` gives up what was read
longest ago first, and a removed picture is drawn again. Where there are no workers the recipe is drawn on the main thread; where there is no cache it is drawn every run. A changed recipe, or a changed raster, is a
different entry, so nothing stale is ever read.

A picture with a `figure` layer or text needs the authoring tools to draw and is baked to its `.png` instead; so is a source's
surface (its normal and roughness maps).

## Memory & residency

Textures are the largest thing most 2D games hold, and they are reference-counted and
evictable rather than resident forever. Budgets, the LRU, and reading actual usage are
covered in [Texture memory & budgets](/docs/assets/overview/#texture-memory--budgets).

The short version: a texture nothing references can be evicted under memory pressure
and is revived transparently on the next load of the same path.
