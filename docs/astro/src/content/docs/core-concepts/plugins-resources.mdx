---
title: Plugins & Resources
description: How subsystems are composed and reached — the Res(XxxAPI) pattern.
---

An Estella game is an `App` composed of **plugins**. Each subsystem — physics,
audio, tilemaps, particles, UI, and so on — is a plugin that registers its
systems and exposes a runtime API as a **resource**.

## Reaching a subsystem: `Res(XxxAPI)`

Inside a system, list the resource you need in the parameter array; the callback
receives it in the same order:

```typescript
import { defineSystem, Res, Audio } from 'esengine';

defineSystem([Res(Audio)], (audio) => {
  audio.playSFX('assets/hit.wav');
});
```

Every subsystem's imperative API is reached the same way:

| Subsystem | Resource | Guide |
|---|---|---|
| Input | `Res(Input)` | [Input](/docs/scripting/input/) |
| Audio | `Res(Audio)` | [Audio](/docs/assets/audio/) |
| Assets | `Res(Assets)` | [Assets](/docs/assets/overview/) |
| Tilemaps | `Res(Tilemaps)` | [Tilemaps](/docs/world/tilemaps/) |
| Particles | `Res(Particle)` | [Particles](/docs/world/particles/) |
| Post-processing | `Res(PostProcess)` | [Post-processing](/docs/graphics/post-processing/) |
| Scenes | `Res(SceneManager)` | [Scenes](/docs/world/scenes/) |
| Tweens | `Res(Tween)` | [Animation](/docs/animation/overview/) |
| Frame animation | `Res(SpriteAnimation)` | [Animation](/docs/animation/overview/) |
| Animator | `Res(AnimatorController)` | [Animation](/docs/animation/overview/) |
| Timers | `Res(TimerRes)` | [Scripting](/docs/scripting/overview/) |
| Timeline | `Res(Timeline)` | [Timeline](/docs/animation/timeline/) |
| Prefabs | `Res(Prefabs)` | [Prefabs](/docs/world/prefabs/) |
| Navigation / AI | `Res(Nav)` | [Gameplay AI](/docs/gameplay/ai/overview/) |
| Localization | `Res(Localization)` | [Localization](/docs/assets/localization/) |
| Camera view | `Res(CameraView)` | [Camera](/docs/graphics/camera/) |
| UI events | `Res(UIEvents)` | [UI](/docs/ui/overview/) |
| Physics | `Res(Physics)` — from `esengine/physics` | [Physics](/docs/gameplay/physics/) |
| Spine | `Res(Spine)` — from `esengine/spine` | [Spine](/docs/animation/spine/) |

Physics and Spine are **optional side-modules** loaded on demand, so their APIs
live on subpaths to keep the base bundle small; everything else is in the main
`esengine` package. All the base subsystems above ship in the standard app — no
plugin wiring needed.

Some subsystems also publish **event resources** on the same pattern — a
resource whose contents are this frame's events, read the same frame:
`Res(PhysicsEvents)` (contacts), `Res(SpineEvents)` (animation events),
`Res(UIEvents)` (clicks and input from widgets).

<br />

`Res(X)` gives read access; use `ResMut(X)` when the system **replaces or
mutates the resource's state** — same contract as `Mut` on components.

## Components vs. resources

- **Components** are per-entity data. You attach them (in the editor or with
  `Commands`) and iterate them with `Query`.
- **Resources** are per-app singletons — shared state and subsystem APIs — read
  with `Res`.

## Getting an entity

Subsystem APIs act on an entity, and that entity comes from a `Query` (or a
spawn). This is the shape you'll see throughout the guides:

```typescript
import { defineSystem, Query, Res, SpriteAnimator, Tween, TweenTarget } from 'esengine';

defineSystem([Query(SpriteAnimator), Res(Tween)], (q, tween) => {
  for (const [entity] of q) {
    tween.to(entity, TweenTarget.PositionX, 0, 100, 1.0, {});
  }
});
```

## Spawning: `Commands`

To create entities and attach components from a system, take `Commands()`:

```typescript
import { defineSystem, Commands, Transform, Sprite } from 'esengine';

defineSystem([Commands()], (cmds) => {
  cmds.spawn()
    .insert(Transform, { position: { x: 0, y: 0, z: 0 } })
    .insert(Sprite, { size: { x: 32, y: 32 } });
});
```
