A **system** is a function the schedule runs every frame. Its parameter list declares the data it receives — queries
over components, resources, commands and events — and the system is called with exactly those values.

```typescript
import {
    defineComponent, defineSystem, addSystem,
    Query, Mut, Res, Time, Transform
} from 'esengine';

const Speed = defineComponent('Speed', { value: 200 });

addSystem(defineSystem(
    [Res(Time), Query(Mut(Transform), Speed)],
    (time, query) => {
        for (const [entity, transform, speed] of query) {
            transform.position.x += speed.value * time.delta;
        }
    }
));
```

`defineSystem(params, fn, options?)` returns a `SystemDef`. The callback receives one argument per parameter, in the
same order.

## Parameters

| Parameter | Callback receives |
|---|---|
| `Query(...)` | An iterable over every entity that has all listed components. Each item is `[entity, ...components]`. |
| `Mut(Component)` | Inside a query: a component the system writes. Unwrapped components are read-only. |
| `Res(Resource)` | The resource value itself, for reading (for example `Time`). |
| `ResMut(Resource)` | A handle around the resource: `.get()`, `.set(v)`, `.modify(fn)`. |
| `Commands()` | Deferred structural changes (spawn, despawn, insert, remove). They are applied when the declaring system returns, so systems that run later in the same frame see them. |
| `EventReader(E)` / `EventWriter(E)` | A typed event stream to read or send ([Events](#events)). |
| `GetWorld()` | The `World` itself ([Declared access](#declared-access)). |
| `Removed(C)` | The entities that lost component `C` ([Filters](#filters-and-change-detection)). |

<Aside type="caution">
  Wrap a component in `Mut` only when the system writes it. Read-only access skips change-detection work, and the
  parameter list is what the scheduler reads to decide whether two systems conflict
  ([Declared access](#declared-access)).
</Aside>

## Options

| Option | Type | Description |
|---|---|---|
| `name` | `string` | Name referenced by ordering edges and shown in timings. |
| `runBefore` | `string[]` | The system runs before each named system or set. |
| `runAfter` | `string[]` | The system runs after each named system or set. |
| `runWhenPaused` | `boolean` | Runs in `First`, `PreUpdate`, `Update` and `PostUpdate` while the app is paused. `Last` always runs; fixed steps stay stopped. |
| `touches` | `SystemTouches \| () => SystemTouches` | Components reached through `GetWorld()` ([Declared access](#declared-access)). |

## Schedules

Systems are registered into a **schedule** of ordered phases:

| Phase | When it runs |
|---|---|
| `Startup` | Once, before the first frame. |
| `First` → `PreUpdate` → `Update` → `PostUpdate` → `Last` | Every frame, in this order. |
| `FixedPreUpdate` → `FixedUpdate` → `FixedPostUpdate` | On the fixed timestep, zero or more times per frame. |

| Function | Registers into |
|---|---|
| `addSystem(system)` | `Update` |
| `addStartupSystem(system)` | `Startup` |
| `addSystemToSchedule(Schedule.X, system)` | Any phase |

These top-level functions queue registrations at module scope; the `App` methods of the same names register on a
specific app ([App API](/docs/core-concepts/app/app-api/#systems-and-events)). Within one frame the phases run as
listed in [The frame loop](/docs/core-concepts/app/app-api/#the-frame-loop).

Systems registered by a scene run only while that scene is active, so several scenes can share one world.

## Ordering

Within a phase, systems run in **registration order**. Phase order is fixed: input read in `PreUpdate`, movement in
`Update` and camera follow in `PostUpdate` need no further ordering.

### Ordering edges

`runBefore` and `runAfter` order a system relative to other systems in the same phase. Edges reference system
**names**. Edges declared on `defineSystem` travel with the definition, which is how a system registered with the
top-level `addSystem` (which takes no options) is ordered:

```typescript
const move = defineSystem([...], moveFn, { name: 'move' });
const camera = defineSystem([...], cameraFn, {
  name: 'camera',
  runAfter: ['move'],
});

addSystem(move);
addSystem(camera);
```

`app.addSystemToSchedule(schedule, system, options)` accepts the same edges plus `runIf` and `activeWhen`. Edges given
at registration are **added** to those declared on the definition:

```typescript
import { Schedule } from 'esengine';

app.addSystemToSchedule(Schedule.Update, camera, {
  runAfter: ['input'],         // in addition to the 'move' edge
  runIf: () => isPlaying,      // the system is skipped while this returns false
});
```

| Registration option | Description |
|---|---|
| `runBefore` / `runAfter` | Additional ordering edges. |
| `runIf` | Run condition checked every frame; `false` skips the system. |
| `activeWhen` | Components the system's work depends on. While no entity has any of them the system is skipped; it runs for one more frame after the last one is removed. |

An edge naming a system that is not in the phase is ignored. Edges that form a cycle make the scheduler throw with
the offending path, for example `Circular system dependency: move → camera → move`.

<Aside type="note">
  The top-level `addSystem` / `addSystemToSchedule` take no options; `name`, `runBefore` and `runAfter` are declared
  on `defineSystem`. A run condition has no definition-site form: it is given to `app.addSystemToSchedule` or to the
  enclosing system set.
</Aside>

### System sets

`defineSystemSet(name, options)` groups systems under one name. The set's `runIf` and edges apply to every member,
and any system or set can order itself against the set's name.

| Option | Type | Description |
|---|---|---|
| `systems` | `SystemDef[]` | Members, run in the order listed. |
| `runIf` | `() => boolean` | Checked every frame; `false` skips every member. |
| `runBefore` / `runAfter` | `string[]` | Edges applied to every member. |

```typescript
import { Schedule, defineSystemSet } from 'esengine';

const physics = defineSystemSet('physics', {
  systems: [applyForces, integrateVelocity, resolveContacts],
  runBefore: ['render'],
  runIf: () => !paused,
});

app.addSystemSetToSchedule(Schedule.FixedUpdate, physics);

// One edge orders against every member of the set:
app.addSystemToSchedule(Schedule.FixedUpdate, debugDraw, { runAfter: ['physics'] });
```

`app.addSystemSet(set)` registers a set into `Update`.

### Numeric priorities

There is no numeric priority option. Registration order is the default order, so a numeric scheme is implemented by
sorting before registration:

```typescript
const ordered = [
  { order: 100, system: input },
  { order: 200, system: move },
  { order: 300, system: camera },
];
for (const { system } of ordered.sort((a, b) => a.order - b.order)) {
  app.addSystemToSchedule(Schedule.Update, system);
}
```

## Filters and change detection

```typescript
// Presence filters — components required or excluded but not read:
Query(Transform, Mut(Velocity)).without(Frozen).with(Enemy)

// Boolean combinations:
import { Query, With, Without, Or, Not } from 'esengine';
Query(Transform).filter(Or(With(Player), With(Ally)))

// Change detection — entities whose component was added or changed since this system last ran:
import { Query, Added, Changed } from 'esengine';
Query(Added(Health))
Query(Changed(Transform))
```

| Filter | Matches |
|---|---|
| `.with(C)` / `.without(C)` | Entities that have / do not have `C`. |
| `.filter(expr)` | A boolean expression built from `With`, `Without`, `Or` and `Not`. |
| `Added(C)` | Entities whose `C` was added since the system last ran. |
| `Changed(C)` | Entities whose `C` was written since the system last ran. |

`Removed(C)` is a separate parameter that yields the entities that lost `C`:

```typescript
import { defineSystem, Removed } from 'esengine';

defineSystem([Removed(Health)], (removed) => {
  for (const entity of removed) { /* cleanup */ }
});
```

A query result provides the following methods besides `for…of`:

| Method | Returns |
|---|---|
| `single()` | The first match, or `null`. For a single player or camera. |
| `count()` | Number of matches. |
| `isEmpty()` | Whether there are no matches. Does not mark `Mut` components as changed. |
| `toArray()` | All matches as an array. |
| `forEach((entity, ...components) => …)` | Calls the callback per match. |

## Declared access

A system's parameter list declares its access: `Query(Mut(Transform))` writes `Transform`, `Res(Time)` reads `Time`.
The scheduler uses this to determine whether two systems can run at the same time and whether their relative order
was specified.

`GetWorld()` gives unrestricted access, so a system that takes it conflicts with every other system. The `touches`
option declares what such a system actually reads and writes, by component name:

```typescript
defineSystem([GetWorld()], (world) => { /* ... */ }, {
  name: 'Perception',
  touches: {
    reads: ['Perceiver', 'Transform'],
    writes: ['Perception'],
  },
});
```

| `SystemTouches` field | Description |
|---|---|
| `reads` | Component names the system reads. |
| `writes` | Component names the system writes. |
| `opaque` | `true` states that the access cannot be fully named. Treated like an omitted `touches` (conflicts with everything), but declared explicitly. |

Components are named by string because a system reaching through the world usually accesses types registered after
it. `touches` may be a function, re-evaluated each time the access is read; a system that runs authored data uses
this to report the access of the data actually loaded — the state-machine system reports the union over the leaves
the loaded `.esfsm` graphs name. `defineBehavior` accepts `touches` for the same purpose
([Scripting](/docs/scripting/overview/#declaring-accessed-components)).

### Asynchronous systems

Systems start in schedule order, and a synchronous system runs to completion before the next one starts. While an
**async** system is suspended on an `await`, the scheduler may start the next system if that system neither depends
on it nor touches the same data. Two async systems loading unrelated data therefore wait concurrently. A required
order between them is expressed with an ordering edge, not by registration order.

### Unordered conflicts

Two systems in one phase that touch the same data without an edge between them run in the order registration
produced, which changes when systems or plugins are added or reordered. The app reports such pairs (both methods
are `@beta`):

```typescript
app.scheduleAmbiguities(Schedule.Update);
// [{ a: 'Move', b: 'Cull', over: ['Transform'] }]

app.scheduleBatches(Schedule.Update);
// [['Move', 'Spin'], ['Cull']]
```

| Method | Returns |
|---|---|
| `scheduleAmbiguities(schedule)` | Pairs of systems that touch the same data with no edge between them, and the data they share. |
| `scheduleBatches(schedule)` | The phase grouped into batches of systems that could run at the same time; a measure of how much of the phase is inherently sequential. |

An ambiguity is resolved by adding an ordering edge or by removing the overlap.

## Events

Events are a typed message stream between systems with no direct reference to each other. `defineEvent<T>(name)`
defines an event, `app.addEvent` registers it, and systems take `EventWriter` / `EventReader` parameters:

```typescript
import { defineEvent, defineSystem, EventWriter, EventReader, Commands } from 'esengine';

const Damaged = defineEvent<{ entity: number; amount: number }>('Damaged');
app.addEvent(Damaged);

// Producer
addSystem(defineSystem([EventWriter(Damaged)], (damaged) => {
  damaged.send({ entity: 12, amount: 5 });
}));

// Consumer — reads what was sent since it last ran
addSystem(defineSystem([EventReader(Damaged), Commands()], (damaged, cmds) => {
  for (const evt of damaged) { /* evt.entity, evt.amount */ }
}));
```

Event channels are double-buffered and swapped every frame. A reader is iterable and also provides `isEmpty()` and
`toArray()`. The **event-system** example shows the complete producer/consumer pattern. Entity-addressed events
authored in the editor are described in [Event Binding](/docs/scripting/events/).
