Every entity that has a position in the world carries a `Transform`: position, rotation and scale. This page defines
the Transform fields, the unit system (world units are design pixels; physics uses metres), the coordinate
conventions, and how transforms compose through the parent/child hierarchy.

## The `Transform` component

`Transform` stores **local** values, which are authored, and **world** values, which the engine computes. Local
fields are relative to the parent, or to the world origin for an entity without a parent. Each frame the transform
system composes the local values down the hierarchy and writes the results to the world fields.

| Property | Type | Default | Description |
|---|---|---|---|
| `position` | Vec3 | `{0, 0, 0}` | Local position in world units, relative to the parent. In a 2D scene `z` breaks draw-order ties within a sorting layer. |
| `rotation` | Quat | `{w: 1, x: 0, y: 0, z: 0}` | Local rotation as a quaternion; identity means no rotation. 2D rotation is about Z ([Rotation in 2D](#rotation-in-2d)). |
| `scale` | Vec3 | `{1, 1, 1}` | Local scale per axis. `1` is original size; negative values mirror. |
| `worldPosition` | Vec3 | `{0, 0, 0}` | **Read-only.** World-space position composed by the engine. |
| `worldRotation` | Quat | identity | **Read-only.** World-space rotation. |
| `worldScale` | Vec3 | `{1, 1, 1}` | **Read-only.** World-space scale. |

Systems write the local fields and read the world fields. Writes to the world fields do not persist: the transform
system recomputes them from the local fields and the parent chain. For a root entity, world equals local.

```typescript
import { defineSystem, Query, Mut, Transform } from 'esengine';

const drift = defineSystem([Query(Mut(Transform))], (q) => {
  for (const [entity, t] of q) {
    t.position = { x: t.position.x + 1, y: t.position.y, z: t.position.z }; // write local
    console.log(t.worldPosition.x);                                        // read world
  }
});
```

| Capability | Fields |
|---|---|
| Animatable by the [Sequencer](/docs/animation/timeline/sequencer/) and [tweens](/docs/animation/tweens/) | `position.x/y/z`, `rotation.x/y/z/w`, `rotation.angle` (the Z rotation in radians; the other two axes are left unchanged), `scale.x/y/z` |
| Replicated by [state replication](/docs/scripting/networking/replication/) | `position`, `rotation`, `scale` |

The Details panel displays rotation as **X / Y / Z Euler angles in degrees**, applied X, then Y, then Z; 2D content
rotates about Z only. The stored value is always the quaternion.

<Aside type="note">
  `LocalTransform` and `WorldTransform` are exported as aliases of the same component:
  `Transform === LocalTransform === WorldTransform`. One component holds both the local and the world data.
</Aside>

## Coordinate system

| Space | Convention |
|---|---|
| World | **Y-up.** `+X` is right, `+Y` is up. Angle `0` points along `+X`; positive angles turn counter-clockwise, so `Math.atan2(dy, dx)` gives the angle toward a target. |
| 3D | Same axes. `z` is a spatial axis; cameras and lights look down `-Z`, and the ground plane is XZ. Applies to meshes, perspective cameras and [3D physics](/docs/gameplay/physics-3d/overview/). |
| 2D | `position.z` is a draw-order tie-break. Renderers sort first by their sorting `layer`, then by `z` within the layer, or by Y in a [y-sorted layer](/docs/graphics/sprites/sorting/#y-sorted-layers). `z` does not scale or foreshorten sprites. |
| Screen | **Y-down.** Pointer coordinates (`Input.mouseX` / `mouseY`, UI hit testing) are pixels from the **top-left** of the canvas. |

The `CameraView` resource converts between screen and world coordinates (full API in
[Camera](/docs/graphics/camera/overview/#screen--world-coordinates)):

```typescript
import { defineSystem, Res, CameraView, Input } from 'esengine';

const pick = defineSystem([Res(CameraView), Res(Input)], (view, input) => {
  // Screen px (Y-down, top-left origin) -> world units (Y-up). null without a camera.
  const world = view.screenToWorld(input.mouseX, input.mouseY);
  if (world) { /* world.x, world.y */ }
});
```

## Units

Authoring uses one spatial unit, the design pixel. Physics uses one derived unit, the metre.

```text
screen px (Y-down)  ── CameraView.screenToWorld ──▶  world units = design px (Y-up)
world / design px   ── ÷ Canvas.pixelsPerUnit (100) ──▶  physics metres (Box2D)
```

### Design pixels

**1 world unit = 1 design pixel.** The default design resolution is 1920×1080 (`Canvas.designResolution`), and
editor scene cameras are authored with `orthoSize = designResolution.y / 2 = 540`, so the camera shows exactly one
design resolution of world. Consequently:

- A texture dropped into the scene creates a sprite at the texture's **pixel size**; a 128×128 image is 128×128 world
  units at default zoom.
- `UINode` pixel sizes map 1:1 to design pixels under scene cameras.
- Gameplay distances, offsets and speeds are in design pixels (px, px/s).

The fit of the design resolution onto real screens is described in
[Screen & Design Resolution](/docs/core-concepts/screen/overview/).

### Physics metres

`Canvas.pixelsPerUnit` (default `100`) is the number of world pixels per physics **metre**. It scales the Box2D world
and tile colliders and is not a sprite display scale.

| Physics surface | Unit |
|---|---|
| Collider dimensions (`halfExtents`, `radius`, …) | **metres** (pixels ÷ `pixelsPerUnit`) |
| Solver methods — forces, impulses, velocities, `setGravity` | **metres** |
| Spatial queries — `raycast`, `shapeCast*`, `overlapCircle`, `overlapAABB` | **world pixels** (scaled automatically) |
| `CharacterController2D.velocity` / `moveCharacter` | **world pixels** per second |

The defaults are exported as constants read from the engine's Canvas defaults:

```typescript
import { DEFAULT_DESIGN_WIDTH, DEFAULT_DESIGN_HEIGHT, DEFAULT_PIXELS_PER_UNIT } from 'esengine';

DEFAULT_DESIGN_WIDTH;    // 1920
DEFAULT_DESIGN_HEIGHT;   // 1080
DEFAULT_PIXELS_PER_UNIT; // 100

const radiusMeters = 24 / DEFAULT_PIXELS_PER_UNIT; // a 24 px circle collider
```

## Rotation in 2D

`Transform.rotation` is a quaternion `{w, x, y, z}`. A 2D rotation is a rotation about Z and uses only the `z` and `w`
components:

```text
angle a (radians)  ->  { w: cos(a/2), x: 0, y: 0, z: sin(a/2) }
```

The `quat()` factory builds a quaternion. Its argument order is **`w` first**: `quat(w = 1, x = 0, y = 0, z = 0)`.

```typescript
import { quat } from 'esengine';

const angle = Math.PI / 4;                                   // 45° counter-clockwise
const rot = quat(Math.cos(angle / 2), 0, 0, Math.sin(angle / 2));
```

| Helper | Signature | Description |
|---|---|---|
| `quaternionToAngle2D` | `(rz, rw) => number` | Z angle in radians from a quaternion's `z` / `w` (`2 * atan2(z, w)`). From `esengine`. |
| `normalizeAngle` | `(a) => number` | Wraps an angle to `(-π, π]`, for shortest-turn deltas. From `esengine/ai`. |

Turrets tracking the cursor:

```typescript
import { defineSystem, defineTag, Query, Mut, Res, Transform, CameraView, quat, quaternionToAngle2D } from 'esengine';
import { normalizeAngle } from 'esengine/ai';

const Turret = defineTag('Turret');

const aim = defineSystem([Query(Mut(Transform)).with(Turret), Res(CameraView)], (q, view) => {
  const target = view.getWorldMousePosition();
  if (!target) return;
  for (const [entity, t] of q) {
    const angle = Math.atan2(
      target.y - t.worldPosition.y,
      target.x - t.worldPosition.x,
    );
    t.rotation = quat(Math.cos(angle / 2), 0, 0, Math.sin(angle / 2));

    // Gradual turning: read the current facing and step toward the target.
    const facing = quaternionToAngle2D(t.rotation.z, t.rotation.w);
    const delta = normalizeAngle(angle - facing); // shortest signed turn
  }
});
```

`TweenTarget.RotationZ` animates the Z angle **in radians** and rebuilds the quaternion each step; the Sequencer keys
`rotation.angle` in the same way ([Tweens](/docs/animation/tweens/)). Direction vectors without a rotation are
produced by `v2.fromAngle(angle, len)` and `v2.rotate(v, angle)` ([Math Helpers](/docs/scripting/math/)).

## Parenting and hierarchy

Entities form a tree through the `Parent` and `Children` components. The hierarchy is edited through the world API:

```typescript
import { defineSystem, addStartupSystem, GetWorld, Transform } from 'esengine';

const build = defineSystem([GetWorld()], (world) => {
  const ship = world.spawn('Ship');
  world.insert(ship, Transform, { position: { x: 400, y: 300, z: 0 } });

  const turret = world.spawn('Turret');
  world.insert(turret, Transform, { position: { x: 0, y: 24, z: 0 } }); // 24 px above the ship
  world.setParent(turret, ship);
});
addStartupSystem(build);
```

| Method | Behaviour |
|---|---|
| `world.setParent(child, parent)` | Attaches or re-attaches `child` under `parent`, updating both the child's `Parent` and the parent's `Children`. The child is appended after its new siblings. Parenting an entity to itself or to one of its descendants is rejected without changes. |
| `world.removeParent(entity)` | Detaches the entity, which becomes a root. Its own children stay attached to it. |
| `world.despawn(entity)` | Despawns the **whole subtree**, children first. |

Inserting or setting `Parent` or `Children` directly is routed through the same operation, so both sides of the link
stay consistent; `world.setParent` is the explicit form.

`Parent` holds `{ entity }` (the parent) and `Children` holds `{ entities }` (an `Entity[]`). They are queried like any
component:

```typescript
import { defineSystem, Query, Parent, Children, Transform } from 'esengine';

const followers = defineSystem([Query(Transform, Parent)], (q) => {
  for (const [entity, t, parent] of q) { /* parent.entity */ }
});
```

### World-transform composition

Each frame the transform system walks the tree depth-first from the roots. For each entity it builds the local matrix
as **translate × rotate × scale** (TRS) and multiplies it by the parent's world matrix:

```text
world = parentWorld × T(position) × R(rotation) × S(scale)
```

A child's `position` is therefore measured in the parent's rotated and scaled frame: a child at local `{x: 24, y: 0}`
under a parent rotated 90° lies 24 px *above* the parent in world space. The decomposed result is written to
`worldPosition`, `worldRotation` and `worldScale`.

### Hierarchy behaviour

- **Reparenting keeps local values.** `setParent` does not adjust the local fields to preserve the world pose; a child
  at local `{0, 0}` moves to its new parent's position. To keep the entity in place, convert its world position into
  the new parent's frame before reparenting.
- **`Children` order is meaningful.** UI layout and UI draw order follow it, and hierarchy-order layers
  (`Renderer.setTreeSortLayers`) stack by it. Detaching a child keeps the remaining siblings in order; re-attaching
  appends it last. Sibling order is set in the World Outliner. For ordinary 2D draw order use `position.z` or sorting
  layers.

## Scale

`scale` is per axis. `{2, 2, 1}` doubles an entity uniformly, `{2, 1, 1}` stretches it horizontally, and negative
values mirror it: `{-1, 1, 1}` flips horizontally. For sprites, `Sprite.flipX` flips without changing the transform.

Scale composes down the hierarchy through `worldScale`. A child under a `{2, 2, 1}` parent renders at twice its own
scale, and its local `position` is scaled by the parent as well: local `{x: 10, y: 0}` lands 20 px away in world
space.

<Aside type="caution">
  Non-uniform scale on a parent combined with rotation on a child produces skew: the composed matrix is no longer a
  pure rotation, and physics colliders (unscaled shapes in metres) no longer match the rendered result. Use uniform
  scale (equal x and y) on parents. A camera is zoomed with `Camera.orthoSize`, not by scaling its Transform.
</Aside>
