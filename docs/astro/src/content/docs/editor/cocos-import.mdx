The editor can bring a **Cocos Creator 3.x** project across: its scenes, prefabs, scripts and
assets become an Estella project that you keep editing here. The Cocos folder is only ever read.

## Open a Cocos project

Choose a Cocos Creator folder in **Open Project**. The editor recognises it by the Creator
version in its `package.json` and offers to convert it into a new project beside it, named
`<name>-estella`, and then opens that. Opening the same Cocos folder again opens the converted
project instead of converting twice.

The conversion shows its progress: the stage it is in and how far through it is, in a bar over the
window. It runs off the editor's main thread, so the window does not freeze.

- **Images, fonts and spine files are linked, not copied.** They are hard-linked into the converted
  project (copied only across drives), so a multi-gigabyte art folder is neither duplicated nor
  stored twice. The project reads those files and never writes into them.
- **The project starts as the game does.** It opens at the Cocos launch scene with the Cocos
  design size, and scripts that only define globals (the game configuration) run before the ones
  scenes name. Editor built-in assets that a scene names by uuid, such as the default progress bar
  images, are read from your Creator install.
- **Components that did not come across are listed.** After the first conversion, a message lists
  the components that have no counterpart, most used first. Their data is kept on the entity, but
  nothing runs for them.
- **The Cocos project's own effects are converted** into Estella shaders and materials, so a sprite,
  mesh or particle that used one keeps its look.

## What the conversion keeps

**Screen fit.** The Cocos design fit (fit width, fit height) becomes the project camera's scale
mode (fixed width, fixed height), so a UI laid out in design units comes out the same size on every
screen. See [Screen & Design Resolution](/docs/core-concepts/screen/).

**Layers.** A node's Cocos layer becomes the layer of its sprites, texts, shapes, spine, particles and
meshes (the layer's bit index), which is what a camera's culling mask selects among. A UI camera
that draws only one layer therefore draws what it did in Cocos.

**UI.** Converted UI behaves as it does in Cocos:

- The UI layer is painted in hierarchy order, so a popup covers the text of the view under it
  (see [hierarchy-order layers](/docs/graphics/sprites/#hierarchy-order-layers)).
- `Widget` becomes the engine's [`RectAnchors`](/docs/ui/overview/#rectanchors--world-content-that-follows-its-parent)
  on a [`ContentRect`](/docs/ui/overview/#contentrect--a-rectangle-for-world-content), so the scene is
  laid out in the editor where it will run. A root pinned to the screen is stored where the engine
  places it in the design box. The Cocos `Layout` runs between the engine's two anchor passes.
- A Label with no overflow rule does not wrap and is laid out from its anchor.
- An `EditBox` becomes the engine's text field with its two labels folded in.
- An inactive node becomes the `Disabled` tag, and its subtree goes with it.
- Bitmap font pages keep their full size.

**Scripts.** Each script's component classes are declared to the editor, so they reach the
Inspector. Scripts are bundled with Cocos's tolerated gaps (missing `cc` names, a reassigned
`const`, package files outside `exports`, imports used only in preview). Two scripts that write the
same `@ccclass` name are told apart: the second gets its own component name (`Name_2`, in path
order), the converter writes which script that was beside the entry, and the bundler writes the new
name into that script's decorator. The script bundle is rebuilt on Play only when a file it read
changed.

## Re-import without losing your edits

Run **Re-import Cocos Project** in a project converted from Cocos Creator. Scenes and prefabs that
changed on the Cocos side are brought across and new ones are added. A document you edited here is
left as it is and counted in the result, for example *3 new, 2 updated, 5 kept because you edited
them*. The one exception is `Cocos.Widget` components on an edited document, which are turned into
`RectAnchors` (same fields), so a project converted by an older importer keeps its alignment.

A converted project records the importer's revision. When the editor opens a project written by an
older importer, it is converted again.

Running the command in a project that did not come from Cocos tells you so and changes nothing.

## The `cc` compatibility layer

Cocos scripts keep working because the project's scripts are built with `cc` resolved to the
engine's Cocos layer (`esengine/cocos`). A `Node` there is an entity and a `Component` subclass is an
Estella component. Parts of Cocos with no counterpart are not simulated: a part of the `cc` module the
layer does not provide is a stand-in that survives being read, called and constructed, and says
once that it is missing, rather than `undefined`. Each script of a converted project loads on its
own, so one whose module throws does not stop the others from registering.

What is covered:

| Area | Provided |
|---|---|
| Scenes and `director` | `director.loadScene` runs a project scene through the engine's scene manager (a persistent root is `SceneOwner.persistent`). A scene's components start in one phase before the frame's updates. `director` has a scheduler and fires its frame events, and is a class scripts can patch. A node's scripts load and enable as it joins an active parent or is switched on, and a node made between frames joins the running world. |
| Nodes and components | `setSiblingIndex` reorders through the engine's entity order. `getComponent` finds a component by a base class it derives from, or by its `cc.` name. `Component.EventHandler`, `Node.getParent` and `Camera.screenPointToRay` exist. The design resolution is known to scripts before they run. |
| Loading assets | `resources.load` gives images, sprite frames and audio by path, and finds an image's `spriteFrame` and `texture` by the end of the path. A directory load leaves out what the layer cannot load instead of failing. `loadAny` takes a uuid. A loaded asset is named for its file and counts its holders. `assetManager` has a downloader, a factory and `AssetManager.Cache`. |
| Meshes and materials | `MeshRenderer` is a view on the engine's mesh renderer: `getSharedMaterial`, `getMaterialInstance` (the per-renderer instance, made once), `material`, `setMaterial`. `Material.setProperty` / `getProperty` write through to the engine material (colours 0..255 become 0..1); `mainColor`, `albedo`, `baseColor` and `color` write the renderer's tint. `ModelRenderer`, `UIMeshRenderer` and `cc.geometry` (`AABB`, `Ray`, `Plane` and the box, ray and plane tests) exist. |
| Utilities | `js` (class names and lookup, `isChildClassOf`, `mixin`, `addon`, property definers), `ccenum`, `NodePool` (the handler component is told `unuse` and `reuse`), `cc.profiler` (`showStats`, `hideStats`). |
| UI components | Widget, Layout, Button, Toggle (a toggle belongs to the container its parent holds; assigning `isChecked` switches the others of its group off), ProgressBar, ScrollView, Label, Sprite, EditBox and the rest of the layer. Sprites, labels and graphics accept the rebuild requests scripts send. |

<Aside type="note">
  Where two pressable things overlap at the same depth and layer, a press goes to the one drawn
  later by its place in the hierarchy, so a node taken from a pool and added under a panel does not
  take presses meant for what covers it.
</Aside>
