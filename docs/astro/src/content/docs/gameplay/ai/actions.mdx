An **action** does something (chase, attack, play a sound); a **condition** answers a yes/no question (is the player
visible?). Each is registered under a name once, and state machines, behavior trees, script graphs and event bindings
resolve those names against the same process-wide registry.

```typescript
import { registerAction, registerCondition } from 'esengine';
import { Status, Perception, setNavDestination } from 'esengine/ai';

registerCondition('seesPlayer', (ctx) =>
  ctx.has(Perception) && ctx.get(Perception).visible);

registerAction('chase', (ctx) => {
  const per = ctx.get(Perception);
  setNavDestination(ctx.world, ctx.entity, { x: per.targetX, y: per.targetY });
});
```

| Function | Description |
|---|---|
| `registerAction(name, fn \| spec)` | Registers an action, as a function or as a spec object. |
| `registerCondition(name, fn)` | Registers a condition function. |
| `registerValue(name, spec)` | Registers a pure value that only answers a question, for script graphs to read through its declared outputs. |
| `aiRegistry` | The registry instance; `aiRegistry.registerCondition(name, spec)` also accepts a spec object. |

<Aside type="tip">
  Actions and conditions are registered at module load (top level, or in a `Schedule.Startup` system) so they exist
  before any agent ticks. The registry is shared across `App` instances.
</Aside>

## `AiContext`

Every action and condition receives an `AiContext` for the agent it runs on. It offers the same entity, world and command
access as a [`defineBehavior`](/docs/scripting/overview/) update, plus the agent's blackboard.

| Member | Type | Description |
|---|---|---|
| `ctx.entity` | `Entity` | The agent the action or condition runs for. |
| `ctx.dt` | `number` | Frame delta in seconds. |
| `ctx.world` | `World` | World access for reading other entities. |
| `ctx.commands` | `Commands` | Deferred spawn/despawn, safe during a tick. |
| `ctx.input` | `InputState` | Runtime input, the same state a `defineBehavior` reads. Empty (nothing pressed) when the host has no devices. |
| `ctx.blackboard` | `Blackboard` | The agent's data store ([The Blackboard](/docs/gameplay/ai/blackboard/)). |
| `ctx.get(Comp)` | `ComponentData` | Reads a component on this entity. |
| `ctx.set(Comp, data)` | `void` | Writes a component on this entity. |
| `ctx.has(Comp)` | `boolean` | Whether this entity has `Comp`. |

## Signatures and specs

An action is called as `(ctx, blackboard, arg?, params?, out?)` and a condition as `(ctx, blackboard)`.

`registerAction` also accepts a spec object:

| Spec field | Description |
|---|---|
| `run` | The action function. |
| `params` | Declared parameters (`name`, `type`: `'string'`, `'number'`, `'bool'` or `'enum'`, …). The editor renders them as typed controls instead of one text box, and the action receives the values by name as its fourth argument. |
| `outputs` | Declared outputs, written into the `out` record. |
| `pure` | `true` when running it changes nothing. A pure name may be evaluated on demand and in any order, so a script graph can pull its value along data wires. |
| `touches` | The components it reads and writes ([below](#declaring-what-a-leaf-touches)); may be a function of the action's input. |
| `separator` | Separator joining the parameter values in the argument string (default `:`). The last parameter absorbs any remaining separators. |

An action can carry an optional **string argument**, set next to the action name in the FSM state inspector or on a BT
action node. Built-in actions use it for data such as the clip `spriteAnim.play` switches to; registered actions receive
it as their third parameter: `(ctx, blackboard, arg) => …`.

## Declaring what a leaf touches

The system that ticks state machines reaches whatever its leaves reach, which is known only once the graphs are loaded.
Declaring it on the registration lets the scheduler distinguish that system from one that may touch anything:

```typescript
import { registerAction, aiRegistry } from 'esengine';
import { Perception } from 'esengine/ai';

registerAction('chase', {
  run: (ctx) => { /* ... */ },
  touches: { reads: ['Perception'], writes: ['NavAgent'] },
});

aiRegistry.registerCondition('seesPlayer', {
  check: (ctx) => ctx.has(Perception) && ctx.get(Perception).visible,
  touches: { reads: ['Perception'] },
});
```

The declaration is optional. A single undeclared leaf makes the whole system's access unknown to the scheduler. See
[What a system touches](/docs/core-concepts/systems/#declared-access).

## Return values

A condition returns a `boolean`. An action may return a `Status` or nothing:

```typescript
export enum Status { Success = 'success', Failure = 'failure', Running = 'running' }
```

- In a **behavior tree**, a leaf returns `Status` to run across frames (`Running`), succeed or fail. Returning nothing
  counts as `Success`.
- In a **state machine**, the return value is ignored; FSM actions are one-shot side effects.

An action that returns `Status` therefore serves as both a BT leaf and an FSM hook.

## Built-in names

The engine pre-registers the following names. They appear in the editor palettes beside the game's own names and operate
on components of the agent entity.

| Name | Kind | Effect |
|---|---|---|
| `timeline.play` | action | Raises the agent's [`TimelinePlayer`](/docs/animation/timeline/playback/#timelineplayer-component) play flag. A finished clip replays from the start. |
| `timeline.pause` | action | Lowers the play flag (resume with `timeline.play`). |
| `timeline.finished` | condition | True once the clip has completed (a `once` clip that ran to its end) and is not playing. |
| `spriteAnim.play` | action | Plays the agent's sprite flipbook; the argument switches to that clip. |
| `spriteAnim.restart` | action | Rewinds the flipbook to frame 0 and plays (the argument switches clip). |
| `spriteAnim.stop` | action | Pauses the flipbook. |
| `spriteAnim.finished` | condition | True once a one-shot sprite clip has finished. |
| `audio.play` | action | Raises the agent's `AudioSource` play flag; the argument switches to that clip. No effect if the same clip is already sounding. |
| `audio.stop` | action | Lowers the `AudioSource` play flag. |
| `audio.finished` | condition | True once a non-looping clip has ended and is no longer playing. |
| `soundEvent.trigger` / `soundEvent.stop` | action | Starts / stops the agent's `SoundEventSource`. |
| `property.set` | action | Writes a component field on the agent (or on another entity through the optional `entity` parameter) by `Component.field` path and a value, e.g. `UIVisual.color.a`. In argument form, `path=value`; the value is parsed as JSON when possible (`3`, `true`, `{"r":1}`) and otherwise kept as a string. |

A registration under the same name as a built-in replaces it. Game names avoid the built-in prefixes (`timeline.`,
`spriteAnim.`, `audio.`, …) to keep the namespaces apart.

In the FSM and behavior-tree editors, the action and condition fields suggest every registered name, grouped by
namespace, with a short description for built-ins. Free text remains valid for names the game registers at run time.

### Example: a cutscene state

`timeline.play` and `timeline.finished` form a cutscene state with no game code: entering the state starts the clip, and
its completion drives the transition out.

```typescript
import { registerFsm } from 'esengine/ai';

registerFsm('intro', {
  initial: 'Cutscene',
  states: [
    {
      name: 'Cutscene',
      onEnter: 'timeline.play',
      transitions: [{ to: 'Gameplay', condition: 'timeline.finished' }],
    },
    { name: 'Gameplay' },
  ],
});
```

The agent entity carries the `TimelinePlayer` (clip, speed, wrap mode); the state machine only switches its flags. The
[`cutscene` example](https://github.com/esengine/estella/tree/master/examples/cutscene) uses this pattern: an intro
timeline plays on scene start, gameplay starts when it completes, and R replays it, with no registered actions.
