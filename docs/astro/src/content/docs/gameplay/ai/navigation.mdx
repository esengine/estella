Navigation moves an agent to a world point along a route that goes round whatever
is in the way. The route is planned over the **`Nav`** resource's active *surface*,
and there are two of them:

- **`NavGrid`** — a rectangular mask of walkable and blocked cells. What a tilemap
  already is, and the one you can flip a cell of while the game runs.
- **`NavMesh`** — convex polygons **baked** out of a scene's own collision geometry.
  It follows sloped and stacked ground, which no single grid can.

Everything above them — the agent, the overlay, `nav.findWorldPath` — asks the same
questions of either, so nothing in a game has to know which one it was handed.

### Building a grid

```typescript
import { defineSystem, Res } from 'esengine';
import { Nav, NavGrid } from 'esengine/ai';

export const setupNav = defineSystem([Res(Nav)], (nav) => {
  nav.setSurface(new NavGrid({
    width: 60,          // columns
    height: 44,         // rows
    cellSize: 20,       // world pixels per cell
    origin: { x: -600, y: -440 },  // world position of cell (0,0)'s center
  }));
}, { name: 'SetupNav' });
```

| `NavGrid` option | Type | Description |
|---|---|---|
| `width` | number | Cell columns. |
| `height` | number | Cell rows. |
| `cellSize` | number | World pixels per cell (square). |
| `origin` | `{ x, y, z? }` | World position of cell `(0,0)`'s center. Its `z` is the depth every waypoint comes back at. Defaults to `(0,0,0)`. |
| `walkable` | `ArrayLike<number>` | Optional row-major `width*height` mask, `1` = walkable, `0` = blocked. Omitted → all walkable. Copied in, not retained. |

To derive a grid from a painted tilemap instead of hand-authoring the mask, use
`navGridFromTilemapLayer` (which cells a layer's solid tiles block) or
`navGridFromTiles`. `grid.setWalkable(x, y, false)` closes a cell at any time — a
door shuts, a tower goes up — and the next plan routes around it. A
[destructible tilemap](/docs/world/tilemaps/#destructible-tilemaps) keeps a grid in step with what is dug and built by itself.

A route over a grid is **string-pulled** before it is handed back: A\* answers in
steps of one cell, and only the cells where the route actually has to turn survive.
A shortcut is taken only along a line the search itself could have walked — every
cell it touches fits the body, and a diagonal needs both of its shared orthogonals
— so a smoothed route is exactly as legal as the staircase it replaced, and the
same shape of route a mesh gives.

### Replacing a surface after asynchronous work

`nav.beginSurfaceUpdate()` returns a versioned `NavSurfaceUpdate`. Build a
replacement separately, then call `update.commit(surface)`. Only the latest
pending request can commit; a superseded, cancelled or completed handle returns
`false`. `nav.setSurface(...)` and assigning `nav.surface` also cancel a pending
request. `update.cancel()` keeps the previous surface and resumes its routes.

While `nav.surfaceUpdatePending` is true, the navigation driver retains agent
destinations and stops its steering. Character gravity remains active. Resource
queries return no route, and `queryWorldPath` reports `unavailable / building`;
the editor's route inspector displays the pending update. Planning counters
include agents waiting for this replacement.

```typescript
import { Navigation, NavGrid, type NavGridOptions } from 'esengine/ai';

async function replaceTerrain(nav: Navigation, load: () => Promise<NavGridOptions>) {
  const update = nav.beginSurfaceUpdate();
  try {
    const data = await load();
    if (update.pending) update.commit(new NavGrid(data));
  } finally {
    update.cancel(); // Also releases a failed request; harmless after commit.
  }
}
```

Cancel on owner teardown as well. Cancellation revokes the right to commit; the
producer owns aborting its I/O or worker. This protocol schedules no background
worker and does not make synchronous mesh baking asynchronous. Do not mutate the
live surface while staging a replacement: cancellation cannot roll back those
mutations. The courtyard workshop provides terrain reload/cancel controls using
an actual JSON asset and releases its asset lease on every outcome.

### A mesh for a 3D scene

A 3D scene has geometry rather than a tile mask, so its surface is **baked** from
the bodies it already collides against. Put a **`NavVolume`** on an entity and the
nav plugin fills the box it describes:

| `NavVolume` field | Default | Description |
|---|---|---|
| `halfExtents` | `1000, 500, 1000` | Half the box to bake, in world pixels; the entity's Transform is its centre. |
| `cellSize` | `50` | Voxel size in the ground plane. Smaller hugs the geometry more closely and bakes more slowly. |
| `cellHeight` | `10` | Voxel size vertically — what decides whether a balcony and the floor under it are two levels or one. |
| `maxSlopeDegrees` | `45` | Steepest ground an agent can stand on. Anything steeper is a wall. |
| `agentHeight` | `180` | Headroom an agent needs. Ground with less is a crawlspace, not a corridor. |
| `agentRadius` | `30` | How wide the agent is. The mesh is pulled back from every wall by this. |
| `stepHeight` | `40` | How high a step the agent can climb rather than walk round. |
| `layers` | `0` | Physics layers the ground is taken from; `0` = every layer. |

The bake voxelises the collision triangles in the box, keeps the surfaces an agent
of that size could stand on, and turns what is left into convex polygons. Every
column of the world keeps **all** of its floors, so a bridge and the road under it
are two places and a route can use either.

<Aside type="note">
  **One volume per scene.** A scene has one navigable world, so the first volume is
  the one that is baked and any others are named in the log. What a box decides is
  where to *look*; walkability comes from the geometry inside it, so one box big
  enough to hold the level costs voxels and never costs correctness.
</Aside>

<Aside type="note">
  **Static bodies only.** A crate that is about to be pushed is not floor, and a
  mesh baked over one would describe the world for exactly as long as nobody
  touched it. Give anything that should be walked on (or walked round) a
  `RigidBody3D` with its body type set to **Static**.
</Aside>

Each volume is baked once, on the first frame its geometry is available — a mesh
collider contributes nothing until its asset has loaded, so the bake waits for it.
`buildNavMesh(verts, indices, options)` is callable directly if a game wants to bake
on its own terms, and `collectNavGeometry(world, { min, max, layers? })` is what gathers the triangles.

<Aside type="caution">
  **One agent size per mesh.** `agentRadius` is baked in, not applied per query: the
  mesh *is* the set of places a body that wide may stand. A `NavAgent` wider than
  the volume it walks on is routed as if it were the narrower one, and says so once
  in the log.
</Aside>

### Ways the ground does not provide

A mesh is baked from what an agent can WALK, so two floors with a gap between them
are two places — which is the honest answer and not the whole one. A scene knows
things the floor does not: that this ledge can be dropped off, that this ladder is
climbable, that this plank reaches the roof. **`NavLink`** is where it says them.

| `NavLink` field | Default | Description |
|---|---|---|
| `start` | `0, 0, 0` | Where the way starts, as an offset in the entity's own frame. |
| `end` | `0, 0, 150` | Where it comes out. |
| `bidirectional` | `true` | Whether it can be taken both ways. A drop off a ledge cannot. |
| `radius` | `50` | How far from each end ground may be and still be joined. |
| `enabled` | `true` | Whether the way exists right now. |

Both ends are offsets in the entity's frame, so a link travels and turns with
whatever carries it — a ladder inside a prefab is a ladder wherever the prefab is
put down. A link whose end reaches no ground joins nothing at all: a route that
ended in the air would be worse than no route.

Moving or switching a link costs a **lookup**, not a bake — it joins polygons that
already exist. That is the difference between it and an obstacle, and the reason
one is cheap to animate and the other is not.

<Aside type="note">
  **The route breaks at both ends of a link.** A funnel pulled taut over a ladder
  would plan a walk through the air beside it, so the waypoints always include the
  two points the link joins, and a following agent goes through them. While it is
  crossing, it is not standing on the navigable world at all — a replan asked there
  has no answer, so the agent keeps the route it already had rather than stranding
  itself halfway.
</Aside>

### Ground that costs something

The mesh answers where an agent CAN walk. **`NavArea`** is where a scene says what
it would rather walk on:

| `NavArea` field | Default | Description |
|---|---|---|
| `halfExtents` | `200, 100, 200` | Half the box, in world pixels; the Transform is its centre. It turns with the entity. |
| `cost` | `3` | What a unit of distance inside it costs, against `1` for open ground. |
| `enabled` | `true` | Whether the price applies right now. |

Under 1 is preferred and over 1 is avoided — a road at half price is worth going
out of the way for, a swamp at four times is walked round if there is any way
round. It never **blocks**: an agent with nowhere else to go wades through, which
is the difference between a swamp and a fence.

Moving or resizing a patch rebuilds the navigable world, the way an obstacle does.
Changing its `cost` does not: the mesh carries which patch a polygon belongs to,
and what that patch costs is read fresh on every search.

<Aside type="note">
  **The string-pull respects it.** A route over a grid is pulled taut afterwards,
  and straightening one back through the mud it had just gone round would undo the
  only reason it went round — so a shortcut may not cross ground priced
  differently from the ground it starts on.
</Aside>

### Doors, gates and things placed in the way

Anything with a collider already blocks, because the mesh is baked from the
scene's collision geometry. **`NavObstacle`** is for what blocks *without* being
geometry, or what stops blocking without moving:

| `NavObstacle` field | Default | Description |
|---|---|---|
| `halfExtents` | `50, 100, 50` | Half the blocking box, in world pixels; the Transform is its centre. Unlike the volume, it turns with the entity. |
| `enabled` | `true` | Whether it blocks right now. A door that opens is this field. |

Blocking is a **bake input**, not a filter over the answer: an obstacle takes its
ground away *before* the walkable area is eroded, so routes keep the agent's full
width clear of it rather than scraping along its face. Changing one — moving it,
resizing it, switching it on or off — rebuilds the mesh at most once per 200 ms.
The 2D grid marks obstacle changes on the next navigation tick without that bake
delay, so a newly closed passage is excluded before agents plan or move.

```typescript
// A door swinging open, from any system with world access:
const door = world.get(entity, NavObstacle);
door.enabled = false;
world.set(entity, NavObstacle, door);
```

Both surfaces answer to it: a mesh is baked again, a grid has the cells under the
box marked. The grid's own walkability is kept separate, so a door closing and
opening gives back exactly the ground that was there.

<Aside type="caution">
  **Not for something that travels.** An obstacle is for something that blocks and
  then stops — a door, a gate, a tower just built. One that moves continuously
  rebuilds the world several times a second and says so in the log; a moving body
  is a job for the character controller it collides with, not for the bake.
</Aside>

### Seeing what was baked

The volume's wireframe says where the bake looked. To see what it **found** while
you are still authoring, turn on **View → Show Navigation Mesh** (or the Navigation
button on the viewport toolbar): the editor bakes the scene's volume and draws the
walkable faces where they are, with the edges they stop at picked out. It rebakes
as the scene changes, so widening `agentRadius` pulls the mesh back from the walls
in front of you.

The same picture from inside a running game comes from the `NavDebugDraw` resource:

```typescript
import { NavDebugDraw } from 'esengine/ai';

app.getResource(NavDebugDraw).enabled = true;
```

Its `showFaces`, `showBorders` and `showLinks` (all `true`) switch the face outlines, the red
stop edges and the `NavLink` connections on and off individually.

Every walkable face is outlined where it actually is — at the height of the ground
for a mesh, in the scene's own plane for a grid — and every edge the walkable world
**stops** at is marked in red. Those edges are the only thing that explains a route
going the long way round. Off by default (a surface is thousands of loops a frame),
and it stops after 4096 faces: `cellSize` is the knob for seeing more of a
big world.

<Aside type="tip">
  The `Nav` resource also answers one-off queries directly:
  `nav.findWorldPath(from, to)` returns an array of world-space waypoints without
  needing a `NavAgent`.

  A goal it cannot reach — behind a shut door, on an island, off the mesh
  entirely — is answered with the route to the nearest place it CAN reach, because
  an agent sent somewhere it cannot get to should walk to the door rather than
  stand where it was told. Whether it got there is yours to see: you named the
  goal, and the last waypoint either is at it or is not. `null` means the agent
  itself is nowhere — there is no route from a point that is not on the navigable
  world at all.
</Aside>

### Explaining a route

Use `nav.queryWorldPath(from, to, { radius })` when a best-effort path must be
distinguished from reaching the destination. It returns `{ path, status, reason }`:

| Status / reason | Meaning |
|---|---|
| `complete` / `none` | Reaches the surface's resolved destination, including normal endpoint snapping. |
| `partial` / `disconnected` | Stops on the reachable side of a disconnected region or closed passage. |
| `partial` / `insufficient-clearance` | A point can get through the grid, but the requested body cannot. |
| `unavailable` / `no-surface` | No navigation surface is installed. |
| `unavailable` / `building` | A surface update is pending (`nav.surfaceUpdatePending`). |
| `unavailable` / `start-unavailable` | No usable starting point was found. |
| `unavailable` (grid) or `partial` (mesh) / `target-unavailable` | No usable destination was found; a mesh still returns a partial approach toward it. |
| `unavailable` / `radius-mismatch` | The requested body is wider than the mesh's baked radius. |
| `unknown` / `diagnostics-unavailable` | A custom surface implements only the legacy path API. |

```typescript
const result = nav.queryWorldPath(from, target, { radius: 20 });
if (result.status !== 'complete') console.info(result.reason);
// result.path can still describe a useful partial approach.
```

`findWorldPath` retains its existing best-effort behavior. The diagnostic query
describes the currently installed surface; it does not start a rebuild. Change
grid walkability through `setWalkable`, `setObstructed` and `clearObstructions` so
clearance and cached connectivity are invalidated together. Dynamic blockers
contribute to body clearance. Area prices remain live without rebuilding connectivity.

Repeated grid queries reuse working memory. Returned routes remain independent,
so callers may retain or edit them without changing a later search. Route costs,
endpoint snapping and best-effort partial paths retain their existing behavior.

In the editor, select a `NavAgent` during **Play** and expand its component in
Details. **Inspect current route** queries once from its current world position
to its stored target with the agent's radius. It shows the reason, sampled world
endpoints, waypoint count and query time. Results are snapshots; click again after
changing doors, obstacles or targets. No search runs during recurring inspector
refreshes. This requires a ready local Play session; connected device inspection
does not yet support this query. It describes the installed surface, not pending
rebuilds or the agent's cached movement route.

The reproducible CPU corpus runs in headless Chromium with door and building
changes on 32/64/128-cell maps and 64 simultaneous replans:

```sh
node tools/navigation-rebuild-benchmark.mjs output/navigation-current.json
node tools/navigation-rebuild-benchmark.mjs output/navigation-reference.json --search-reference=48631844c53113825a15493afeb8e6e2b972900c
```

The reference substitutes only the previous search; both sides use current
obstacle clearance. Reports record source and bundle identity, raw rebuild and
query times, and frame gaps. They measure navigation CPU work, excluding physics
geometry collection, avoidance, rendering and the rest of the game frame.

### Moving an agent

`NavAgentSystem` serves planning requests in FIFO order across frames. By default
it allows **16 plans** and a **2 ms soft planning budget** per tick. At least one
query can run; the time check happens between synchronous queries, so one query
can exceed the budget. This spreads bursts by adding route latency, rather than
making the same work free. Direct `findWorldPath` / `queryWorldPath` calls remain
synchronous and are outside this queue.

```typescript
const nav = app.getResource(Nav);
nav.planningBudgetMs = 2;
nav.maxPlansPerFrame = 16;
// Set either limit to 0 to disable that limit.
console.info(nav.planningStats); // completed, pending, elapsedMs from the last tick
```

Queued requests read the latest position, target and radius when served. Agents
without a valid route pause; periodic refreshes keep following valid cached routes.
When paused, character steering stops horizontally while gravity
remains active. Replacing the surface, editing built-in grid topology, or changing
an agent's radius retires stale routes, including agents whose periodic replanning
is disabled. After changing a custom surface or its costs/links in place, call
`nav.invalidatePaths()`. A transient failed query on an unchanged surface can keep
an existing route while an agent crosses a link; an invalidated route is discarded.

The editor's **Inspect current route** also samples the last planning tick's
completed/pending counts, time and configured limits. This is a queue snapshot,
not the time taken by the manual diagnostic query or by a navigation rebuild.

To compare unlimited planning with the defaults on identical building maps:

```sh
node tools/navigation-planning-benchmark.mjs output/navigation-planning.json
```

The headless report keeps all 64 route shapes, per-frame CPU and callback gaps,
batch completion latency and total CPU. It includes obstacle marking and the
agent step over an in-memory World with zero movement speed; it excludes actual
rendering, physics and the rest of an application frame. Lower peak CPU does not
prove a full game reaches 60 FPS.

Attach a `NavAgent`, then point it at a destination. The built-in nav plugin plans
the path and steps the agent along it each frame — you just set the goal.

```typescript
import { NavAgent, setNavDestination, stopNavAgent } from 'esengine/ai';

cmds.spawn()
  .insert(Transform, { position: { x: 0, y: 0, z: 0 } })
  .insert(NavAgent, { speed: 140, arriveRadius: 8 });

// From any system/action with world access — safe to call every frame:
setNavDestination(world, entity, { x: 320, y: -120 });
// …and to halt in place:
stopNavAgent(world, entity);
```

| `NavAgent` field | Default | Description |
|---|---|---|
| `speed` | `120` | Movement speed in world pixels per second. |
| `radius` | `0` | How wide the body is, in pixels. On a grid, planning routes it around anything it would not fit through; on a mesh this is the volume's `agentRadius` instead. |
| `arriveRadius` | `6` | Stop distance from the final goal. |
| `repathInterval` | `0.5` | Seconds between periodic replans; `0` disables periodic refresh. Target/topology changes and blocked-route recovery still replan. |
| `hasTarget` | `false` | Whether a destination is set. Set by `setNavDestination`; cleared on arrival and by `stopNavAgent`. |
| `targetX`, `targetY`, `targetZ` | `0` | Current destination in world pixels. |
| `arrived` | `false` | Set true when the agent reaches its goal; stays true until the next `setNavDestination`. |

`setNavDestination` is safe to call every frame to chase a moving target — the agent
replans for changed targets/topology, stalled-route recovery or an elapsed periodic timer. Read
`agent.arrived` (or `Perception`) to know when to switch behavior.

For built-in surfaces, reaching the end of a **partial** route keeps `hasTarget`
true and `arrived` false. The agent waits near the obstacle and can resume when
the surface changes, even with periodic replanning disabled. Call `stopNavAgent`
to cancel that intent. Custom surfaces without `queryWorldPath` retain their
legacy arrival behavior because completeness is unknown.

`surface.isNavigable(point, { radius })` checks whether a body can stand there:
grids check a disk against tile faces and world bounds; meshes refuse a radius
larger than the baked radius. Grid planning includes half a tile when converting
body radius to clearance cells, so a fractional radius cannot squeeze through a
door narrower than the body. Kinematic grid followers validate sampled movement
segments and replan from the current position after a blocked or stalled step.
This is navigation steering, not a substitute for a physics collision solver.

## Agents with a body

An agent whose entity also carries a **`CharacterController3D`** is **steered**
rather than moved: the plugin writes the controller's horizontal velocity toward
the next waypoint and lets the character's own solver do the walking, so the agent
collides with the world, steps up what it can and falls where it should. The
vertical axis is never written — that one belongs to the world, which is what makes
a route down a step a fall rather than a glide.

```typescript
cmds.spawn()
  .insert(Transform, { position: { x: 0, y: 200, z: 0 } })
  .insert(CharacterController3D, { radius: 30, halfHeight: 50 })
  .insert(NavAgent, { speed: 400, arriveRadius: 90 });
```

Distances are measured in the ground plane for such an agent, because a character
stands with its capsule's centre above the floor the route was planned on. Set the
volume's `agentRadius` to the controller's `radius` (and `agentHeight` to roughly
twice `halfHeight` plus the radius) so the mesh is the set of places that body fits.

Without a controller the agent's Transform is moved along the path directly, which
is what every flat game wants and what a 3D one gets before it has a body.

## Agents give way to each other

A route is planned against a world that does not move. Agents do, and a dozen of
them sent to one place all plan the same route and walk it as one body. An agent
whose `radius` is greater than zero declares that it IS a body, and from then on
it steers round the other bodies walking the same ground:

```typescript
cmds.spawn()
  .insert(Transform, { position: { x: 0, y: 0, z: 0 } })
  .insert(NavAgent, { speed: 300, radius: 40, arriveRadius: 60 });
```

Everyone assumes everyone else is doing the same, so each takes half the
avoidance and two meeting head-on part rather than both dodging the same way and
meeting again. Where that is not enough to break the tie — a perfect mirror —
the convention is keep right.

A step aside is checked against the navigable world before it is taken, so
steering never walks an agent into a wall. Two bodies too wide to pass in one
corridor therefore do not pass: waiting is the honest answer, and going through
the wall is not.

An agent with `radius` left at `0` is routed as a point, gives way to nobody and
is given way to by nobody — which is what every flat game had before this, and
what a scripted mover still wants.

## Agents have width

On a **grid**, set `radius` to the body's actual half-width and planning keeps it
out of gaps it cannot fit through. Left at `0` an agent is routed as a point, which
is what you want for something that has no collider — and what produces the classic
sight of an enemy walking confidently into a doorway and stopping there, because
the cell it was routed to is walkable and the half of it hanging over the next one
is not.

On a **mesh** the same thing is settled at bake time by `agentRadius`, which is why
a route over one is already clear of the walls with nothing asked of the planner.

A goal the body cannot stand on (a pickup in a corner) is still reached either way:
the plan ends as close as the body fits, and `arriveRadius` covers the rest.
