The gameplay AI layer makes an entity sense, decide and move. It consists of four parts that share one registry of named
actions and conditions:

| Part | Components | Description |
|---|---|---|
| [Perception](/docs/gameplay/ai/perception/) | `Perceiver`, `PerceptionTarget`, `Perception` | Senses the nearest visible target within a sight cone, and noises within hearing range, and writes the result to a component. |
| [Navigation](/docs/gameplay/ai/navigation/overview/) | `NavAgent`, `NavVolume`, `NavLink`, `NavArea`, `NavObstacle` | Moves an agent to a world point over a cell grid or a navigation mesh baked from geometry, replanning as the target moves. |
| [State machines](/docs/gameplay/ai/state-machines/) | `StateMachineAgent` | Runs an `.esfsm` graph: states with enter/update/exit hooks and guarded transitions. |
| [Behavior trees](/docs/gameplay/ai/behavior-trees/) | `BehaviorTreeAgent` | Runs an `.esbt` graph: selectors, sequences, decorators and leaves. |

State machines and behavior trees are two authoring forms over the same building blocks. Actions and conditions are
registered by name once, in code ([Actions & Conditions](/docs/gameplay/ai/actions/)); the graphs that use them are
assets authored in the editor ([Authoring in the Editor](/docs/gameplay/ai/authoring/)). Perception provides the input to
decisions, and decisions set navigation targets.

## Setup

The AI layer is TypeScript in the `esengine/ai` subpath, with no WebAssembly side module. Importing `esengine/ai`
registers the perception, state machine, behavior tree and navigation plugins; the editor and the web runtime add them to
the app. A bare `new App()` adds them explicitly ([Custom app setup](/docs/gameplay/ai/advanced/#custom-app-setup)).

The registry functions (`registerAction`, `registerCondition`, `registerValue`, `aiRegistry`) are also exported from the
main `esengine` barrel.

## Example

The [`enemy-ai` example](https://github.com/esengine/estella/tree/master/examples/enemy-ai) has two enemies that share
the same senses and leaves; one is driven by a state machine, the other by a behavior tree:

```typescript
import { defineSystem, Res, registerAction, registerCondition } from 'esengine';
import { Nav, NavGrid, setNavDestination, Perception } from 'esengine/ai';

// Shared leaves — the same names serve BOTH the .esfsm and the .esbt.
registerCondition('seesPlayer', (ctx) => ctx.has(Perception) && ctx.get(Perception).visible);
registerCondition('lostPlayer', (ctx) => !ctx.has(Perception) || !ctx.get(Perception).visible);

registerAction('chase', (ctx) => {
  if (!ctx.has(Perception)) return;
  const per = ctx.get(Perception);
  if (per.visible) setNavDestination(ctx.world, ctx.entity, { x: per.targetX, y: per.targetY });
});
registerAction('patrol', () => { /* hold position until the player is seen */ });

// One open nav grid over the arena.
export const setupNavGrid = defineSystem([Res(Nav)], (nav) => {
  nav.setSurface(new NavGrid({ width: 60, height: 44, cellSize: 20, origin: { x: -600, y: -440 } }));
}, { name: 'SetupNavGrid' });
```

The enemies' `StateMachineAgent.fsm` and `BehaviorTreeAgent.bt` point at `enemy.esfsm` and `enemy.esbt`, authored in the
editor and loaded with the scene. Perception, the FSM and BT ticks and path following are built in; the game code
consists of the shared leaves and the grid setup.

<Aside type="note">
  [`Hunter`](/docs/gameplay/ai/hunter/) is a ready-made 3D melee enemy that combines perception, navigation and
  `MeleeAttack` without a state machine or behavior tree.
</Aside>
