A **Marker** is a named point of gameplay interest (a spawn point, a waypoint, a door, a pickup location) placed in the
editor as an ordinary entity. A **Trigger Area** is a Marker with a sensor collider: a region that reports when a body
enters or leaves it. Both serialize with the scene, are edited in the Inspector, and are read with `Query(Marker)`.

## The `Marker` component

A Marker is the `Marker` component on an entity that also has a `Transform`. `Marker` is exported from the main
`esengine` barrel and needs no plugin.

| Property | Type | Default | Description |
|---|---|---|---|
| `type` | string | `''` | The kind of marker (`spawn`, `waypoint`, `door`, …). Free-form; the game defines the vocabulary. |
| `properties` | `Record<string, string>` | `{}` | Per-marker data (`team`, `targetScene`, `event`, …), edited as a key→value map in the Inspector. Properties of imported Tiled objects are stored here too. |

<Aside type="note">
  `properties` values are strings. Parse them where they are read (`Number(marker.properties.hp)`,
  `marker.properties.locked === 'true'`).
</Aside>

## Placing markers in the editor

- **+ Add → Create entity… → Common → Marker** creates a named point at the scene origin. A Marker shows a pin gizmo in
  the viewport.
- **+ Add → Create entity… → Physics → Trigger Area** creates a sensor region: `Transform`, a static `RigidBody2D`, a
  `BoxCollider2D` with `isSensor: true`, and a `Marker`. It also draws its collider outline, edited with the
  [collider gizmo](/docs/gameplay/physics-2d/bodies/).

In the Inspector, **Type** sets the marker's type and **Properties** holds any number of key→value rows. Both are saved
with the scene and included in the build.

![The Marker component in the Inspector — a Type field and a key→value Properties map with an Add-property button](@/assets/guides/en/marker-inspector.png)

*A `spawn` marker in the Inspector: **Type** is what `Query(Marker)` code filters on; each **Properties** row is one
entry of the string→string map.*

## Reading markers

```typescript
import { defineSystem, Commands, Query, Marker, Transform } from 'esengine';

// Find every spawn marker and place the player at the first one.
// Register it with app.addSystemToSchedule(Schedule.Startup, placePlayer) to run it once.
const placePlayer = defineSystem([Commands(), Query(Marker, Transform)], (cmds, markers) => {
  for (const [entity, marker, transform] of markers) {
    if (marker.type !== 'spawn') continue;
    cmds.spawn().insert(Transform, { position: { ...transform.position } });
    // …then chain .insert(Player, {…}), .insert(Sprite, {…}), and so on.
    break;
  }
});
```

`marker.properties` carries the per-marker data as strings (`marker.properties.targetScene`, `marker.properties.team`).

## Trigger Areas

A Trigger Area's collider is a sensor: it detects overlaps without a physical response. Entries and exits are read from
the `Physics2DEvents` resource. Each sensor event names the `sensorEntity` (the trigger) and the `visitorEntity` (the
body that crossed it); the trigger's `Marker` determines the response.

```typescript
import { defineSystem, Res, Query, Marker } from 'esengine';
import { Physics2DEvents } from 'esengine/physics';

const onTrigger = defineSystem([Res(Physics2DEvents), Query(Marker)], (events, markers) => {
  const markerOf = (e) => {
    for (const [entity, marker] of markers) if (entity === e) return marker;
    return null;
  };
  for (const s of events.sensorEnters) {
    const m = markerOf(s.sensorEntity);
    if (m?.type === 'door') loadScene(m.properties.targetScene);
    if (m?.type === 'hazard') damage(s.visitorEntity, Number(m.properties.dps));
  }
  for (const s of events.sensorExits) { /* left the zone — clear an effect, etc. */ }
});
```

Trigger Areas use the 2D physics module. The editor and the web runtime load it when a scene uses physics components; a
custom app adds the plugin ([2D Physics Basics](/docs/gameplay/physics-2d/overview/#setup)).

The same crossings are also sent to the entities as `trigger_enter` / `trigger_exit` events, to which an
[event binding](/docs/scripting/events/) on the area reacts without code. The complete event surface is described in
[Collision & sensor events](/docs/gameplay/physics-2d/queries/#collision--sensor-events). Placing triggers and the
bodies that should notice them on dedicated [collision layers](/docs/gameplay/physics-2d/bodies/#collision-filtering)
limits what each sensor considers.

Trigger Areas do not block movement. Blocking geometry uses a non-sensor collider or a tilemap
[collision layer](/docs/world/tilemaps/collision/#collision-layers).

## Imported from Tiled

When a [`Tilemap`](/docs/world/tilemaps/tiled/) loads a `.tmj` map, its object layers become the same entities:

| Tiled object | Becomes |
|---|---|
| **Point** | A `Marker`: `type` is the Tiled class; custom properties go to `Marker.properties`. |
| **Rectangle / ellipse / polygon / polyline** | A trigger region: a `Marker` (`type` = the Tiled class) plus a static body and a matching collider: a box, a circle, a polygon of up to 8 vertices (more falls back to its bounding box) or an open chain. It is a sensor, or solid geometry when the object group is named `collision`. |
| **Tile object** (has a gid) | A sprite child of the map. |

One `Query(Marker)` therefore reads markers placed in the editor and markers drawn in Tiled. Imported objects are
re-derived from the `.tmj` on each load and exist in play mode only; markers placed in the editor are serialized
entities. The raw object-group data is available through `tilemapSource(assets, ref)` from `esengine/tilemap`, for
example for a shape's exact vertices.

## Nearest markers

`nearestMarkers(world, from, options)` from `esengine/gameplay` returns the markers near a point, nearest first, for
example to decide what an interact button does:

```typescript
import { nearestMarkers, nearestEntities } from 'esengine/gameplay';

const near = nearestMarkers(world, { x: player.x, y: player.y }, { radius: 60, type: ['door', 'tree', 'bed'], limit: 1 });
if (near[0]) promptFor(world.get(near[0].entity, Marker).type);    // what the button says is the game's
```

| Option | Description |
|---|---|
| `type` | One type or an array of types. |
| `has` | Keeps only markers whose `properties` contain every given key and value. |
| `radius` | Maximum distance. |
| `limit` | Maximum number of results. |
| `plane` | `'xy'` (default) or `'xz'`, measuring on the ground plane; with `'xz'`, `from.y` is the ground z. |

Each result is `{ entity, distance, x, y }`. `nearestEntities(world, Component, from, options)` does the same over any
component, with a `filter` on its data. Entities switched off with `Disabled` are not returned. Each call is one pass
over the entities that carry the component.

## Guidelines

- Use a small, stable set of `type` values for roles and put variable data in `properties`.
- Read spawn points, waypoint graphs and patrol routes once at scene start and cache them.
- Use the same marker vocabulary in editor scenes and Tiled maps; the query code does not depend on the source.
