A 3D model can be imported, animated, skinned and lit. This is what makes it stand
somewhere: a rigid-body world powered by **Jolt Physics**, running in its own
WebAssembly module.

It sits **beside** the [2D physics](/docs/gameplay/physics/), not on top of it. A 2D
scene keeps the solver, the units and the feel it already has, and a project that
never asks for a 3D world never loads it.

## Setup

Like the 2D side module, the 3D world loads on its own in the editor and the web
runtime when a scene uses a 3D body. In a custom app, add the plugin yourself; every
option is optional (gravity defaults to `{ x: 0, y: -9.81, z: 0 }`, `fixedTimestep` to
`1/60`, `collisionSteps` to `1`, `pixelsPerUnit` to `100`, `maxBodies` to `1024`; `layerMasks` is covered under
[collision layers](#collision-layers)):

```typescript
import { Physics3DPlugin } from 'esengine/physics3d';

app.addPlugin(new Physics3DPlugin('physics3d.js', { gravity: { x: 0, y: -9.81, z: 0 } }));
```

## Bodies

An entity is in the world when it carries a `RigidBody3D` **and** a shape. A body
with no shape has no extent to collide with, so it is left out entirely rather than
falling forever as an invisible point.

```typescript
cmds.spawn()
  .insert(Transform, { position: { x: 0, y: 400, z: 0 } })
  .insert(RigidBody3D, { bodyType: BodyType.Dynamic })
  .insert(CapsuleCollider3D, { radius: 30, halfHeight: 50 });
```

| Field | What it does |
|---|---|
| `bodyType` | `Static` never moves, `Kinematic` is moved by hand, `Dynamic` is solved. |
| `gravityScale` | This body's share of world gravity. `0` is weightlessness, not slow falling. |
| `linearDamping` / `angularDamping` | How quickly motion bleeds off (both default `0.05`; 2D bodies default to `0`). |
| `fixedRotation` | Freezes the orientation the body was given — what keeps a character from toppling. It does not right a body that starts tilted. |
| `layer` | Which of the sixteen [collision layers](#collision-layers) the body is in. |
| `continuousCollision` | Checks the whole path a step covers rather than where the body ended up. What a bullet needs; off by default, since it costs more. |

## Shapes

| Component | Extent |
|---|---|
| `BoxCollider3D` | `halfExtents` on each axis. |
| `SphereCollider3D` | `radius`. |
| `CapsuleCollider3D` | An upright capsule: `halfHeight` is the cylinder's half, with a cap of `radius` on each end, so the total height is `2 * (halfHeight + radius)`. |

Defaults: `halfExtents` `{ 0.5, 0.5, 0.5 }`, `radius` `0.5` (`0.3` on the capsule), `halfHeight` `0.5` —
world units, so a freshly added shape is small until you size it. All three also carry `friction` (`0.3`),
`restitution` (`0`) and `isSensor` (`false`).

Each of the three also takes an optional `center`: the shape's place from the entity origin, in world
units (default `{ 0, 0, 0 }`). The body stays at the entity, so a dynamic body turns about its origin and
an off-centre shape swings round it.

<Aside>
  Sizes are authored in **world units** and reach the solver in metres, at the same
  `pixelsPerUnit` the 2D world uses (100 by default). A solver tuned for metres
  behaves nothing like itself when a character is 180 units tall, so the conversion
  is not optional — it is why a capsule 60 units wide falls the way a person does.
</Aside>

### Colliding against imported geometry

A `MeshCollider3D` collides against a mesh's own triangles — a terrain, a
staircase, the inside of a room. It is what a box and a capsule cannot say.

```typescript
cmds.spawn()
  .insert(Transform, {})
  .insert(RigidBody3D, { bodyType: BodyType.Static })
  .insert(MeshCollider3D, { mesh: 'assets/models/level.esmesh' });
```

<Aside>
  Always static, whatever its `RigidBody3D` says: a triangle soup has no inertia
  tensor, so there is nothing for a solver to push. And the triangles are
  ONE-SIDED — a floor whose winding faces down is one that rays still report and
  bodies fall straight through. That is the failure to expect if imported geometry
  stops nothing.
</Aside>

For imported geometry that has to MOVE, use a `ConvexCollider3D`: it collides
against the tightest convex volume around the same vertices, which a solver
handles as readily as a box. A rock, a chamfered crate, a barrel that rolls —
anything whose concave detail does not need to be felt.

```typescript
cmds.spawn()
  .insert(Transform, { position: { x: 0, y: 400, z: 0 } })
  .insert(RigidBody3D, { bodyType: BodyType.Dynamic })
  .insert(ConvexCollider3D, { mesh: 'assets/models/rock.esmesh' });
```

## Seeing a shape

The viewport draws every 3D collider as a wireframe, turned the way its entity is —
nothing else on screen says how big the box around a model is. It is on the same
switch as the 2D collider gizmos.

An entity gets ONE body shape, chosen in the order `BoxCollider3D`,
`SphereCollider3D`, `MeshCollider3D`, `ConvexCollider3D`, `CapsuleCollider3D`. Whatever loses — a
disabled collider, one shadowed by that order, or any collider on an entity with no
enabled `RigidBody3D` — is drawn dimmed and dashed: still there to author, visibly
not what the world will collide with. A `CharacterController3D` capsule is drawn
beside it, since a character is swept rather than solved.

<Aside>
  A mesh collider draws the BOUNDS of its triangles rather than every edge — the
  triangles are the mesh you are already looking at, and a few thousand projected
  edges would bury it.
</Aside>

### While the game runs

The editor's gizmos are hidden in play, so the running game draws its own. Turn
the `Physics3DDebugDraw` resource on when you need to see why something got
stuck where it did:

```typescript
app.getResource(Physics3DDebugDraw).enabled = true;
```

| Field | What it does |
|---|---|
| `enabled` | Off by default — an overlay costs a line per edge per frame. |
| `showColliders` | The shape of every body the solver built. |
| `showContacts` | A cross at each contact point reported this step. |

<Aside>
  Only what the solver actually built is drawn here. A disabled collider is
  authoring state, and the editor is where you see it — the running game showing
  it would be describing a collision that cannot happen.

  The overlay ignores the depth buffer, so a shape inside a wall is still
  visible. That is what a debug view is for.
</Aside>

A `Planet` with `gravity` above 0 pulls every dynamic body toward its centre instead of
along the world's single gravity vector, so a round world has a down everywhere (see
[Terrain](/docs/graphics/terrain/) for the planet itself).

## Characters

A `CharacterController3D` replaces a `RigidBody3D` rather than accompanying one: a
body the solver pushes and a character that sweeps are two answers to where an
entity is. Set `velocity` from gameplay each step and read the result back.

```typescript
const drive = defineSystem([Query(Mut(CharacterController3D)), Res(Input)], (q, input) => {
  for (const [, c] of q) {
    c.velocity.x = (input.isKeyDown('KeyD') ? 200 : 0) - (input.isKeyDown('KeyA') ? 200 : 0);
    if (input.isKeyPressed('Space') && c.isOnFloor) c.velocity.y = 500;
  }
});
app.addSystemToSchedule(Schedule.FixedUpdate, drive);
```

| Field | What it does |
|---|---|
| `velocity` | Desired velocity in world units/second. A positive `y` is a jump. |
| `radius` / `halfHeight` | The upright capsule that is swept (defaults `0.3` / `0.5`, world units), shaped like `CapsuleCollider3D`'s. |
| `stepHeight` | Tallest step it climbs instead of stopping at (default `0.4`). `0` climbs nothing. |
| `snapDown` | How far it reaches down to stay on the floor over a crest (default `0.5`). `0` is off. |
| `maxSlope` | Steepest ground it can stand on, radians (default `0.87`, about 50°); beyond this it slides. |
| `mass` | The character's mass in kilograms (default `70`), used when it shoves bodies. |
| `pushForce` | How hard it shoves dynamic bodies it walks into (default `5000`). `0` moves nothing. |
| `layer` | Which [collision layer](#collision-layers) it is in (0–15). |
| `isOnFloor` / `floorNormal` / `realVelocity` | Outputs, read after the step. |

<Aside>
  The vertical component is carried for you: `velocity.y = 0` means "walk", not
  "hang in the air". A character does not fall on its own in Jolt — the vertical
  speed belongs to the caller — so the module integrates gravity rather than
  leaving every caller to rediscover it.

  A character is SWEPT rather than solved, so nothing moves out of its way on its
  own: `pushForce` is the force it may spend shoving what it walks into. The
  default gets a crate of its own size going; something heavier wants more, and
  `0` walks into everything as if it were a wall.
</Aside>

## Third person

`ThirdPersonController` and `ThirdPersonCamera` are the gameplay layer above a
character: input becomes a request, the character controller answers it, and the
answer is what the animator hears.

```typescript
// Nothing to write. Both are components a scene declares.
world.insert(player, ThirdPersonController, { moveSpeed: 320, jumpSpeed: 520 });
world.insert(rig, ThirdPersonCamera, { target: player, distance: 420 });
```

The stick is read in the camera's GROUND plane, so an eye angled steeply down
still walks the character across the floor. Pitch never reaches the character.

| Field | What it does |
|---|---|
| `moveSpeed` | Top speed on the ground, world units/second (default `320`). |
| `acceleration` / `deceleration` | How fast it reaches that speed, and sheds it, units/second² (defaults `2400` / `3200`). |
| `rotationSpeed` | How fast it turns to face where it went, degrees/second (default `720`). |
| `jumpSpeed` | Upward speed a jump starts with. `0` (the default) cannot jump. |
| `airControl` | How much of `acceleration` applies off the ground, 0..1 (default `0.3`). |
| `cameraRelative` | Read the stick in the camera's ground plane (default `true`) rather than the world's. |
| `camera` | Whose forward the stick is read against; `0` (the default) means the first `ThirdPersonCamera` found. |
| `idleThreshold` | Speed under which the animator is told the character is standing still (default `8`). |

`ThirdPersonCamera` orbits a `target` under pointer control:

| Field | What it does |
|---|---|
| `target` | The entity it orbits; `0` leaves the camera inert. |
| `distance` | How far back it sits when nothing is in the way, world units (default `420`). |
| `yaw` / `pitch` | Turn about world up, and above the horizon (positive looks down), degrees (defaults `0` / `15`). |
| `minPitch` / `maxPitch` | Pitch limits, degrees (defaults `-30` / `70`). |
| `sensitivity` | Degrees per pixel of pointer travel (default `0.2`). |
| `followDamping` | How fast the position catches up, per second; `0` is rigid (default `12`). |
| `targetOffset` | Lifts the pivot off the target's origin so the eye frames the chest, not the feet (default `{ 0, 90, 0 }`). |
| `obstruction` / `obstructionRadius` / `obstructionLayers` | Pull in when something solid is between pivot and eye (default on), how fat the probe is (default `15`), and which layers it hits (`0` is all). |

<Aside>
  The animator is told the speed the character REACHED, not the speed it asked
  for. A character shoving a wall has a full stick and no motion, and it must not
  be running on the spot; the same reading is what makes a slope it cannot climb
  look like the stop it is.

  The camera sweeps the physics world between the pivot and the eye, pulling in
  when something solid stands between. It moves nothing but itself.
</Aside>

## Melee combat

Three facts, and the whole of a combat system is keeping them apart:

```text
an animation event   ≠   a hit   ≠   damage
```

The clip says only that the swing reached its effective moment. What was in that
space is the physics world's answer. What that does to anyone is gameplay's.
Collapse any two and you get a combat system that cannot be re-aimed, re-timed
or re-balanced without touching the other two.

`MeleeAttack` sits beside an `Animator` whose attack clip declares three beats
on a `customEvent` track — `attack-start`, `hit`, `attack-end`:

```typescript
world.insert(player, MeleeAttack, { radius: 70, damage: 25, anchor: swordSocket });
world.insert(dummy, Health, { current: 100, max: 100 });
```

| Field | What it does |
|---|---|
| `radius` | Radius of the sphere a `hit` beat tests, world units (default `60`). |
| `damage` | What a landed blow takes off (default `25`). |
| `layers` | Physics layers the swing can reach; `0` is every layer. |
| `anchor` | The entity whose WORLD placement the query is centred on. |
| `attackId` | Engine-written: the live swing, `0` when none is running. |
| `hitCount` | Engine-written: how many targets it has landed on. |

<Aside type="caution">
  `anchor` should be a socket parented to an animated joint, not the character.
  Centre the query on the character and the reach is an offset from its feet:
  the skeleton is drawn but never consulted, and a swing that misses on screen
  still lands. The anchor's world placement is composed before the query, so
  what it asks about is what the animation did.
</Aside>

A swing is an INSTANCE with its own id and its own set of who it has already
reached, so one swing lands on one target once and the next one may land again.
A hit window is normally several `hit` beats, and leaning on "the event only
fires once" instead breaks the first time a clip declares two — silently, as
double damage, which reads as a balance problem rather than a bug.

Nothing in the swing writes health. A landed blow is sent on the `Damage` bus and
one system answers it, so `Health` has a single author and every rule that will
ever sit between a hit and a health bar has one seam to sit in:

```typescript
import { defineSystem, EventReader, GetWorld, Res, Damage, Children, ParticleEmitter, Particle } from 'esengine';

const hitSparks = defineSystem(
  [EventReader(Damage), GetWorld(), Res(Particle)],
  (blows, world, particles) => {
    for (const blow of blows) {
      if (!world.has(blow.target, Children)) continue;
      for (const child of world.get(blow.target, Children).entities) {
        if (world.has(child, ParticleEmitter)) particles.play(child);
      }
    }
  },
  { name: 'HitSparkSystem' },
);
```

A blow carries `target`, `source`, `amount` and the point it landed at (`x`, `y`, `z`) — that
point cannot be recovered later, because by the time a spark is drawn the swing
has moved on. The bus is double buffered, so a blow sent this frame lands on the
next.

<Aside type="tip">
  The physics query answers with colliders and nothing else. Self, already-hit
  and not-damageable are gameplay's rules and live with the swing — the floor is
  a collider too, and it is `Health` that says an entity can be hurt at all.
</Aside>

## Joints

A door, a rope bridge, a lift, a ragdoll: none of them are one body and a shape.
They are two bodies and a rule about how they may move relative to each other. A
joint lives on the entity that declares it and names the other one.

```typescript
cmds.spawn()
  .insert(Transform, { position: { x: 100, y: 0, z: 0 } })
  .insert(RigidBody3D, {})
  .insert(BoxCollider3D, { halfExtents: { x: 50, y: 100, z: 5 } })
  .insert(HingeJoint3D, {
    connectedEntity: frame,
    anchor: { x: -50, y: 0, z: 0 },   // the door's own edge
    axis: { x: 0, y: 1, z: 0 },       // upright
    enableLimit: true, lowerAngle: 0, upperAngle: Math.PI / 2,
  });
```

| Component | Rule |
|---|---|
| `PointJoint3D` | A shared point, free to turn on all three axes. |
| `HingeJoint3D` | One axis of rotation, with optional limits and a motor. |
| `SliderJoint3D` | One axis of travel, with optional limits and a motor. |
| `DistanceJoint3D` | A distance kept: a rope with `maxLength`, a rod when the lengths meet, a spring with `frequency`. |
| `FixedJoint3D` | No freedom at all — the two move as one. |

`anchor` and `axis` are written in the declaring entity's own local space, in
world units, and are resolved against its transform when the joint is made. That
pose is also the **zero** of every limit: a door placed closed has `angle` 0 and
opens to `upperAngle`.

Set `motorSpeed` from gameplay at any time — the world is re-driven when it
changes. In the other direction, `HingeJoint3D.angle` and
`SliderJoint3D.translation` are written back each step, so a game can ask how far
the door swung without integrating the swing a second time.

<Aside>
  `collideConnected` is false by default, and it joins the two bodies into ONE
  assembly rather than one pair: everything a chain of joints reaches stops
  colliding with the rest of that chain. That is what a door needs (it must not
  fight its own frame) and what a ragdoll needs. Turn it on when the two really
  should meet.

  One joint per entity — the world keys a constraint by the entity that declared
  it. An entity that needs two joints carries a child for the second, which is
  also how a scene says which is which.
</Aside>

## Asking the world what is where

The `Physics3D` resource answers spatial questions in world units.

```typescript
const q = app.getResource(Physics3D);

// Is anything on this line?
const hit = q.raycast(muzzle, { x: 0, y: 0, z: -2000 }, ENEMIES);

// Can this thing GET there? A ray is infinitely thin and slips through gaps a
// moving body would not fit — that is what a swept shape answers instead.
const blocked = q.sphereCast(from, 30, travel, WORLD);

// What is already here, before something is spawned into it?
const occupants = q.overlapSphere(spawnPoint, 50);
```

| Query | Answers |
|---|---|
| `raycast(origin, direction, layerMask?)` | The nearest body on a line, as `{ entity, fraction, x, y, z, normalX, normalY, normalZ }`, or `null`. `direction` carries the ray's length. |
| `sphereCast(origin, radius, direction, layerMask?)` | The first body a moving sphere would meet, same shape, or `null`. |
| `overlapSphere(centre, radius, layerMask?)` / `overlapBox(centre, halfExtents, layerMask?)` | Every body already inside a volume, as `{ entity, x, y, z }[]`. |

`Physics3D` holds `null` until the physics module has finished loading, so a system
that asks in the first frames should check for it.

<Aside>
  A layer mask of `0` means EVERY layer, not none: a caller that did not ask to
  filter is asking for everything, and the other reading would make the commonest
  call return silently empty. Hit normals come back unscaled — they are
  directions, and multiplying one by `pixelsPerUnit` leaves a unit vector 100
  units long.
</Aside>

## Collision layers

Every body is in one of sixteen layers, and a project says which layers hear from
which. Both sides must agree — one of them refusing is enough to keep two bodies
apart, so a rule only has to be written once to hold.

```typescript
app.addPlugin(physics3dPlugin(url, {
  layerMasks: [
    0xFFFF,             // 0: everything
    0xFFFF,             // 1: the world
    ~(1 << 3),          // 2: bullets — not their own team
    0xFFFF,             // 3: that team
  ],
}));
```

<Aside>
  ONE layer per body, not a set of category bits like the 2D world uses: Jolt
  classifies a body by a single id. And a body's layer is fixed when it enters the
  world, so the matrix has to be in place before anything is registered — the
  plugin installs it as the world is built.
</Aside>

## Collision events

Each step publishes what touched what into the `Physics3DEvents` resource. It is
drained per fixed step, so a system reading it must run inside one — a read from
`Update` sees whatever the last step happened to leave.

```typescript
const events = app.getResource(Physics3DEvents);
for (const hit of events.contactEnters) {
  // both entities, and where they met
  spawnSparks(hit.pointX, hit.pointY, hit.pointZ);
}
for (const { sensorEntity, visitorEntity } of events.sensorEnters) {
  if (sensorEntity === goalZone) score(visitorEntity);
}
```

| Channel | What it carries |
|---|---|
| `contactEnters` | Both entities, the contact normal and the point, in the same units as `Transform`. |
| `contactExits` | Only the pair — see below. |
| `sensorEnters` / `sensorExits` | The **sensor first**, then the visitor. |

<Aside>
  An ended contact carries no geometry: at that moment the solver has both bodies
  locked and one of them may already have been destroyed, so there is nothing left
  to report but who the pair was. A contact also ends when a body falls asleep,
  not only when it moves away — treat an exit as "this pair is no longer touching",
  not as "something moved".
</Aside>

A collider with `isSensor` reports overlaps and stops nothing: the visitor passes
straight through and shows up in `sensorEnters` instead of `contactEnters`.

## Which world a scene is in

Nothing stops an entity carrying both sets, but nothing merges them either: the two
worlds do not see each other, and a 2D collider will never stop a 3D body. Pick one
per scene.

### Swing/twist and six-axis joints

`SwingTwistJoint3D` locks translation and limits rotation with an elliptical swing
cone and a separate twist interval. `axis` is local constraint X (twist),
`normalAxis` is its local Y reference. Directions are normalized and orthogonalized;
zero or parallel directions are rejected.

`SixDOFJoint3D` independently controls each axis using `JointMotion3D.Locked` (0),
`Limited` (1), or `Free` (2) in `translationMotion` and `rotationMotion`. Locked axes
stay at the creation pose; limited axes use the corresponding lower/upper vector;
free axes ignore those bounds. Limited lower bounds must be strictly below upper
bounds. Angular limits lie within −π to π; Y/Z rotation uses Jolt's pyramid limits.

```typescript
cmds.spawn().insert(SixDOFJoint3D, {
  connectedEntity: base,
  translationMotion: { x: JointMotion3D.Limited, y: JointMotion3D.Locked, z: JointMotion3D.Locked },
  translationLower: { x: -100, y: 0, z: 0 },
  translationUpper: { x: 100, y: 0, z: 0 },
});
```

The Inspector shows angles in degrees; files and scripts store radians. Translation
limits and linear velocity use world units and world units/s. Angular velocity is
rad/s; force and torque are N and N·m, independent of `pixelsPerUnit`.

Motors default off. `enableMotor`, `linearVelocity` (SixDOF only),
`angularVelocity`, `maxMotorForce` and `maxMotorTorque` can change while running
without rebuilding the joint. Targets describe **connected body B relative to the
owning body A**, in constraint axes. If B is static, A moves in the opposite direction.
Each motor axis shares the specified force/torque cap. This is velocity control,
not a pose servo or active ragdoll.

Changing a frame, collision setting or limit rebuilds these joints using the
current pose as zero. Disabling/removing a component releases it before its bodies
are removed. `joint3DSettingsError(settings)` reports invalid settings; invalid
joints remain uncreated instead of entering the solver with malformed limits.

The existing **3D Physics** example includes a shoulder/arm and a limited carriage.
Press **J** to reverse their motors; **F1** toggles collider debug drawing. Select
either joint in the editor to inspect its limits. Viewport limits are read-only;
edit their numbers in Details. These components are experimental. Headless Jolt
checks cover limits and motors; target-device acceptance is recorded separately.
