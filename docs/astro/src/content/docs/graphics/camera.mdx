Every scene is rendered through a camera: an entity with a `Camera` component. A
camera controls zoom, projection, and which slice of the world reaches the screen.
This guide covers configuring a camera, following a target, converting between
screen and world space, shaking and blending the view, and running several cameras
at once.

## How it works

You can have many camera entities, but one is **active** at a time. The engine
picks the active camera by `isActive` + `priority` (the highest-priority active
camera wins), and renders the world through it into its `viewport` (a screen
rectangle). For a 2D game the projection is **Orthographic**, where `orthoSize` —
the visible half-height in world units — *is your zoom*: smaller means zoomed in.

<Aside type="note">
  A camera is just an entity with a `Camera` component — nothing to install. The
  follow, blend, and shake systems below run in the editor and the standard
  runtime automatically.
</Aside>

## Quick start

Spawn an orthographic camera and make it active:

```typescript
import { defineSystem, Commands, Transform, Camera, ProjectionType } from 'esengine';

const spawnCamera = defineSystem([Commands()], (cmds) => {
  cmds.spawn()
    .insert(Transform, { position: { x: 0, y: 0, z: 0 } })
    .insert(Camera, {
      projectionType: ProjectionType.Orthographic,
      orthoSize: 540,        // half-height in world units → zoom
      isActive: true,
    });
});
```

## The `Camera` component

The SDK defaults are tuned for 2D (Orthographic, active, `orthoSize` 540). Move
the camera by moving its entity's `Transform`.

| Property | Type | Default | Description |
|---|---|---|---|
| `projectionType` | `ProjectionType` | `Orthographic` | `Orthographic` (2D) or `Perspective`. |
| `orthoSize` | number | `540` | Visible half-height in world units (Orthographic) — your **zoom**. Animatable. |
| `fov` | number | `60` | Field of view in degrees (Perspective only; 1–179). |
| `nearPlane` | number | `0.1` | Near clip distance (Perspective only). |
| `farPlane` | number | `1000` | Far clip distance. Orthographic has no near plane and renders a symmetric `±farPlane` box, so this is its reach in both directions. |
| `aspectRatio` | number | `1.77` | Width / height. `0` = auto from the viewport. |
| `isActive` | boolean | `true` | Whether this camera is eligible to be the active one. |
| `priority` | number | `0` | Tie-breaker among active cameras (higher wins). |
| `viewport` | Vec4 | `{0,0,1,1}` | Screen rect `x, y, w, h` in 0–1 (split-screen / PiP). |
| `clearFlags` | `ClearFlags` | `ColorAndDepth` | What to clear first: `Nothing` / `Color` / `Depth` / `ColorAndDepth`. |
| `pixelPerfect` | boolean | `false` | Snap to the world pixel grid for crisp pixel art (Orthographic). |
| `cullingMask` | number | all layers | Bitmask of sorting layers this camera renders (bit *i* = layer *i*). |
| `renderTarget` | number | `0` | `RenderTexture` handle this camera draws into instead of the screen (`0` = screen) — a minimap or mirror; set from a script at run time. |
| `showFrustum` | boolean | `false` | Editor-only: draw this camera's whole view volume, near face to far. Off, its gizmo outlines what it frames on the content plane — which is empty for a camera aimed away from it. |

## Zoom & projection

`orthoSize` is the zoom control — halve it to double the on-screen scale. Because
it's `animatable`, the smoothest way to zoom is a [tween](/docs/animation/overview/):

```typescript
import { defineSystem, Res, Tween, TweenTarget } from 'esengine';

const zoomIn = defineSystem([Res(Tween)], (tween) => {
  tween.to(cameraEntity, TweenTarget.CameraOrthoSize, 270, 0.5);   // zoom to 2×
});
```

Use `Perspective` only for pseudo-3D layered scenes; leave 2D games on
`Orthographic` so sizes stay constant with depth.

## Design-resolution fit

A shipped game runs on screens of every aspect. Each frame the engine resolves a
*fit source* and, when one is active, adapts the main camera to the actual screen
aspect: `orthoSize` is the camera's half-height **at the design aspect**, and the
scale mode decides what happens on a wider or narrower screen (keep the height, keep
the width, expand, shrink or match). The fit source is, in order:

1. the **`ScreenScaling`** resource (Settings → Project → Game → Display → Camera fit), when
   its `scaleMode` is a real mode (`≥ 0`);
2. else the scene's **`Canvas`** component, if one exists;
3. else none — the camera renders its raw `orthoSize`.

`orthoSize` stays the zoom under a fit — the tween above works with a `Canvas` in the
scene. UI does not follow the zoom: the box UI lays out in is the design resolution
fitted to the screen, so zooming the camera never reflows it, and screen-space UI is
drawn through its own projection.

Set `orthoSize` to `designResolution.y / 2` to show exactly the design frame (the
default `540` matches the default 1080-high design). Up to 0.97 a fit ignored
`orthoSize` and always used `designResolution.y / 2`; a scene that authored another
value under a fit now shows that value. Scale modes, worked letterbox
examples, and the `ScreenScaling` fields are covered in
[Screen & Design Resolution](/docs/core-concepts/screen/).

## Follow a target

Add a `FollowTarget` to the camera and point it at an entity. The follow is a
frame-rate-independent damped move with a dead zone, so the camera drifts smoothly
and ignores tiny movements:

![The camera holds the target at a fixed offset from the view centre; the target roams free inside a deadzone circle and the camera eases after it once it leaves](@/assets/guides/camera-follow.svg)

```typescript
import { defineSystem, Query, Commands, Camera, FollowTarget } from 'esengine';

const follow = defineSystem([Query(Camera), Commands()], (cameras, cmds) => {
  for (const [cameraEntity] of cameras) {
    cmds.entity(cameraEntity).insert(FollowTarget, {
      target: playerEntity,   // the Entity to follow
      offsetY: 40,
      deadzone: 24,
      damping: 0.25,
    });
  }
});
```

| Property | Type | Default | Description |
|---|---|---|---|
| `target` | Entity | `0` | Entity to follow (`0` = none; a `-1` from an older scene reads as none too). |
| `offsetX` | number | `0` | World-space X offset from the target (in the world even under a parent). |
| `offsetY` | number | `0` | World-space Y offset from the target. |
| `offsetZ` | number | `0` | World-space Z offset from the target (used by 3D follow). |
| `followZ` | boolean | `false` | Follow the target's depth too. Off for a flat scene, where the camera's z is how far back it stands. |
| `deadzone` | number | `0` | Radius (world units; a sphere in 3D) the target may roam before the camera moves. |
| `damping` | number | `0.25` | Smoothing time-constant in seconds (larger = slower; `0` = snap). |

The data shape is exported as the `FollowTargetData` type. The follow system writes
the camera's `Transform` directly (so the director blends already-followed views)
and runs in **play mode only** — the editor's navigation view is never dragged
around by it.

## Look at a target

`FollowTarget` decides where a camera stands; `LookAtTarget` decides where it looks. Add it to a perspective camera
and point it at an entity: the camera turns so the target sits at a chosen point of the screen, the way Unity
Cinemachine's Rotation Composer frames a shot. The target may drift inside a dead zone around that point without the
camera turning, and outside it the camera turns only enough to bring it back to the zone's edge, eased by `damping`.

```typescript
import { LookAtTarget } from 'esengine';

cmds.entity(cameraEntity).insert(LookAtTarget, {
  target: hero,
  offsetY: 160,          // the head, not the feet
  screenX: 0.5,          // held in the middle...
  screenY: 0.6,          // ...a little above centre
  deadzoneWidth: 0.1,    // free to move across a tenth of the screen
  deadzoneHeight: 0.1,
  damping: 0.2,
});
```

| Property | Type | Default | Description |
|---|---|---|---|
| `target` | Entity | `0` | Entity to look at (`0` = none). |
| `offsetX` / `offsetY` / `offsetZ` | number | `0` | Point looked at, as a world-space offset from the target. |
| `screenX` | number | `0.5` | Where the target is held across the screen: `0` left edge, `0.5` centre, `1` right edge. |
| `screenY` | number | `0.5` | Where the target is held up the screen: `0` bottom edge, `0.5` centre, `1` top edge. |
| `deadzoneWidth` / `deadzoneHeight` | number | `0` | Share of the screen the target may move in without the camera turning. |
| `damping` | number | `0.1` | Seconds to turn most of the way to the target (`0` = at once). The same at any frame rate. |

The camera turns about world up and its own right, so it never rolls. A camera under a parent is turned in the world
and its own rotation is worked out through the parent's. An orthographic camera is left alone: it draws a plane, and
turning it would show the plane's edge. The screen point is measured on the view the camera actually draws, its
`viewport` share of the screen, so a shot holds the same framing on a phone and on a wide monitor.

## The camera pipeline

Every `Camera` is a virtual camera: a view the scene describes. Each frame, before any view is chosen, every camera is
moved by the components it carries, always in this order:

| Stage | Component | Cinemachine | Unreal |
|---|---|---|---|
| 1. Position: where it stands | `FollowTarget` or `CameraDolly` | Position Control (Follow, Spline Dolly) | camera rig position node |
| 2. Rotation: where it looks | `LookAtTarget` | Rotation Control (Rotation Composer) | camera rig look-at node |
| 3. Finalize: limits on the result | `CameraBounds` | Extensions (Confiner) | camera modifiers |
| 4. Noise: drift on the drawn view | `CameraNoise` | Noise (Basic Multi-Channel Perlin) | camera shake |

Each stage decides in the world and writes through the camera's parent, and reads what the stages before it wrote, so
a camera that follows and looks at the same character aims from where it stands this frame. Noise moves only the drawn
view, per camera, before the blend. The camera director then picks one live camera and blends into it (below): Cinemachine's
Brain and Unreal's `PlayerCameraManager`. Camera shake is applied after that, to the drawn view only, never to a
camera's `Transform`, as a Cinemachine Impulse and an Unreal camera shake are. The pipeline runs in **play mode only**.

## Ride a track

A `CameraDolly` puts a camera on a track: a `Spline` entity laid in the scene, like a dolly on rails. It is the other way
to say where a camera stands (`FollowTarget` is the first); a camera uses one of the two. `mode` picks the place on the
track:

- **Fixed** (`DollyMode.Fixed`): at `position`, for a script or an animation to move.
- **Track Target** (`DollyMode.TrackTarget`): at the point of the track nearest `target`, moved along by `offset`: a
  camera that runs beside what it films.
- **Speed** (`DollyMode.Speed`): moving at `speed`, round and round a closed track or to the end of an open one.

```typescript
import { CameraDolly, DollyMode, LookAtTarget } from 'esengine';

cmds.entity(cameraEntity)
  .insert(CameraDolly, { spline: railEntity, mode: DollyMode.TrackTarget, target: runner, offset: -150, damping: 0.4 })
  .insert(LookAtTarget, { target: runner });
```

| Property | Type | Default | Description |
|---|---|---|---|
| `spline` | Entity | `0` | The entity whose `Spline` is the track. |
| `mode` | number | `Fixed` | How the place on the track is chosen (`DollyMode`). |
| `position` | number | `0` | Where on the track the camera is, in world units from its start. Written back every frame, in every mode. |
| `target` | Entity | `0` | What a Track Target dolly keeps level with. |
| `offset` | number | `0` | World units ahead of (or, negative, behind) the point nearest the target. |
| `speed` | number | `0` | World units a second along the track, for Speed; negative runs backwards. |
| `damping` | number | `0.3` | Seconds for a Track Target dolly to catch up most of the way; `0` is at once. |

Distances are along the curve in world units, so a scaled spline is longer. On a closed track a Track Target dolly takes
the short way round, so a target crossing the seam does not send the camera round the loop. The track is the same curve a
`PathFollower` rides.

## Handheld noise

A `CameraNoise` makes a camera drift and nod like one held by hand, or sway like one on a boat: six channels of smooth
Perlin noise, three moving the view across, up and along itself and three turning it about the same axes, as Cinemachine's
Basic Multi-Channel Perlin does.

```typescript
import { CameraNoise } from 'esengine';

cmds.entity(cameraEntity).insert(CameraNoise, { rotation: 0.5, frequency: 0.3 });   // handheld
cmds.entity(carCamera).insert(CameraNoise, { amplitude: 4, rotation: 1.5, frequency: 2 });   // on a vehicle
```

| Property | Type | Default | Description |
|---|---|---|---|
| `amplitude` | number | `0` | How far the view drifts, in world units. |
| `rotation` | number | `0.5` | How far the view turns, in degrees. About `0.5` is a camera held by hand. |
| `frequency` | number | `0.3` | How often the drift changes direction, in Hz: about `0.3` by hand, `2` on a vehicle. |
| `seed` | number | `0` | Which drift; `0` takes one from the entity, so no two cameras move alike. |

Noise moves the view that is drawn and never the camera's `Transform`, so it does not build up, and follow, dolly and
look-at work from where the camera really is. It is applied to each camera before the director blends between them, so a
blend from a shaky camera to a steady one settles. A 2D camera drifts across the screen and rolls. Noise follows the game
clock: it stops when the game is paused.

## Keep the camera inside the level

Add a `CameraBounds` to the camera and the view never leaves the rectangle — the
level's edge stays at the edge of the screen instead of showing the void past it:

```typescript
import { Camera, CameraBounds } from 'esengine';

cmds.entity(cameraEntity).insert(CameraBounds, {
  minX: -1280, maxX: 1280,   // the level's world rectangle
  minY: -768,  maxY: 768,
});
```

| Property | Type | Default | Description |
|---|---|---|---|
| `minX` / `maxX` | number | `0` | Horizontal interval the view stays inside. |
| `minY` / `maxY` | number | `0` | Vertical interval the view stays inside. |

Each axis opts in by naming a real interval, so an axis left at `0`/`0` (or any
`max ≤ min`) is unconstrained — bound the horizontal one alone for a level that
scrolls sideways forever. When an interval is narrower than the view, the whole
of it is shown centred rather than pinned against one wall.

The clamp runs after everything that moves a camera, `FollowTarget` included: it
constrains where a camera ends its frame, not what put it there. Orthographic
cameras only — a perspective camera's half extents depend on how far away the
subject is, which no camera property describes. Like the follow, it runs in
**play mode only**.

## Screen ↔ world coordinates

Read the `CameraView` resource to convert between the two spaces — for placing
entities under the cursor, or testing what's visible. Each method returns `null`
when there is no active camera:

```typescript
import { defineSystem, Res, CameraView, Input } from 'esengine';

const pick = defineSystem([Res(CameraView), Res(Input)], (view, input) => {
  const world  = view.screenToWorld(input.mouseX, input.mouseY);  // { x, y } | null
  const screen = view.worldToScreen(x, y);                        // { x, y } | null
  const mouse  = view.getWorldMousePosition();                    // { x, y } | null
  const bounds = view.getWorldBounds();  // { left, right, bottom, top } | null
});
```

| Method | Returns | Description |
|---|---|---|
| `screenToWorld(sx, sy, planeZ = 0)` | `{x, y} \| null` | Screen pixel → world position on the plane at `planeZ`. Orthographic cameras ignore the plane; under a perspective camera pass the z the target sits on. |
| `worldToScreen(wx, wy, wz = 0)` | `{x, y} \| null` | World position → screen pixel. `null` when there is no camera or the point is at or behind the eye; outside the viewport still returns coordinates. |
| `getWorldMousePosition()` | `{x, y} \| null` | The cursor in world space. |
| `getWorldBounds()` | `{left, right, bottom, top} \| null` | The visible world rectangle. |

## Camera shake

`shakeCamera` adds a decaying perturbation to the **rendered** view only — never to
a Transform, so the camera always recovers and the scene stays clean:

```typescript
import { shakeCamera } from 'esengine';

shakeCamera(app, { amplitude: 12, rotation: 0, frequency: 22, duration: 0.4 });
```

Both `shakeCamera` and `setViewTarget` accept either the `App` (host code) or the
`CameraDirector` resource state — inside a system, pass what `Res(CameraDirector)`
gives you:

```typescript
import { defineSystem, Res, Input, CameraDirector, shakeCamera } from 'esengine';

const shakeOnHit = defineSystem([Res(Input), Res(CameraDirector)], (input, director) => {
  if (input.isKeyPressed('Space')) shakeCamera(director, { amplitude: 16 });
});
```

| Option | Default | Description |
|---|---|---|
| `amplitude` | `12` | Peak positional offset (world units). |
| `rotation` | `0` | Peak rotational shake (radians). |
| `frequency` | `22` | Oscillations per second. |
| `duration` | `0.4` | Seconds to decay to zero. |

## Blending between cameras

`setViewTarget` switches the active view to another camera entity, optionally
**blending** over `time` seconds instead of cutting — for cinematic hand-offs:

```typescript
import { setViewTarget, BlendCurve } from 'esengine';

// Cut instantly:
setViewTarget(app, cutsceneCamera);
// Or ease over 1.5s:
setViewTarget(app, cutsceneCamera, { time: 1.5, curve: BlendCurve.EaseInOut });
```

`BlendCurve` values are `Linear`, `EaseIn`, `EaseOut`, and `EaseInOut`. `time <= 0`
(or no prior view) is an instant cut. Position, zoom, and rotation interpolate;
a 3D camera's orientation turns the short way round from one camera's to the
other's; discrete fields (projection, viewport) snap at the midpoint.

## Switching cameras by priority

Among the active cameras that fill the screen, the one with the highest `priority` is live; on a tie, the first. Raise
a camera's priority, or turn a camera on or off, and a different one goes live. By default the view cuts to it. Add a
`CameraBrain` to any entity of the scene and the view blends instead, the way a Cinemachine Brain's Default Blend does:

```typescript
import { CameraBrain, BlendCurve } from 'esengine';

cmds.spawn().insert(CameraBrain, { defaultBlend: 1.2, blendCurve: BlendCurve.EaseInOut });

// Later: this camera goes live, and the view eases over to it in 1.2 seconds.
cmds.entity(bossCamera).insert(Camera, { ...bossCameraData, priority: 10 });
```

| Property | Type | Default | Description |
|---|---|---|---|
| `defaultBlend` | number | `1` | Seconds the view takes to move to a camera that goes live without being asked for. `0` cuts. |
| `blendCurve` | number | `EaseInOut` | Easing of that blend: `BlendCurve.Linear`, `EaseIn`, `EaseOut` or `EaseInOut`. |

If the live camera changes again in the middle of a blend, the new blend starts from where the view is, so it never
jumps. A `setViewTarget` names its own blend time and is not affected by the brain. One brain per scene; a scene
without one cuts, as before.

## The camera director

`setViewTarget` and `shakeCamera` are the API of the **camera director** — a
per-app resource (`CameraDirector`) that resolves *one* main point of view each
frame from the full-frame camera candidates: the committed view target (or the
active/priority camera), blended toward a new target while a transition is in
flight, with shakes applied on top of the rendered view only. Its state
(`CameraDirectorState`) is readable; treat it as **read-only** and mutate through
`setViewTarget` / `shakeCamera`:

| Field | Type | Default | Description |
|---|---|---|---|
| `target` | number | `-1` | Committed view-target entity; `-1` = fall back to the `isActive` / highest-`priority` pick. |
| `blending` | boolean | `false` | A view-target blend is currently in flight. |
| `duration` / `curve` | number | `0` / `EaseInOut` | Length (seconds) and easing of the active blend. |
| `currentMain` | `CameraPOV \| null` | `null` | The last resolved main POV, **pre-shake** — also what screen↔world conversion uses. |
| `shakes` | `ActiveShake[]` | `[]` | Active transient shakes (pushed by `shakeCamera`, dropped when they decay out). |

The remaining fields (`timelineShot`, `timelineOwner` — set by a playing timeline's camera track — `hasPending`, `pendingTarget`, `pendingTime`, `pendingCurve`,
`from`, `startTime`, `shakeSeq`) are the director's internal request/blend
bookkeeping written by `setViewTarget`.

```typescript
import { defineSystem, Res, CameraDirector } from 'esengine';

const watchDirector = defineSystem([Res(CameraDirector)], (director) => {
  if (director.blending) { /* e.g. suppress player input during the hand-off */ }
  const pov = director.currentMain;   // CameraPOV | null — the view being rendered
  if (pov) { /* pov.x, pov.y, pov.orthoSize, ... */ }
});
```

### `CameraPOV`

A `CameraPOV` is a camera's *authored view parameters* as one plain snapshot —
the unit the director blends and the shape stored in `currentMain`:

| Field | Type | Description |
|---|---|---|
| `entity` | number | Source camera entity, or `-1` for a synthetic POV (the editor view). |
| `isActive` | boolean | The authoritative "this is the main camera" flag. |
| `x` / `y` / `z` | number | Camera position (world units). |
| `rotation` | number | Z rotation in radians. |
| `projection` | number | A `ProjectionType` value. |
| `orthoSize` | number | Authored ortho half-height (world units). |
| `fov` | number | Field of view in degrees (Perspective). |
| `near` / `far` | number | Clip distances. |
| `viewport` | `{x, y, z, w}` | Screen rect in 0–1 (`z`/`w` are width/height). |
| `clearFlags` | number | A `ClearFlags` value. |
| `priority` | number | Tie-breaker among active cameras. |
| `pixelPerfect` | boolean | Pixel-grid snapping flag. |

During a blend, continuous fields (position, `rotation` via the shortest angular
path, `orthoSize`, `fov`, `near`/`far`) interpolate; discrete fields (`projection`,
`pixelPerfect`) flip at the midpoint, and `viewport` / `clearFlags` / `priority`
take the target's values.

## Matching the canvas aspect

`updateCameraAspectRatio(world, aspect)` stamps `aspectRatio` onto **every**
`Camera` component in the world. The shipped runtimes call it at boot with the
real canvas's `width / height`, keeping the authored field in sync with the actual
surface (rendering itself derives aspect from the live viewport each frame):

```typescript
import { updateCameraAspectRatio } from 'esengine';

updateCameraAspectRatio(app.world, canvas.width / canvas.height);
```

## Multiple cameras & split-screen

With several `Camera` entities, the active one with the highest `priority` is live (see
[Switching cameras by priority](#switching-cameras-by-priority)). Give
each camera a sub-rectangle via `viewport` to share the screen — e.g. two-player
split-screen, left and right halves:

```typescript
.insert(Camera, { viewport: { x: 0,   y: 0, w: 0.5, h: 1 }, isActive: true }); // left
.insert(Camera, { viewport: { x: 0.5, y: 0, w: 0.5, h: 1 }, isActive: true }); // right
```

## Best practices

- **Drive zoom through `orthoSize`**, not Transform scale — scaling the camera
  entity distorts rendering.
- **Follow with a dead zone** so the camera doesn't jitter on small movements;
  raise `damping` for a lazier, cinematic feel.
- **Shake, don't move**: use `shakeCamera` for impacts so the view always recovers.
- **Enable `pixelPerfect`** for pixel-art games to kill sub-pixel shimmer.
- **Prefer blending** (`setViewTarget` with `time`) over teleporting the camera for
  scene and cutscene transitions.

## Large worlds

A position held in a single float is precise only near zero: 50 km out a step is 4 mm, and a mesh there jitters as the camera moves. `setRenderOriginStep(step)` draws the world relative to a point near the camera instead:

```ts
import { setRenderOriginStep } from 'esengine';

setRenderOriginStep(1024); // metres; 0 (the default) draws relative to the world's own zero
```

The origin is the camera's position rounded to `step`, and it stays where it is until the camera is further than `step` from it, so shadow maps, the light grid and the other caches laid out on the world's grid change only when it does. The renderer takes every mesh, light, probe, particle, trail, tilemap and world-space UI from the origin before the GPU sees it, and the camera's view-projection is built for the same origin, so the picture is the same and the numbers in it are small. Terrain, planets, water, foliage, height fog and the sky's clouds are laid by the world's own position and read it back from the origin, so they do not slide when it steps.

Things that stay in the world's own coordinates, and are not affected: transforms, physics, networking, `screenToWorld` and picking. Draw callbacks and debug drawing are handed the world's view-projection and draw in the world's coordinates, so they keep the precision a single float has far from zero. One origin serves a frame: with several cameras it follows the screen's own, and a camera far from it draws at single-float precision. The previous frame's view and meshes are taken to the new origin when it steps, so motion vectors and temporal effects carry on; the global-illumination voxels settle for a frame.
