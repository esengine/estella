import { Aside } from '@astrojs/starlight/components';

The widget factories build common controls out of the [UI](/docs/guides/ui/) component
model (`UINode` + `Interactable` + a `$interaction`
[controller with gears](/docs/guides/ui-controllers/)), so you don't wire
each one by hand. Each factory takes an options object and returns a **handle** —
always with `entity` and `dispose()`, plus imperative methods to read and drive it.

Interactive widgets need the world and the UI event queue — `world` from `GetWorld()`
and `events` from `Res(UIEvents)`, exactly as in the [UI guide](/docs/guides/ui/). They
all accept `parent?`, a `node?` ([`UINode`](/docs/guides/ui/#uinode--the-layout-box)
layout), and visual overrides. Interactive widgets are **keyboard-reachable by
default**: they carry a `Focusable`, so Tab reaches them, Enter/Space clicks them, and
arrow keys drive sliders — opt out with `focusable: false`.

<Aside type="tip">
  These are a convenient starting point, not a closed set — a widget is just an entity
  tree with the UI components on it, so you can compose your own the same way.
</Aside>

<Aside type="note">
  For **shared** state across many elements — tabs, radio groups, show/hide panels, or
  custom button states driven from data — reach for
  [UI Controllers](/docs/guides/ui-controllers/): a named "page" state plus declarative
  per-page field bindings, authorable in the editor.
</Aside>

## Button

`createButton(opts)` spawns a clickable entity (with an optional child label) that
transitions between visual states. Returns a `ButtonHandle`. A click is a
press-then-release *over* the button — or Enter/Space while it has keyboard focus.

```typescript
import { createButton } from 'esengine';

const btn = createButton({
  world, events, parent,
  text: 'Play',
  node: { width: px(160), height: px(44) },
  states: {
    normal:  { color: { r: 0.20, g: 0.55, b: 1.0, a: 1 } },
    hover:   { color: { r: 0.30, g: 0.65, b: 1.0, a: 1 } },
    pressed: { color: { r: 0.12, g: 0.45, b: 0.9, a: 1 } },
    disabled:{ color: { r: 0.3, g: 0.3, b: 0.3, a: 1 } },
  },
  onClick: (entity) => { /* … */ },
});
```

| Option | Description |
|---|---|
| `text` | Label — a string or a `TextInit`. Omit for no label. |
| `states` | Map of state name (`normal` / `hover` / `pressed` / `disabled` / `focused`) → color / sprite / scale override. Omit to use the active theme's control roles. |
| `background` | Background visual (default: solid white). |
| `fadeDuration` | Tween time for color/scale state changes (default `0` = snap; sprite swaps always snap). |
| `disabled` | Start disabled. |
| `focusable` / `tabIndex` | Keyboard reachability (default `true` / `0`). |
| `onClick(entity)` | Click callback. |

**Handle:** `entity`, `setDisabled(disabled)`, `dispose()`.

Flip a custom state later with `setButtonState(world, handle.entity, 'loading')`.

## Toggle

`createToggle(opts)` composes a button with an on/off check indicator. Returns a
`ToggleHandle`.

```typescript
import { createToggle } from 'esengine';

const toggle = createToggle({
  world, events, parent,
  interactionStates: { normal: { color: /* … */ }, hover: { /* … */ }, pressed: { /* … */ } },
  check: { color: { r: 0.2, g: 0.8, b: 0.4, a: 1 } },   // the "on" indicator
  isOn: true,
  onChange: (isOn, entity) => { /* … */ },
});

toggle.setIsOn(false);      // programmatic change (fires onChange)
toggle.setIsOn(true, true); // silent — skips onChange
```

| Option | Description |
|---|---|
| `interactionStates` | Frame visual states (like the button's `states`; theme defaults when omitted). |
| `check` | The on-state indicator: `{ node?, color?, sprite? }`, shown when on (theme accent by default). |
| `isOn` | Initial state. |
| `onChange(isOn, entity)` | Fires on toggle. |

**Handle:** `isOn()`, `setIsOn(value, silent?)`, `setDisabled(disabled)`, `entity`, `dispose()`.

## Slider

`createSlider(opts)` builds a track + fill + handle. Returns a `SliderHandle`.
Input is built in: **drag** anywhere on the track (press captures until release),
or focus it and use **arrow keys** (`step`, or 1% of the range when continuous),
**Home**/**End**.

```typescript
import { createSlider } from 'esengine';

const slider = createSlider({
  world, events, parent,
  min: 0, max: 100, value: 50, step: 5,
  onChange: (value) => { /* … */ },
});

slider.setValue(75);
```

| Option | Description |
|---|---|
| `min` / `max` / `value` | Range and initial value. |
| `step` | Quantization step (`0` = continuous). Also the keyboard nudge. |
| `handleWidth` | Thumb width in pixels (default `12`). |
| `disabled` / `focusable` / `tabIndex` | Interactivity + keyboard reachability. |
| `trackVisual` / `fillVisual` / `handleVisual` | Per-part visuals. |
| `onChange(value, entity)` | Fires on value change — from input, `setValue`, or any other writer. |

**Handle:** `getValue()`, `setValue(v)`, `dispose()`, plus `trackEntity` /
`fillEntity` / `handleEntity`.

<Aside type="note">
  The state lives in a **`UISlider` component** on the track entity; the behavior
  system is the single writer of the visuals. Anything that writes `UISlider.value` —
  the pointer, the keyboard, `setValue`, the editor inspector on a placed prefab —
  moves the fill and thumb and fires `change` identically.
</Aside>

## Progress

`createProgress(opts)` is a non-interactive fill bar. Returns a `ProgressHandle`.

```typescript
import { createProgress } from 'esengine';

const bar = createProgress({
  world, parent,
  direction: 'right',
  fill: { color: { r: 0.2, g: 0.8, b: 0.4, a: 1 } },
  value: 0,
});

bar.setValue(0.6);   // 0..1

// Radial gauge (cooldown / ring meter) — a clockwise wedge from 12 o'clock:
const ring = createProgress({ world, parent, radial: true, value: 0.75 });
```

| Option | Description |
|---|---|
| `value` | Initial progress, `0..1`. |
| `direction` | Linear fill growth: `'right'` (default), `'left'`, `'up'`, `'down'`. |
| `radial` | Radial gauge instead of a bar — a clockwise wedge sweeping the full circle. Ignores `direction`. |
| `background` / `fill` | Track and fill visuals. |

**Handle:** `value()`, `setValue(v)`, `dispose()`, plus `fillEntity`.

<Aside type="note">
  **One fill primitive.** A progress bar is a single [`UIVisual`](/docs/guides/ui/) in
  **`Filled`** mode — the same primitive the slider's fill is built on, mirroring Unity's
  "health bar = Filled Image". `setValue()` writes `fillAmount`, so the fill is a
  render-time crop with **no per-frame layout pass**, and a sprite fill *reveals* along
  the axis instead of stretching. `direction` resolves to the `Filled` crop axis and
  anchor edge through the shared `FILL_AXIS` table, so progress, slider, and any other
  Filled-based widget fill identically.
</Aside>

## Dropdown

`createDropdown(opts)` shows the current selection and opens a popup of option rows.
It's generic over the option type. Returns a `DropdownHandle<T>`.

```typescript
import { createDropdown } from 'esengine';

const dd = createDropdown({
  world, events, parent,
  options: ['Low', 'Medium', 'High'],
  selectedIndex: 1,
  onSelect: (index, option) => { /* … */ },
});

// Objects need a label mapper:
createDropdown({
  world, events, parent,
  options: resolutions,                       // e.g. { w, h }[]
  optionToLabel: (r) => `${r.w}×${r.h}`,
  onSelect: (i, r) => applyResolution(r),
});
```

| Option | Description |
|---|---|
| `options` | The list of selectable values. |
| `selectedIndex` | Initial selection. |
| `optionToLabel(option, i)` | Map a non-string option to its display text. |
| `buttonStates` / `optionStates` | Colors for the main button and the option rows. |
| `optionHeight` | Row height in pixels (default `32`). |
| `onSelect(index, option, entity)` | Fires on selection. |

**Handle:** `getSelected()`, `getSelectedIndex()`, `setSelectedIndex(i, silent?)`,
`open()`, `close()`, `isOpen()`, `dispose()`.

<Aside type="note">
  Click-outside-to-close isn't wired — call `close()` from your own global input layer
  if you need it.
</Aside>

## Dialog

`createDialog(opts)` is a modal: a click-blocking backdrop with a centered panel,
hidden until opened. Returns a `DialogHandle`. **Add your content as children of
`panelEntity`** — closing sets `display: none` on the backdrop root, so the whole
subtree (your content included) leaves layout, rendering, and input in one write.

```typescript
import { createDialog, spawnUIEntity } from 'esengine';

const dialog = createDialog({
  world, events, parent,
  panelNode: { width: px(420), height: px(260) },
});

spawnUIEntity({ world, parent: dialog.panelEntity, text: { content: 'Are you sure?' } });

dialog.open();
// …later
dialog.close();
```

| Option | Description |
|---|---|
| `backdropNode` / `backdropVisual` | The full-viewport scrim behind the panel. |
| `panelNode` / `panelVisual` | The modal panel (default: 400×300, centered). |
| `startHidden` | Start closed (default `true`). |
| `closeOnEscape` / `closeOnBackdrop` | The standard dismissals — Escape, and a click on the scrim (not the panel). Both default `true`. |
| `onOpenChange(open)` | Fires on every open/close, whoever initiated it. |

**Handle:** `open()`, `close()`, `isOpen()`, `dispose()`, plus `entity` (the
backdrop root) / `panelEntity`.

<Aside type="note">
  Dismissal is data-driven by a **`UIDialog` component** on the backdrop root, and the
  open state IS the root's `UINode.display` — so a dialog instantiated from the editor
  prefab closes on Escape / scrim clicks without any code hookup.
</Aside>

## Lists & collections

For long, scrollable, **data-driven** lists — inventories, leaderboards, chat logs —
`createListView` builds a **virtualized** list (or grid): only the items near the
viewport are ever mounted, so a 10 000-row list stays cheap. One call composes a data
source, a layout, item recycling, scrolling, and clipping.

```typescript
import { createListView, uiPlugin, arrayDataSource, spawnUIEntity, px } from 'esengine';

const list = createListView<Player>({
  world, host: uiPlugin, parent,
  viewportSize: { x: 320, y: 480 },     // the visible window, in pixels
  data: arrayDataSource(players),        // any DataSource<T>, or a raw array
  layout: { itemHeight: 56 },            // a column list
  item: {
    create: (world, parent) => spawnUIEntity({ world, parent, node: { height: px(56) } }),
    bind: (entity, player, index) => { /* fill the row's Text / Sprite from `player` */ },
  },
});
```

`host` is the plugin that ticks virtualization and routes scroll input — pass the
`uiPlugin` your app was built with. `item.create` builds one row entity; `item.bind`
fills it from the data. `bind` runs every time a row is reused for a different index,
so keep it a pure "apply this data" function.

**Layout** is a column, a row, or a grid:

| `layout` | Result |
|---|---|
| `{ itemHeight }` | A vertical list. |
| `{ itemWidth, direction: 'row' }` | A horizontal list. |
| `{ columns, itemSize }` | A grid (a *TileView*). |

**Updating** the list means mutating its data source — an `ArrayDataSource` notifies
the view, which re-syncs on the next frame:

```typescript
list.data.append([newPlayer]);        // add
list.data.remove(3);                   // remove index 3
list.data.update(0, updatedPlayer);    // replace one
list.data.setItems(freshList);         // replace all
```

**Handle:** `data` (mutate it to change the list) · `scrollToIndex(i)` · `refresh()` ·
`mountedCount()` (never grows with the data — handy in tests) · `dispose()`, plus
`scroll` and `view` as escape hatches to the underlying `ScrollContainer` / `ListView`.

<Aside type="note">
  Scrolling works out of the box: mouse wheel over the viewport, and pointer **drag with
  a kinetic fling** — the platform layer funnels the primary touch into the pointer
  stream, so touch scrolling rides the same path. Tune it with `dragScroll: false` or
  `decelerationRate` (fling velocity left after 1s; default `0.135`, the ScrollRect
  standard). For heterogeneous rows, pass a map of item type → template instead of one
  `item`, and give the data source a `getItemType(i)`.
</Aside>

### Free-form scrolling

For a scrollable panel of **arbitrary content** (a settings page, a long form) — no
virtualization, no data source — use `createScrollView` and parent anything under its
`content` frame:

```typescript
import { createScrollView, uiPlugin } from 'esengine';

const panel = createScrollView({
  world, host: uiPlugin, parent,
  viewportSize: { x: 320, y: 480 },
  contentSize:  { x: 320, y: 1200 },
});
// build your content under panel.content …
panel.scrollTo({ x: 0, y: 300 });
```

Wheel, drag/touch, and the kinetic fling work exactly as in the list view; call
`setContentSize()` after the content grows.

## Text input

`createTextInput(opts)` builds an editable field — background, caret, placeholder,
and IME plumbing included — with theme-role colors that re-resolve on a theme swap.
Returns a `TextInputHandle` (`getValue()` / `setValue(v)` / `entity` / `dispose()`).

```typescript
import { createTextInput } from 'esengine';

const name = createTextInput({
  world, events, parent,
  placeholder: 'Your name', maxLength: 20,
  onChange: (value) => { /* value edited */ },
  onSubmit: (value) => save(value),   // Enter
});
```

The factory is sugar over the `TextInput` **component** — insert that directly on any
UI entity for full manual control:

```typescript
import { spawnUIEntity, TextInput, px } from 'esengine';

const field = spawnUIEntity({ world, parent, node: { width: px(240), height: px(32) } });
world.insert(field, TextInput, { placeholder: 'Your name', maxLength: 20 });

events.on(field, 'change', () => { /* value edited */ });
events.on(field, 'submit', () => save(world.get(field, TextInput).value));  // Enter
```

| Field | Default | Description |
|---|---|---|
| `value` / `placeholder` | `''` | Content / hint shown while empty. |
| `maxLength` | `0` | Character cap (`0` = unlimited). |
| `multiline` | `false` | Enter inserts a newline instead of submitting. |
| `password` | `false` | Mask the characters. |
| `readOnly` | `false` | Focusable but not editable. |
| `fontSize` / `fontFamily` | `16` / `Arial` | Text style — `color`, `placeholderColor`, `backgroundColor`, and `padding` (`6`) round out the look. |

Click (or Tab to) the field to focus it; **Escape** blurs, **Enter** fires
`submit` on single-line fields.

<Aside type="note">
  Text input runs in **play mode only** and needs a browser DOM (it drives a
  hidden native textarea for IME support) — it's inert in the editor's edit view.
</Aside>

## Drag & drop

Add `Draggable` to any interactable UI entity and pointer drags move it — its
absolute `UINode` insets when it has one, otherwise its `Transform`:

```typescript
world.insert(entity, Draggable, { dragThreshold: 5, lockY: true });
events.on(entity, 'drag_start', () => { /* also 'drag_move' and 'drag_end' */ });
```

`lockX` / `lockY` constrain the axis and `constraintMin` / `constraintMax` clamp
the range; the auto-inserted `DragState` component exposes the live drag
(`isDragging`, `deltaWorld`, `totalDeltaWorld`, …). There's no built-in
drop-target concept — decide what the drop hit in your `drag_end` handler.

## Keyboard focus

Entities with a `Focusable` component participate in keyboard focus: **click**
focuses, **Tab / Shift+Tab** cycles (ordered by `tabIndex` ascending, skipping
disabled widgets, wrapping at the ends), **Enter / Space** activates the focused
control (a synthesized `click`; text fields keep those keys for editing), sliders
take the **arrow keys**, and **Escape** or a click on empty space clears focus.
Widget factories add `Focusable` automatically (`focusable: false` opts out); a
focused control shows its `focused` interaction page (theme hover color by
default). The `FocusManager` resource exposes `focusedEntity` plus
`focus(entity)` / `blur()` for programmatic control, and focused entities
receive `focus` / `blur` events on the UI event bus.

## Safe area (mobile notches)

Add `SafeArea` to a full-screen, absolutely-positioned `UINode` container and its
insets track the platform safe area — device notches, rounded corners, the WeChat
capsule — so children laid out inside never hide under hardware. `applyTop` /
`applyBottom` / `applyLeft` / `applyRight` (all default `true`) pick which edges
apply.

## Theming

Widget colors come from a shared token set: `getTheme()` / `setTheme(tokens)`
with roles like `surface`, `control`, `controlHover`, `primary`, `onPrimary`,
`track`, and `backdrop` (`DARK_TOKENS` / `LIGHT_TOKENS` are built in). `setTheme`
affects widgets constructed afterwards; **`switchTheme(world, tokens)`** also
live-restyles everything already on screen — widgets record which theme *role*
each color came from (a `ThemeStyle` component, carried into prefabs too), so a
swap re-resolves hues while preserving each color's alpha.

## Editor prefabs

The same widgets ship as editor prefabs, so **Create… → UI** drops a ready-made
Button, Toggle, Slider, Dialog, TextInput, and so on into the scene, which you then
edit in Details. Behavior that lives in components — a slider's drag/keys, a
dialog's Escape/scrim dismissal — works on placed prefabs without code. See
[The Editor](/docs/guides/editor/).
