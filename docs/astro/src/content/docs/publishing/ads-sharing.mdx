The `Ads`, `Share`, `Recorder`, `Leaderboard`, `Identity` and `Payment` services wrap mini-game host APIs. Each
service exists on every platform and reports what the current platform supports through `available`, so gameplay code
checks capability instead of branching on the platform.

| Service | Package | Mock in Play mode |
|---|---|---|
| `Ads` | `esengine` | Yes |
| `Identity` | `esengine` | No |
| `Share`, `Recorder`, `Leaderboard`, `Payment` | `estella-plugin-minigame-services` | `Recorder` records; `Leaderboard` renders locally; `Share` and `Payment` report unavailable |

## Rewarded ads

`Ads.showRewarded(adUnitId)` shows a rewarded video and resolves, after the ad has closed and the game is running
again, with whether the reward was earned:

```typescript
import { defineSystem, Res, GetWorld, Ads } from 'esengine';

const reviveSystem = defineSystem([Res(Ads), GetWorld()], (ads, world) => {
  if (!reviveClicked(world)) return;
  ads.showRewarded('adunit-xxxx').then(({ completed }) => {
    if (completed) revivePlayer(world);   // watched to the end → grant the reward
    else showToast(world, 'Watch the whole ad to revive');
  }).catch(() => {
    showToast(world, 'No ad available right now');
  });
}, { name: 'ReviveSystem' });
```

While the ad is shown, the service:

- pauses the game clock;
- suspends the audio device without changing any user volume;
- restores both however the ad ends, including on every error path. A game paused before the ad stays paused.

The host's load/show sequence (an ad with no fill is loaded and retried once) is handled internally. On runtimes that
grant a reward without reporting `isEnded`, an absent close record counts as completed.

| Method | Description |
|---|---|
| `Ads.showRewarded(adUnitId)` | Shows a rewarded ad; resolves with `{ completed }`. |
| `Ads.showInterstitial(adUnitId)` | Same contract without the reward. |
| `Ads.preloadRewarded(adUnitId)` | Loads a unit in advance so the next show starts immediately. |

<Aside type="tip">
The `adUnitId` comes from the host's ad console (WeChat: 流量主 → ad units in the MP dashboard). Ads serve only in a
game with monetization enabled there; the DevTools simulator shows a test ad.
</Aside>

### Availability

`Ads.available` is `true` where an ad source exists — the platform's or an installed provider:

| Platform | Ad source |
|---|---|
| Mini-games (WeChat, Douyin and the other family hosts) | The host's rewarded and interstitial ads. A vendor whose host has no ad API reports `false`. |
| Web on a portal channel | Poki, CrazyGames and YouTube Playables install their own provider ([Web Portals](/docs/publishing/web-portals/)). |
| Editor Play mode | A mock provider: `showRewarded` resolves `completed: true` after a moment, with the real pause and audio handling. |
| Android, iOS | The project's native ad SDK, once its code answers `ads.show` ([Native Code](/docs/publishing/native-code/#ads)). |
| Standalone web, desktop | None; `false`. |

## Sharing

Sharing, recording, the leaderboard and in-game purchase are provided by the `estella-plugin-minigame-services`
package. The editor carries the package, so it can be imported in Play and in every export without installation; a
copy installed in the project's own `node_modules` takes precedence.

```typescript title="src/main.ts"
import { addPlugin } from 'esengine';
import { miniGameServicesPlugin } from 'estella-plugin-minigame-services';

addPlugin(miniGameServicesPlugin);
```

A mini-game host has two share surfaces; configure both:

```typescript
import { defineSystem, addStartupSystem, Res } from 'esengine';
import { Share } from 'estella-plugin-minigame-services';

addStartupSystem(defineSystem([Res(Share)], (share) => {
  // The DEFAULT card: what the host's own share menu (top-right on WeChat)
  // shows, and what share() without arguments uses. A function is asked at
  // share time, so the card can carry live state — a score, a room code.
  share.setShareCard(() => ({
    title: `I scored ${currentScore()} — beat me!`,
    query: `room=${currentRoomCode()}`,
  }));
}, { name: 'SetupShare' }));

// In the game's own share button handler (share is Res(Share) as above):
share.share();                          // the default card
share.share({ title: 'Join my game' }); // or a one-off card
```

| Surface | Configured by |
|---|---|
| The host's own share menu | `setShareCard(card \| () => card)`; also the default for `share()`. |
| The game's share button | `share(card?)`. |

The player who opens a shared card receives `query` in the host's launch options; invite links and room codes travel
this way.

Sharing is fire-and-forget: mini-game hosts do not report whether the player completed a share. Off-platform (web,
native, the editor), `Share.available` is `false` and `share()` returns `false`; hide the button.

## Recording a clip

`Recorder` (same package) records the game canvas for sharing:

```typescript
import { Recorder } from 'estella-plugin-minigame-services';

// When the run starts (recorder is Res(Recorder)):
if (recorder.available) await recorder.start();

// When something worth keeping just happened — a kill, a near miss:
recorder.highlight(3, 2);   // keep 3s before now and 2s after

// When the run ends:
await recorder.stop();

// In the "share my run" button's tap handler — both hosts refuse a share
// the player did not tap for:
if (recorder.canShare) await recorder.share({ title: 'Look at this run' });
```

With highlights, the shared clip is the highlights in order; without, it is the whole recording. Every call resolves
when the host confirms the action and rejects with the host's reason (and `code`, where given). A recording the host
ends with an error is reported through `recorder.onFailure(...)`, and `state` returns to `'idle'`.

| | WeChat | Douyin | Editor / web |
|---|---|---|---|
| Length (`maxSeconds`) | 5–7200 s | 4–300 s | Any |
| `stop()` result | The duration; WeChat keeps the video | A temporary file (`path`) | A WebM preview (`blob`) |
| Shared clip | At most 60 s of highlights, at least 2 s | The highlights, merged | Cannot share |

`maxSeconds` defaults to 300 and is clamped to the host's range. Only the game canvas is recorded; ads and host
dialogs over it are not.

<Aside type="caution">
Douyin's developer tools do not support recording ("开发者工具不支持录屏调试，请在真机上调试录屏相关功能"). WeChat
shares a recording from WeChat 8.0.28 on Android and 8.0.30 on iOS; where the host has no share call, `canShare` is
`false`.
</Aside>

In Play mode the recording is real: `stop()` returns the canvas as WebM. `canShare` is `false`, so a share button
hides as it would on a host that cannot share. The `record-share` example demonstrates the complete flow.

## Friends leaderboard

On a mini-game host, friends' data can be read only inside the **open data context**: a second JavaScript runtime the
host starts beside the game, with no engine, WebGL or wasm, and no channel back to the game. The leaderboard is drawn
there and reaches the game as a texture.

```typescript
import { UIVisual } from 'esengine';
import { miniGameServicesPlugin, Leaderboard } from 'estella-plugin-minigame-services';

addPlugin(miniGameServicesPlugin);
const leaderboard = app.getResource(Leaderboard);

// Your half: write your own row. It is the one cloud operation the game
// itself may do — reading anyone's, including your own, belongs to the context.
leaderboard.submit(score);

// Ask the context to draw. This is a request, not a question: no rows come
// back, no count, no "did it work".
leaderboard.show({ limit: 10, order: 'desc' });

// What it drew, as a texture handle any UIVisual can wear.
world.get(panel, UIVisual).texture = leaderboard.texture;

leaderboard.hide();   // clears the board and stops sampling
```

| Member | Description |
|---|---|
| `submit(score)` | Writes the player's own row — the only cloud operation the game itself may perform. |
| `show(options)` | Requests a draw. Returns no rows or status. Options: `limit`, `order`, `style` (colours, row height, font size, avatars). |
| `texture` | The drawn board, as a texture handle for any `UIVisual`. |
| `hide()` | Clears the board and stops sampling. |
| `available` | `false` where there is no context: web, native, and packages that declare none. |

The board ranks rows, emphasizes the player's own row, and omits friends who have never played. The canvas has a
fixed size and **cannot scroll** — no pointer or key events reach the context — so `limit` is the number of rows
that fit.

### Open data context file

The project owns the context directory; the package supplies its content:

```typescript title="open-data/index.ts"
import 'estella-plugin-minigame-services/open-data';
```

The exporter bundles `open-data/` separately and names it in `game.json`. A project without the directory ships no
context, and `available` reports `false`.

To draw a custom board, write the file without importing the package. It runs in the context, so it must **not import
`esengine`**; the export and entering Play both fail if it does. The context provides a 2D canvas from
`wx.getSharedCanvas()`, `wx.getFriendCloudStorage()`, and `wx.onMessage()` carrying the options sent by `show()`.

### Play mode

Play mode runs the project's `open-data/index.ts` against an offscreen canvas with generated placeholder friends, and
answers `Leaderboard` through the same capabilities a device uses. `submit()` reaches it, so the player's row moves.
Real friends and the host sandbox can be checked only on a device.

## Signing in

A mini-game host signs the player in and returns a **one-time code**. Exchanging the code for an identity requires the
app secret, which must stay on the game's server; the engine's role ends at the code.

```typescript
import { defineSystem, Res, Identity } from 'esengine';

if (!identity.available) return;             // web, native, the editor

// Skip the round trip when the session your server holds is still good.
if (await identity.sessionValid()) return;

const { code } = await identity.login();     // a CODE, not a session
const session = await postToYourServer('/session', { code });
```

| Member | Description |
|---|---|
| `available` | Whether the platform has sign-in. |
| `sessionValid()` | Whether the host session is still valid. |
| `login()` | Resolves with `{ code }`. Rejects with the host's message when sign-in fails, and immediately where the platform has no sign-in. |

The code is short-lived and single-use: cache the session the server returns, never the code. Play mode has no mock
for sign-in, because a placeholder code cannot be exchanged by any server; `available` is `false` off-platform.

## In-game purchase

In-game purchase is a device permission. On WeChat it is Android-only: the call exists on iOS and the platform refuses
it. `Payment.available` therefore reports for the **device**; check it before opening a shop.

```typescript
import { defineSystem, Res } from 'esengine';
import { Payment } from 'estella-plugin-minigame-services';

if (!payment.available) return;   // iOS, web, native — do not open the shop

try {
  await payment.request({ offerId: 'your-offer-id', quantity: 10 });
  // The HOST says the purchase completed. Now ask YOUR server what the player
  // owns — do not add the coins here.
  await refreshInventoryFromYourServer();
} catch (err) {
  // The host's own message and code, including "the player changed their mind".
  // Those are different UI, and only the host can tell them apart.
  if ((err as { code?: number }).code === /* your host's cancel code */ 2) return;
  showPurchaseFailed(err);
}
```

`request()` options: `offerId`, `quantity`, `sandbox: true` while developing the flow, and `zoneId` for games with more
than one server.

- The service **does not interpret host error codes**; they differ between vendors and are passed through unchanged.
- The service **grants nothing**. The host notifies the game's server, which grants currency; a resolved `request()`
  is the signal to query the server.
- Play mode has no mock for purchases.
