The **Android** and **iOS** targets package the project as a native app: the engine's C++ core compiled for arm64,
rendering through an embedded [Dawn](https://dawn.googlesource.com/dawn) (WebGPU on **Vulkan** on Android, on **Metal**
on iOS). Game scripts run on an embedded JavaScript engine — [V8](https://v8.dev/) with its JIT on Android,
[QuickJS-ng](https://github.com/quickjs-ng/quickjs) on iOS, where a JIT is not permitted. The app contains no WebView
or browser.

Scenes, components and TypeScript are the same as on every other target; a project needs no mobile-specific content.

## Targets

Android and iOS are separate targets because their outputs and assembly hosts differ. They share one runtime and one
export payload: the engine, the SDK and the game runtime are in the app binary, and the export writes app **content**
— scenes, scripts and cooked assets.

| | Android | iOS |
|---|---|---|
| Graphics | Vulkan (via Dawn) | Metal (via Dawn) |
| Export folder | `dist-android/` | `dist-ios/` |
| Assembled by | The editor (no Android SDK) | The editor, then Xcode |
| Assembly host OS | Any desktop OS | macOS only |
| Result | A signed `.apk` (optionally with an `.aab`), or an Android Studio project | An Xcode project |

## Device requirements

| | Android | iOS |
|---|---|---|
| Minimum OS | **Android 10** (API 29) | **iOS 17.0** |
| Target API | 33 | — |
| CPU | `arm64-v8a`; `x86_64` (emulator) only when requested | arm64 device and simulator slices |
| GPU | **Vulkan 1.0.3**, declared `required="true"` | Metal |

- The Android minimum is API 29 because the font path calls `AFontMatcher_create`, which requires API 29.
- The Vulkan requirement follows from Dawn's Android backend; there is no GLES fallback. Because it is declared in the
  manifest, Google Play does not offer the app to devices without Vulkan.
- An Android package carries the phone ABI only. **Include the emulator (x86_64)** in the Android target settings, or
  `--emulator-abi` on the command line, adds the emulator libraries; leave it off for release builds.

## Prerequisites

<Steps>

1. **Install the runtime template.** The template is the prebuilt engine for the target, published with each release.
   The target's row in Package Project offers **Download**, or **Install from file…** for an archive obtained
   separately. The template must match the editor version exactly, because the SDK is compiled into the app binary.

   :::tip[Download source]
   Releases are mirrored to `dl.estella.games`, which the editor tries before the origin. Every archive is checked
   against the size and SHA-256 stated by the release index; a missing, stale or mismatched copy falls back to GitHub.
   `ESTELLA_RELEASE_MIRROR` sets other mirrors (comma-separated, tried in order); each mirror lays out a version as the
   release does, under `v<version>/`.
   :::

2. **Install the platform toolchain (iOS only).**
   - *Android*: none. The APK is compiled, aligned and signed by the editor on any OS; no Android SDK, NDK or JDK is
     needed.
   - *iOS*: **macOS with Xcode**. No CMake, Ninja, xcodegen or Dawn checkout is needed. On other operating systems the
     export still writes a complete project that can be opened on a Mac.

3. **Check the dialog.** The target's row shows a warning until its prerequisites are met, and the panel names what
   is missing.

</Steps>

A project with `@compiled` systems also needs the **Android NDK** on the exporting machine for Android
([Script execution](#script-execution)).

## Exporting

<Steps>

1. **Build → Package Project…**, then select **Android** or **iOS** under **Mobile**.
2. Choose a configuration and an output folder (`dist-android` / `dist-ios` by default). Source maps are not offered.
3. Review **Scenes in build**.
4. Click **Package**. The export cooks assets, bundles scripts, writes the content and an `app.config.json` with the
   app's identity, and assembles the app around it.

</Steps>

| Output | Contents |
|---|---|
| **Android**, *Package as: Installable package (.apk)* | A signed `.apk`, ready for `adb install -r`. With **Google Play App Bundle (.aab)** ticked, an `.aab` is written beside it; the bundle is the Google Play upload format and cannot be installed on a device. |
| **Android**, *Package as: Android Studio project* | A Gradle project: content under `app/src/main/assets`, the engine under `app/src/main/jniLibs`, the host's Java shim as source, and `app/build.gradle.kts` with the app's identity. Open it in Android Studio and run. A re-export rewrites the game and leaves the build script unchanged, so SDKs added to `build.gradle.kts` persist. |
| **iOS** | An Xcode project: the `.xcframework`, the app shell and a generated `.pbxproj` around the content. Open it, select a signing team under *Signing & Capabilities*, and run. |

The app binary is identical for every game and an export is content only, so assembly copies files and writes project
files; no compiler is involved.

### Android signing

| Build | Signed with |
|---|---|
| Development | A development key the editor generates on first use. Accepted by devices, refused by stores. |
| Shipping | The project's release key, when set: **Release private key** and **Release certificate** (PEM, project-relative or absolute) in the Android target's signing group. The two are checked against each other before signing. **Release key passphrase** is stored in the machine's keychain; the CLI reads `ESTELLA_ANDROID_KEY_PASSPHRASE`. |

Keep the release key out of the project's repository. An app can also be assembled from an export with
`node build-tools/cli.js native --package --content dist-android`, passing `--key` / `--cert` (and `--passphrase`) to
sign with a specific key, and `--aab` to write a bundle.

### Native libraries

**Compress native libraries** (Android target settings, on by default) deflates the native libraries in the APK: an
empty project downloads as about 20 MB instead of 54 MB, and Android extracts the libraries once at install. Off, the
libraries are stored for the system to map in place: about half the installed size, nearly three times the download.
The App Bundle always stores them; Google Play compresses what it delivers.

## App identity

The following settings are written into `app.config.json` beside the content, not into `game.config.json`, which the
runtime reads:

| Setting | Location | Effect |
|---|---|---|
| **App Icon** | Settings → Project → Build and modules → Packaging | One project-relative square PNG (1024×1024 recommended). Android uses it as the launcher mipmap, iOS as the asset catalog from which Xcode derives every size. Empty ships the Estella mark. |
| **Application ID** | Same | The Android manifest package and the iOS bundle id (reverse-DNS). Empty derives one from the project name. |
| **Android Version Code** | Android target settings | The integer Google Play orders builds by; it must increase with every upload. The user-visible version comes from the project version. |
| **Orientation** | Settings → Project → Game → Display | Project-wide; unset follows the design resolution's aspect. |

## Engine subsystems on device

The mobile targets compile the whole engine source list. The subsystems that are separate side modules on the web
(Box2D, the Spine runtimes, the MPEG-1 video decoder) are compiled into the app binary. `app.sideModules` still
reports them, so runtime feature checks behave as in a browser.

| Subsystem | On device |
|---|---|
| Sprites, tilemaps, particles, post-processing | Native (Dawn) |
| Text, bitmap text, rich text | Same atlas and layout as the web; glyphs rasterized from the OS font |
| Physics (Box2D) | Compiled in; solved across worker threads |
| Spine | Compiled in, every version; see [Spine runtimes](#spine-runtimes) |
| DragonBones | Compiled in, one runtime |
| Video | Compiled in (cooked at build, decoded on device) |
| Audio | Native mixer ([miniaudio](https://miniaud.io/)) on CoreAudio / AAudio |
| Text input | The platform's soft keyboard is the field's editing surface |
| Networking | The OS network stack (`NSURLSession` / `HttpURLConnection`) |
| Terrain and streamed worlds | Supported. Terrain layer textures are passed to the device as bytes, and a chunked world's maker uses its own cancellation handle, because the native runtime has no `AbortController`. |
| Compressed textures | KTX2 transcoded to the device format (ASTC, ETC2, BC), with mip chains |
| Lifecycle | `onShow` / `onHide` and OS memory warnings reach the app |

If a future build omits a subsystem, the export names it and the scenes that use it.

### Spine runtimes

A native app reads Spine 2.1, 3.8, 4.1, 4.2 and 4.3. Each skeleton is read by the runtime of the version it was
exported from, so a project can mix versions; the Spine version in Project Settings is only a preference. The runtimes
define the same C names, so the host compiles each under its own prefix. On Android each version is a separate
library (0.2–1 MB per ABI) and the export includes only those the packaged skeletons need. On iOS and desktop all
versions are linked into the app (about 1 MB).

Which runtimes a package carries is decided the same way for web, playable, mini-game and Android packages. Project
Settings → Spine has a row per runtime:

| Value | Behaviour |
|---|---|
| **Auto** (default) | Carried when a packaged skeleton was exported from it. |
| **Include** | Always carried. Use for skeletons only code loads (a path built at run time, content fetched later). |
| **Exclude** | Never carried. If a packaged skeleton needs it, the export fails and names the skeleton. |

The export result lists each runtime and why it was carried or left out. A runtime template from an older release
carries a single Spine version; packaging with it lists every skeleton the template cannot play. Install the
template for the current editor version to resolve it.

## Assets on device

- **Assets referenced only from code are culled.** A build ships what is reachable from the scenes in the build.
  Mark folders referenced only by code with **Delivery → Always include in builds** in the Content Browser, which
  writes `alwaysInclude` into `.esengine/asset-groups.json`:

  ```json
  {
    "version": "1.0",
    "groups": {
      "markup-images": {
        "folder": "assets/textures",
        "mode": "local",
        "alwaysInclude": true
      }
    }
  }
  ```

  It is off by default. See [Assets](/docs/assets/overview/#shipping-what-only-code-names).
- **Per-platform texture settings.** Import Settings have a tab per platform, including the mobile targets, so a
  texture can be compressed harder for a phone without changing the source.

## Script execution

| | Android | iOS |
|---|---|---|
| Engine | V8 with JIT (`libv8android.so` per ABI) | QuickJS-ng interpreter |
| Language support | ICU data for `Intl` and Unicode regular expressions (`/\p{L}/u`); `TextEncoder` / `TextDecoder` provided by the host | — |
| `@compiled` systems | Cross-compiled with the Android NDK for each 64-bit ABI in the package and shipped in `lib/<abi>/` | Interpreted |
| SDK bundle at first launch | Compiled at launch and cached in the app's cache | Precompiled bytecode shipped with the app |

- **Android `@compiled` systems** run as machine code from the first frame. The NDK must be installed on the
  exporting machine (Android Studio's SDK Manager, or `ANDROID_NDK_HOME`); the Package dialog reports it when the
  project has compiled systems and the NDK is missing. A system the host cannot bind runs in the interpreter for that
  frame.
- **iOS** interprets every script. Per-entity loops written in TypeScript cost more than in a browser; prefer engine
  systems and bulk APIs in hot paths.
- **iOS first launch.** The SDK bytecode is built with the app, so a fresh install reaches its first frame without
  parsing the bundle. A build machine without a C compiler cannot produce it; the app then compiles on first run,
  which takes about ten seconds on that launch only.

The boot record ([Boot diagnostics](#boot-diagnostics)) states which applied — `SDK bundle: loaded from the cache
shipped with the app` or `bundle: no compile cache` — and its first lines name the engine (`engine: V8 …` or
`engine: QuickJS-ng …`).

## Boot diagnostics

Every launch writes a boot record:

```
Android   Android/data/<your.package.id>/files/estella-boot.log
iOS       the app's Documents directory
```

The previous run is kept as `estella-boot.prev.log`.

```
estella boot record — 2026-07-29 19:07:38
device: 24129PN74C, Android 16, arm64-v8a
phase: gpu device
gpu: qualcomm Adreno (TM) 830 (adreno-8xx) — Adreno Vulkan Driver 512.800.71
phase: surface
phase: engine context
phase: js runtime
  SDK bundle: loaded from bytecode shipped with the app
phase: game script
ready in 105 ms
```

The last `phase:` line of an unfinished launch is where it stopped; a completed launch ends with `ready in`. A native
crash appends the signal, the phase and the return addresses:

```
FATAL SIGSEGV (bad memory access) during phase: js runtime
backtrace (symbolize against this version's unstripped libestella_js_host.so):
  0x7b41e2632c  /data/app/.../libestella_js_host.so+0x1e32c
```

Resolve the addresses against the **unstripped** `libestella_js_host.so` of the same engine version
(`llvm-addr2line -e libestella_js_host.so 0x1e32c`); the copy in the APK is stripped.

Reading the record from an Android device:

```bash
adb shell cat /sdcard/Android/data/<your.package.id>/files/estella-boot.log
adb pull /sdcard/Android/data/<your.package.id>/files/estella-boot.log
```

<Aside type="caution">
  Since Android 11, an app's `Android/data` directory is not accessible to file managers or the system Files app.
  `adb shell` can read it because its user is in the `ext_data_rw` group.
</Aside>

After a crash, the next launch copies the record to `Android/media/<your.package.id>/` (falling back to
`Download/`), where file managers can reach it, as `estella-crash-<date>.log`. The new run's record states the path:

```
previous run CRASHED; its record was copied to
  /storage/emulated/0/Android/media/com.example.game/estella-crash-20260729-190738.log
```

To collect a crash report from a player: open the game once more, then send the newest `estella-crash-*.log` from that
folder. Only crashes are copied.

While a device is attached, the same lines appear in `logcat`:

```bash
adb logcat --pid=$(adb shell pidof <your.package.id>)
```
