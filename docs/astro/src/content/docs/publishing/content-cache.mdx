title: Device Disk Cache
description: The on-device disk cache of hot-updated assets — where it exists, the Profiler's Device disk cache section, protected and reclaimable bytes, version labels, keeping a version, and cleaning the cache to a budget.
---

A game that loads [Remote content](/docs/publishing/hot-update/) writes verified bytes to a **disk cache** on the
device, so updated assets load without the network at the next launch. Each update leaves the previous revision's
files behind, so the cache grows over time. The Profiler's **Device disk cache** section shows what is stored and what
can be removed, and cleans the cache to a budget without deleting a revision the game may still need.

## Platform support

| Target | Disk cache |
| --- | --- |
| **Desktop** | Managed: can be listed, measured and cleaned. |
| **Mini-games**, **Native (iOS, Android)** | Managed when the host's file API can list and delete files; otherwise storage only. |
| **Web** | None. The next launch refetches from the CDN. |

The section reports the connected host's state:

| State | Meaning |
|---|---|
| **Managed** | All controls below are available. |
| **Storage only** | The host stores cache bytes but cannot list or safely delete them; usage is not available. |
| **Unavailable** | The platform has no managed disk cache. |

## Opening the section

With a device connected to the editor, open the **Profiler** and set **Profiler source** to **Device**. The **Device
disk cache** section appears under the device's controls. It is read once when the device is selected; directory scans
are not polled, so use **Rescan** to refresh.

## Summary

The summary line has the form *Resources · protected · reclaimable · index*:

| Figure | Meaning |
|---|---|
| **Resources** | Bytes of cached assets on disk. |
| **Protected** | Bytes the game may still need: files of a protected version, and files whose owner is unknown. |
| **Reclaimable** | All other bytes; the only bytes a cleanup can free. |
| **Index** | The cache's bookkeeping file, counted separately. |

## Versions

Below the summary, one row per version the cache knows lists its revision, why it is kept, and how many of its files
are missing from disk:

| Label | Meaning |
| --- | --- |
| **Current** | The revision the game is running. |
| **Pending** | An update that was found and staged but not committed. |
| **Rollback** | The previous revision, kept so a failed update can fall back. |
| **Next launch / retained** | A revision kept by request. |
| **Old version** | Unprotected; its files are reclaimable. |

Files of unknown ownership (written before the cache tracked ownership) are protected until a verified write
establishes their owner. Saves are always excluded from cleanup.

## Keeping a version

On the running build's versions, **Keep version** reserves a revision — for example the build under QA — so that
advancing the current/rollback pair does not release it. **Release reservation** removes the reservation. Retention is
stored separately from automatic protection, so an update never drops a reserved revision.

## Cleaning to a budget

1. Set **Resource budget** in MiB (default 128).
2. **Preview cleanup** shows how many files and bytes would be released, without deleting anything.
3. **Clean unprotected resources** deletes them, least recently used first, until the cache fits the budget, and
   reports the bytes released and any failed deletions.

Only unprotected files are candidates. If the protected files alone exceed the budget, the panel reports it and keeps
them. If the cleanup freed space but could not store the updated index, the panel reports it; the next scan reconciles
the index.
