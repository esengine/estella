A **hot update** replaces assets of a shipped game — textures, sounds, prefabs — with new versions served from a
**CDN**. Running clients download only the changed assets; the package is not re-downloaded and the store build is
not resubmitted.

Hot update is **content-addressed**, **atomic** (all-or-nothing, with rollback), **integrity-checked** (bytes that do
not match their hash are rejected) and **transparent to game code** (a built-in rebinder swaps new assets into live
components). The same mechanism runs on Web, Desktop, mini-games and native apps.

<Aside type="tip">
  The [`hot-update-demo`](https://github.com/esengine/estella/tree/master/examples/hot-update-demo) example shows the
  complete flow on a single sprite with no game code.
</Aside>

## How it works

Every cooked asset ships as `<contentHash>.<ext>`, an immutable, permanently cacheable URL. Changing the file bytes gives the asset a new hash and URL. Changing a sampler or nine-slice border keeps the same image URL.

<Steps>

1. **Fetch** the remote manifest (`asset-manifest.json`) from the CDN.
2. **Compare** its file hashes, delivery locations and runtime settings with the active manifest.
3. **Download and verify** files listed in `downloadFiles`.
4. **Activate** the manifest. Live texture bindings pick up the new image or settings.

</Steps>

A settings-only update has `hasUpdate: true` and `totalBytes: 0`. Call `applyUpdate` to use the settings and persist them for the next launch.

## Delivery groups

Whether an asset ships inside the package or is served from a CDN is set per folder by its **delivery group**. Every
folder resolves to one of three modes:

| Mode | Bundle | Badge | Ships | Use for |
| --- | --- | --- | --- | --- |
| **Local** | eager | — | Inside the package, loaded at boot | Core game assets |
| **Subpackage** | lazy | `PKG` (purple) | Inside the package, loaded on demand | Large optional content, [WeChat subpackages](/docs/publishing/wechat/#subpackages) |
| **Remote** | remote | `CDN` (blue) | From a CDN; **hot-updatable** | Content to change after release |

Only **Remote** groups are hot-updated. Local and Subpackage assets are part of the build; subpackages load on demand
from within the package ([Assets → Addressable groups](/docs/assets/overview/#addressable-groups-lazy-loading)).

### Marking a folder for CDN delivery

In the **Content Browser**, right-click a folder and choose **Delivery → Remote (CDN / hot-update)**. Every asset in
the folder, recursively, then ships from the CDN.

![Right-clicking a folder in the Content Browser and choosing Delivery → Remote (CDN / hot-update)](@/assets/guides/en/hot-update-delivery-menu.png)

*Content Browser → right-click a folder → **Delivery** → **Local / Subpackage / Remote (CDN / hot-update)**. The
choice is written to `.esengine/asset-groups.json`.*

The same submenu contains **Always include in builds**, an independent toggle that keeps the folder in a build even
when nothing in it is reachable from a scene ([Assets](/docs/assets/overview/#shipping-what-only-code-names)).

A folder assigned to a Subpackage or Remote group shows a corner badge: `CDN` (blue) for remote, `PKG` (purple) for
subpackage.

![A folder tile in the Content Browser showing the blue CDN delivery badge](@/assets/guides/en/hot-update-cdn-badge.png)

*The `cdn` folder carries the blue **CDN** badge: its assets are delivered remotely and can be hot-updated.*

Delivery is independent of the folder name. When a project has no `asset-groups.json`, a folder named `remote/<name>/`
or `subpackages/<name>/` still implies its delivery mode.

### CDN root

Remote-group assets are fetched from a **root URL** on the CDN. The root is a project packaging setting
(`packaging.remoteRoot` in `project.esproject`), and an **export profile** can override it, so test and production
builds can use different CDNs. The export writes the resolved root into the shipped game. Set it in **Build → Package
Project… → Advanced → CDN root**:

![The Package dialog's Advanced group — the CDN root field, source maps, and open-output-folder](@/assets/guides/en/hot-update-build-cdn.png)

*The **CDN root** field writes the project's `remoteRoot`, or the selected profile's. Empty loads remote assets from
the game's own origin (for example for local testing).*

```json
{
  "packaging": {
    "remoteRoot": "",
    "profiles": {
      "prod-web": { "platform": "web", "config": "shipping", "remoteRoot": "https://cdn.example.com/my-game" }
    }
  }
}
```

`estella export --profile prod-web` (or selecting **prod-web** in the dialog) builds with the production root; other
builds use the project's root.

### `.esengine/asset-groups.json`

Delivery groups and atlas groups are stored in one authored file. The cook and the editor's Play realm read it through
the same resolver.

```json
{
  "version": "1.0",
  "groups": {
    "cdn": { "folder": "assets/cdn", "mode": "remote" }
  },
  "atlases": {
    "ui": { "folder": "assets/art/ui" }
  },
}
```

| Field | Type | Description |
| --- | --- | --- |
| `version` | `string` | Config version (`"1.0"`). |
| `groups` | `Record<name, {folder, mode}>` | Folder-to-delivery assignments. |
| `groups.<name>.folder` | `string` | Project-relative folder; every asset under it, recursively, joins the group. When folders nest, the longest matching prefix wins. |
| `groups.<name>.mode` | `'local' \| 'subpackage' \| 'remote'` | Delivery mode. |
| `groups.<name>.alwaysInclude` | `boolean` | Ship the group even when nothing in the build reaches it — for assets named only in code (a URL, a path, rich-text markup). Default `false`. See [Assets](/docs/assets/overview/#shipping-what-only-code-names). |
| `atlases` | `Record<name, {folder}>` | Folders whose textures pack into one atlas page (with **Pack atlases** ticked). Independent of `groups`: an atlas may span two delivery groups and a group may hold two atlases. Absent, the `<name>.atlas/` folder convention applies. |
| `atlases.<name>.folder` | `string` | Project-relative folder; eligible PNGs under it pack into this atlas. Mesh textures keep their own files. The longest matching prefix wins. |
| `activeProfile`, `profiles` | — | Legacy location of the CDN root, read only while the project sets no `packaging.remoteRoot`. |

## Shipped files

Every Web, Desktop, mini-game and native export writes **`asset-manifest.json`** (the addressable manifest) next to
the game; clients diff against it. When the build has a CDN root, the export also writes a `hotUpdate` block into
`game.config.json`:

```json
{
  "hotUpdate": {
    "remoteRoot": "https://cdn.example.com/my-game",
    "persistUpdateKey": "esengine:hotupdate"
  }
}
```

At boot the runtime reads this block and:

- applies `remoteRoot`, so remote-group `@uuid` references resolve to the CDN;
- with `persistUpdateKey` (default `esengine:hotupdate` whenever a root is set), restores a previously applied update,
  so a returning player starts on updated content, including offline;
- installs the built-in rebinder, so an applied update reaches live components without game code.

To publish an update, upload the newly cooked assets and the new `asset-manifest.json` to the CDN. Uploads are
additive: old files remain valid for clients that have not updated.

## Checking for and applying updates

The game starts the check with one call — at boot, from a **Check for updates** button, or on a timer.

```ts
import { defineSystem, Res, Schedule, Assets } from 'esengine';

async function pullUpdate(assets: Assets): Promise<void> {
  // 1. Fetch the CDN manifest and diff it against the running one (downloads nothing).
  const plan = await assets.checkForUpdate({
    manifestUrl: 'https://cdn.example.com/my-game/asset-manifest.json',
    remoteRoot:  'https://cdn.example.com/my-game',
  });
  if (!plan.hasUpdate) return;
  console.log(`Update available: ${plan.downloadFiles.length} files, ${(plan.totalBytes / 1024) | 0} KB`);

  // 2. Verify each required file before activating the manifest.
  const result = await assets.applyUpdate((loaded, total) => {
    console.log(`Downloading ${loaded}/${total}`);
  });
  if (result.ok) console.log(`Applied — ${result.updated} assets updated`);
  else console.warn('Update failed, rolled back:', result.failed);
}

// Run it once at startup (guarded so the async check fires a single time).
let checked = false;
const checkForUpdates = defineSystem([Res(Assets)], (assets) => {
  if (checked) return;
  checked = true;
  void pullUpdate(assets);
});
// app.addSystems(Schedule.Update, checkForUpdates)
```

`checkForUpdate` fetches the candidate manifest and returns an [`UpdatePlan`](#api-reference) without downloading
assets, so the game can show the size (`N files, K KB`) before committing. `applyUpdate` downloads and swaps.

### Automatic rebinding

When a scene references a remote-group asset by `@uuid`, `applyUpdate` downloads the new bytes, swaps the manifest,
and the built-in rebinder replaces the old texture in every live field that declares one: built-in fields
(`Sprite.texture`, `MeshRenderer.texture` / `.normalMap`, `UIVisual.texture`, `TilemapLayer.tileset`,
`ParticleEmitter.texture`, `TrailRenderer.texture`) and fields of project components declared in `assetFields`.

If a component also lists a texture in `discoverAssets`, a live field such as `Sprite.texture` or
`MeshRenderer.texture` switches to the updated image while the list keeps the generation it acquired.
A spawned prefab or an entity that leaves its scene releases its field receipt when its last matching field
is cleared. The scene or entity that owns the list keeps the original generation until its own lifetime ends.

Live material fields, including `Sprite.material` and `MeshRenderer.material`, also follow their manifest record
when the cooked file moves. If an update removes a texture or material, an existing field keeps its current
handle. Restoring the same UUID in a later update moves that field to the replacement while the game is running.

The replacement is acquired once per scene that holds the asset, and each scene moves to it as a unit — all of that
scene's bindings or none. Unloading one scene never releases the updated texture from another scene still using it,
and an unloading scene releases exactly what it holds, regardless of how many updates it received.

For anything the rebinder does not cover — a manually bound texture, a sound, a custom system — subscribe to
`onInvalidate` and rebind:

```ts
const unsub = assets.onInvalidate((event) => {
  // `event.ref` was just invalidated by an update. `event.type` says what kind of
  // asset it was ('texture', 'audio', 'material', …) and `event.oldValue` what live
  // holders were bound to before the drop (a texture's handle).
  if (event.type !== 'texture') return;
  void assets.loadTexture(event.ref).then((tex) => { /* assign tex.handle */ });
});
```

## API reference

The hot-update API is on the `Assets` resource (`Res(Assets)`):

| Method | Returns | Description |
| --- | --- | --- |
| `checkForUpdate(options)` | `Promise<UpdatePlan>` | Fetches a candidate manifest, diffs it against the active one and stages it. Downloads no assets. |
| `applyUpdate(onProgress?)` | `Promise<ApplyUpdateResult>` | Applies the staged update atomically: verifies the files in `downloadFiles`, then swaps the manifest, rebinds live handles and persists. `onProgress(loaded, total)` reports download progress. |
| `restorePersistedUpdate(key)` | `boolean` | At boot, restores the manifest a previous `applyUpdate` persisted under `key`. Called by the runtime when `persistUpdateKey` is set. |
| `updateStatus()` | `UpdateStatus` | `{ revision, persistedRevision, staged, applying }`, for a diagnostics screen. |
| `setRemoteRoot(url?)` | `void` | Sets the CDN root for remote groups (`undefined` clears it: same-origin). The runtime sets it from the build's `remoteRoot`. |
| `remoteRoot` | `string \| undefined` | The active CDN root (getter). |
| `onInvalidate(listener)` | `() => void` | Subscribes to invalidations. The listener receives `{ ref, type, oldValue }`; returns an unsubscribe function. |
| `loadGroup(name, onProgress?)` | `Promise<AssetBundle>` | Loads a whole group on demand ([On-demand groups](#on-demand-groups)). |
| `releaseGroup(name)` | `void` | Releases the oldest outstanding bundle acquired by `loadGroup(name)`. |

**`CheckForUpdateOptions`**

| Field | Type | Description |
| --- | --- | --- |
| `manifestUrl` | `string` | URL of the candidate (remote) manifest. |
| `remoteRoot` | `string` (optional) | CDN root of the candidate's remote assets. Defaults to the current root. Changing it verifies files whose resolved URL moves, even when the manifest is identical. |

**`UpdatePlan`** (returned by `checkForUpdate`)

| Field | Type | Description |
| --- | --- | --- |
| `hasUpdate` | `boolean` | `true` when assets, group settings or the build revision change. |
| `changedAssets` | `AssetChange[]` | New assets or assets whose main file or delivery changed. |
| `reconfiguredAssets` | `AssetChange[]` | Assets that reuse their main file with changed settings or previews. |
| `removedAssets` | `AssetChange[]` | Records leaving the manifest. Removal requires zero downloads. Existing fields keep the generation they hold. |
| `changedGroups` | `string[]` | Groups with changes to their membership, settings or assets. |
| `downloadFiles` | `UpdateFile[]` | Distinct files to verify. A streamed texture can have a full image and a small preview. Shared files count once at each delivery location. |
| `totalBytes` | `number` | Total size of the files in `downloadFiles`. |
| `fromRevision` / `toRevision` | `string \| null` | Old and new manifest revisions. |

**`ApplyUpdateResult`** (returned by `applyUpdate`)

| Field | Type | Description |
| --- | --- | --- |
| `ok` | `boolean` | `true` once every required file passes verification and the candidate manifest is active. |
| `updated` | `number` | Number of assets applied (`0` on failure). |
| `failed` | `AssetDownloadFailure[]` | Each failed file's path and reason (`fetch`, `integrity`, or `packed` for a changed pack). |
| `stages` | `UpdateStages` | How far the apply got (below). `ok` alone does not state whether the next launch keeps the update. |
| `revision` | `string \| null` | The revision this session runs on afterwards. |
| `uncached` | `string[]` | Changed assets the disk cache refused, by URL; the next launch fetches them again. |
| `reason` | `'nothing-staged'` (optional) | Nothing was attempted: no update was staged, or another `applyUpdate` already took it. |

**`UpdateStages`**

| Field | Type | Description |
| --- | --- | --- |
| `verified` | `boolean` | Every file in the download plan passed verification. |
| `applied` | `boolean` | This session runs on the new manifest and its assets have settled on it. |
| `persisted` | `boolean \| null` | The next launch starts on it (stored and read back). `false` when storage refused (quota full); `null` without a persistence key. |
| `cached` | `boolean \| null` | Every changed remote asset is in the disk cache, so the next launch reads it without the network. `null` where the platform has no disk cache (web). |

`updateStatus()` reports the same information at any time: the running revision, the revision the next launch starts
on, what is staged and its download size, and whether an apply is in progress.

## On-demand groups

A remote group can also be loaded as downloadable content: the game loads the whole group when the player reaches its
content and releases it afterwards.

```ts
// Player enters "world 2" — pull its remote group from the CDN.
const bundle = await assets.loadGroup('world2', (loaded, total) => {
  showProgress(loaded / total);
});
// ...later, player leaves:
assets.releaseGroup('world2');
```

`loadGroup` loads through the same typed loaders as other assets, and `releaseGroup` is reference-counted: an asset
another scene still holds is kept. See [Assets → Addressable groups](/docs/assets/overview/#addressable-groups-lazy-loading).

## Integrity, atomicity and rollback

`applyUpdate` runs in two phases:

<Steps>

1. **Download and verify.** Each file in `downloadFiles` is fetched, hashed and compared with the manifest's `contentHash`. A
   failed download or a mismatch (a corrupted or tampered response) is recorded as a failure. The active manifest is
   not modified during this phase.
2. **Commit.** Only when every asset succeeded: the manifest and root are swapped, live handles are rebound, and the
   new manifest is persisted.

</Steps>

If phase 1 records any failure, nothing is applied: the previous manifest stays active and `applyUpdate` returns
`{ ok: false, failed }`.

<Aside type="caution">
  A cooked web build enforces a **same-origin CSP** by default. Fetching the manifest or assets from another origin
  (another host or port) is blocked unless the CDN sends the required CORS headers. Serve the manifest and assets from
  an origin the game is allowed to reach.
</Aside>

## Persistence and offline start

With `persistUpdateKey` set (the export sets it), `applyUpdate` saves the applied manifest to platform storage. At the
next boot the runtime calls `restorePersistedUpdate(key)` and the game starts on the updated content. On targets with
a disk cache, verified bytes are also written there, so updated assets load without the network; `stages.cached`
reports whether all of them were stored. See [Device Disk Cache](/docs/publishing/content-cache/).

A stored update belongs to the package it was applied to. When a newer build is installed (a new web deployment, an
app-store update), the stored update is older than the shipped content and is discarded.

Applies run one at a time. An update found while another is downloading stays staged; applying it downloads only what
the first did not already bring.

## Platform support

| Target | Manifest and diff | CDN fetch | Persist | Disk cache |
| --- | --- | --- | --- | --- |
| **Web** | Yes | Yes (CORS and CSP apply) | `localStorage` | No; the next launch refetches from the CDN |
| **Desktop** | Yes | Yes | Yes | Yes (content-addressed) |
| **Mini-games** (WeChat, Douyin, …) | Yes | Yes | Yes | Yes (the host's user data directory) |
| **Native (iOS, Android)** | Yes | Yes | Yes | Yes |

The diff is platform-independent; only the fetch, storage and disk-cache primitives differ per platform.

## Recommendations

- Keep hot-updatable content in dedicated Remote folders and the core game Local, so the package boots without a
  network.
- Run the check once at boot or from a button, not every frame.
- Show `totalBytes` and the file count before a large download on mobile data.
- Handle `ok: false`: the update was rolled back; retry later.
- Use export profiles: the project root on a test bucket (or empty for same-origin), the production CDN on a
  production profile.
- Use different `manifestUrl` values for staged rollouts or A/B channels on the same CDN.
