Mini-game hosts (WeChat's `wx`, Douyin's `tt` and others) expose a near-identical API: no DOM, a packaged file system,
subpackages, touch input and key-value storage. Estella implements this model once as a platform **family** and
describes each vendor as a **profile**. WeChat is one profile of the family.

This page describes how to add a vendor Estella does not ship. For WeChat itself, see
[WeChat MiniGame](/docs/publishing/wechat/); for SUD OpenPaaS, see [SUD OpenPaaS](/docs/publishing/openpaas/).

<Aside type="caution">
  **Pre-1.0.** The profile contract is `@beta` and may gain fields as further vendors are supported.
</Aside>

## Runtime profile

A runtime profile is an id, a label and the host global, plus optional overrides:

```ts
import { installMiniGamePlatform } from 'esengine/minigame';

declare const myHost: any;   // the host global, e.g. `tt`

installMiniGamePlatform({
  id: 'myvendor',
  hostLabel: 'MyVendor',
  get global() { return myHost; },
});
```

This is a complete platform. File system, `fetch`, canvas, image decoding, touch and key input, storage, subpackages,
memory-pressure signals, device pixel ratio and language come from the normalized host global, as do **audio**
(`createInnerAudioContext`) and **sockets** (`connectSocket`). Video uses the engine's own wasm MPEG-1 decoder.

Read `global` through a getter: the host global exists only at runtime, and a getter keeps the profile importable in
a bundler or a test.

### WebAssembly instantiation

The one host difference with a dedicated method is WASM instantiation. WeChat instantiates through
`WXWebAssembly.instantiate(path)` instead of the standard `WebAssembly`, so its profile overrides `instantiateWasm`:

```ts
{
  id: 'wechat',
  hostLabel: 'WeChat',
  get global() { return wx as unknown as MiniGameGlobal; },
  instantiateWasm(pathOrBuffer, imports) { /* WXWebAssembly */ },
}
```

A host with standard `WebAssembly` omits it; the family reads the binary through the packaged file system and
instantiates it.

### Replaceable backends

`createAudioBackend`, `createVideoBackend` and `createSocket` are optional overrides. The defaults are
`MiniGameAudioBackend`, the wasm video decoder and `MiniGameSocket`, all exported from `esengine/minigame` for
wrapping. An override also replaces an implementation the project does not want, for example video decoding:

```ts
import type { MiniGameProfile, PlatformVideoBackend, VideoBackendContext } from 'esengine/minigame';

class SoftwareVideoBackend implements PlatformVideoBackend {
  readonly name = 'my-software-decoder';
  constructor(private ctx: VideoBackendContext) {}
  createStream(url: string, options) { /* your decode → VideoStreamHandle */ }
  dispose() {}
}

export default {
  id: 'myvendor',
  hostLabel: 'MyVendor',
  get global() { return myHost; },
  createVideoBackend: (ctx) => new SoftwareVideoBackend(ctx),
} satisfies MiniGameProfile;
```

`VideoPlugin` requests a backend from the platform once at build; every `VideoPlayer` in the game uses it. The contract
is `PlatformVideoBackend`: `createStream(url, options)` returns a `VideoStreamHandle` whose `pump(module)` uploads the
current frame to `textureHandle` once per frame. Audio (`PlatformAudioBackend`) and sockets (`PlatformSocket`) follow
the same pattern.

To keep a host's profile and change one capability, spread it:

```ts
import { wechatProfile } from 'esengine/wechat';

export default { ...wechatProfile, createVideoBackend: (ctx) => new SoftwareVideoBackend(ctx) };
```

<Aside type="note">
  **Built-in targets cannot be overridden.** They install their own profile on import, so selecting *WeChat* in
  Package Project always uses the stock backends. To replace a capability, define a project platform
  ([Project platforms](#project-platforms)) whose `runtimeProfile` spreads the host profile and overrides the
  capability, and select that target.

  The spread does not include WeChat's `WXWebAssembly` polyfill, which `initWeChatPlatform()` installs; call
  `polyfillWebAssembly()` from `esengine/wechat` in that case.
</Aside>

## Host API

The `global` must satisfy `MiniGameGlobal`. Required members:

| Member | Used for |
| --- | --- |
| `createCanvas()` | Display surface (first call) and offscreen 2D |
| `createImage()` | Image decoding |
| `getFileSystemManager()` | `readFileSync` / `readFile` / `access` / `accessSync` / `writeFile` |
| `request(opts)` | The `fetch` polyfill |
| `createInnerAudioContext()` | Audio playback |
| `connectSocket(opts)` | `GameSocket` and replication |
| `getSystemInfoSync()` | Viewport size, pixel ratio, language |
| `onTouchStart/Move/End` and `off*` | Pointer input |
| `getStorageSync` / `setStorageSync` / `removeStorageSync` / `getStorageInfoSync` | Save data, hot-update bookkeeping |

Optional members, probed by the adapter (absence degrades the related feature): `onTouchCancel` / `offTouchCancel`,
`onKeyDown` / `onKeyUp` (and `off*`), `loadSubpackage`, `onMemoryWarning` / `offMemoryWarning`, `onShow` / `onHide`.

<Aside type="note">
  `isMiniGame()` checks the adapter's declared family, not a list of vendor names, so an installed platform receives
  every mini-game code path (packaged reads, subpackage groups, no-DOM branches). `isWeChat()` remains a vendor check
  and returns `false`.
</Aside>

## Booting

The package entry calls the family runtime:

```js
// game.js — the host runs this
const engineFactory = require('./wasm/esengine.js');
const bundle = require('./game-bundle.js');
bundle.boot(engineFactory, { /* side module factories */ });
```

```ts
// bundled with the game
import { installMiniGamePlatform, initMiniGameRuntime } from 'esengine/minigame';
import { myProfile } from './myProfile';

export function boot(engineFactory, sideModuleFactories) {
  installMiniGamePlatform(myProfile);
  return initMiniGameRuntime({
    engineFactory,
    engineWasmPath: 'wasm/esengine.wasm',
    sceneNames: ['Main'],
    firstScene: 'Main',
    sideModuleFactories,
  });
}
```

`initMiniGameRuntime` takes the display canvas from the adapter, registers its GL context with the engine module,
loads the addressable manifest and runs the app. `initWeChatRuntime` is the same function with WeChat's staged wasm
name filled in.

<Aside type="note">
  Install the platform **before** calling `initMiniGameRuntime`; otherwise it throws with the fix in the message. The
  first `createCanvas()` of the process is the display surface on every mini-game host, so nothing may create a canvas
  before the runtime does.
</Aside>

## Project platforms

In **Package Project**, hover the *Project* group of the target list and click **+** (or **New platform**). With Kind
*Mini-game host*, an id and a name, the editor writes both halves of the vendor, already linked, and selects the new
target.
The packaging half is an ordinary project file:

```js
// .esengine/platforms/acme-play.mjs
export default {
  id: 'acme-play',
  label: 'ACME Play',
  blurb: 'ACME mini-game package.',
  defaultOut: 'dist-acme',

  emitConfigFiles(ctx) {
    return [{
      file: 'game.json',
      content: JSON.stringify({
        orientation: ctx.orientation,
        appName: ctx.title,
        ...(ctx.subPackages.length > 0 ? { subPackages: ctx.subPackages } : {}),
      }, null, 2) + '\n',
    }];
  },
};
```

Everything not declared defaults to a standard mini-game host: the vendor-neutral SDK entry (`index.minigame.js`),
`initMiniGameRuntime`, the standard `WebAssembly` engine glue and a generic CommonJS `game.js`. Cooking, the manifest,
scene transforms, the side-module scan, bundling and the runtime copy are the WeChat pipeline.

### Linking the runtime profile

The runtime half is the `MiniGameProfile` described above. `runtimeProfile` points at it, and the generated entry
installs it before booting:

```js
// .esengine/platforms/acme-play.mjs
export default {
  id: 'acme-play',
  label: 'ACME Play',
  runtimeProfile: 'src/acme-runtime.ts',   // ← the other half
  emitConfigFiles(ctx) { /* … */ },
};
```

```ts
// src/acme-runtime.ts — default-exports the runtime MiniGameProfile
export default {
  id: 'acme-play',
  hostLabel: 'ACME Play',
  get global() { return acme; },
  createVideoBackend: (ctx) => new SoftwareVideoBackend(ctx),
};
```

`esengine/minigame` installs no platform until the game names a host; without `runtimeProfile` the package builds but
throws on the device. Omit `runtimeProfile` only when the game calls `installMiniGamePlatform` itself. The editor
checks that the path exists before marking the platform ready.

The `id` must consist of lowercase letters, digits and dashes and must not shadow a built-in target. It is also the
cook's **Import Settings key**, so per-texture overrides can target the platform by name.

<Aside type="note">
  A profile that fails to load is listed with its error. The editor probes the engine runtime the platform needs
  (`wasmDir`, default the editor's web runtime) so the dialog reports a missing runtime before a build starts. A
  profile module runs in the editor's main process and requires approval before it loads
  ([Editor Plugins](/docs/extending/editor-plugins/#project-platform-profiles)).
</Aside>

### Profile fields

| Field | Description |
| --- | --- |
| `id` | Vendor identity; also the Import Settings key the cook reads per texture. |
| `label`, `blurb`, `defaultOut` | Name and description in the target list; default output folder. |
| `sdkEntryFile` | SDK dist entry that `esengine` is aliased to. |
| `runtimeInit` | Boot function the generated entry imports. |
| `engineGlueCandidates` | Engine glue file names to look for, in order of preference. |
| `esTarget` | Syntax level of the bundle and the down-levelled glue. |
| `wasmBuildHint` / `sideModuleBuildTargets` | The `build -t …` names used in error messages. |
| `nativeSuffixes` / `binRestageExts` | The packer's file-suffix policy. |
| `subpackageDir` | Where lazy groups are staged. |
| `emitConfigFiles` / `emitEntry` | The vendor's config files and `game.js`. |
| `wasmDir` | Project-relative engine runtime directory (default: the editor's web runtime). |
| `runtimeProfile` | Project-relative module that default-exports the runtime `MiniGameProfile`. |

The profile module runs in the editor's **main process**, not the renderer: its emitters are functions, which cannot
cross the IPC boundary, so the file is plain `.mjs` with a default export.

## Engine build per host

A host needs its own engine build only if it cannot load the web engine's wasm. WeChat needs one (`-t wechat`,
`ES_BUILD_WXGAME`) because of `WXWebAssembly` and because it has no WebGPU. A host with standard `WebAssembly` and
WebGL2 can ship the web build's glue; `engineGlueCandidates` falls back to `esengine.js` for this case.

A host that refuses WASM SIMD takes the mini-game build without it (`-t quickgame`, `ES_MAIN_DISABLE_SIMD`), and its
side modules from the same flavor (`physics-quickgame`, `spine-quickgame`, …, all into `build/wasm/quickgame`). The
quick-game hosts, Alipay and Huawei use it, and so does Douyin, whose iOS host does not support SIMD and whose one
package runs on both phones. A build without SIMD is optimized without it, so an opcode left in one fails the build.
