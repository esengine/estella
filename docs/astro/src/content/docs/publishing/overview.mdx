An Estella project is exported from the editor to **Web**, **Desktop**, **WeChat MiniGame** and the other mini-game
hosts (Douyin, Kuaishou, Bilibili, quick games, Alipay, Huawei), a single-file **Playable** ad, and native
**Android** and **iOS** apps. Every export runs on the same runtime that the editor's Play mode uses.

## Package Project dialog

![The Package Project dialog — the target list, build configuration, output folder, and scenes in build](@/assets/guides/en/build-dialog.png)

*Left: the categorized target list. Right: the selected target's settings, profile, configuration, compression,
output folder, scenes in build and Advanced options.*

<Steps>

1. Open **Build → Package Project…**.
2. Select a **target**. Targets are grouped as *General* (Web, Desktop, Playable), *Mini-Games* (WeChat, Douyin,
   Kuaishou, Bilibili, Quick game, Alipay, Huawei quick game — see [Mini-Game Platforms](/docs/publishing/minigame-platforms/)),
   *Mobile* (Android, iOS) and *Project* (platforms the project defines). A target with more than one destination
   lists them beneath it: Desktop branches into *Standalone* and *[Steam](/docs/publishing/steam/)*.
3. Fill in the target's own settings (*\<target\> settings*): application identity and store-specific values.
4. Choose a **Profile** (*Project settings*, or a saved export profile), a **Configuration** (*Development* or
   *Shipping*), the **Compression** boxes ([Compression](#compression)) and the **Output** folder. **Advanced**
   holds the CDN root, the size budget, source maps and *Open output folder when done*.
5. Review **Scenes in build** ([Scenes in build](#scenes-in-build)).
6. Click **Package**. The build log streams in the dialog. When the build finishes, the output folder opens (unless
   *Open output folder when done* is off), and Web and Playable builds offer **Preview over http**.

</Steps>

The dialog's choices are saved in `project.esproject` and restored the next time it opens.

### Export profiles

An export profile is a named set of overrides for one target, stored in `packaging.profiles` of
`project.esproject`: configuration, source maps, compression boxes, CDN root, excluded scenes and per-target
settings. With a profile selected, the dialog's controls edit the profile; each overridden value has a reset button
that hands the setting back to the project. *New profile for this target* creates one. The CLI selects a profile
with `--profile <name>`.

## Targets

| Target | Output | Default folder | Next step |
|---|---|---|---|
| **Web** | A static, self-contained web build. | `dist-web/` | **Preview over http**, or upload the folder to a static host. |
| **Desktop** | A native app per installed desktop runtime template: a `.app` on macOS, a `<Name>/` directory with `<Name>.exe` on Windows or `<Name>` on Linux. No Chromium and no npm project. | `dist-desktop/` | Run it. The **Steam** channel also writes depot scripts and `STEAM.md` — see [Steam](/docs/publishing/steam/). |
| **WeChat** | A WeChat MiniGame package. | `dist-wechat/` | Open the folder in WeChat DevTools — see [WeChat MiniGame](/docs/publishing/wechat/). |
| **Douyin**, **Kuaishou**, **Bilibili**, **Quick game**, **Alipay**, **Huawei quick game** | A mini-game package for that host (a signed `.rpk` for quick games and Huawei), built by the same pipeline as WeChat. | `dist-douyin/`, `dist-kuaishou/`, `dist-bilibili/`, `dist-quickgame/`, `dist-alipay/`, `dist-huawei/` | Open it in the platform's developer tool. Douyin and Bilibili take an AppID in the target settings; Kuaishou and Alipay take it in the developer tool; Huawei needs an app registered in AppGallery Connect. |
| **Playable** | One self-contained `index.html` with every resource inlined. | `dist-playable/<network>/` | **Preview over http**, then upload to the selected ad network — see [Playable Ads](/docs/publishing/playable-ads/). |
| **Android** | A native arm64 app rendering through Vulkan: a signed APK, an Android Studio project, or an APK plus App Bundle. | `dist-android/` | Install the APK, or open the project in Android Studio — see [Android & iOS](/docs/publishing/android-ios/). |
| **iOS** | A native arm64 app rendering through Metal, written as an Xcode project. | `dist-ios/` | Open the project in Xcode, select a signing team, run. |

Desktop, Android and iOS exports contain app **content**; the engine, the SDK and the game runtime are in the app
binary, which is assembled from a runtime template the editor installs ([Runtime prerequisites](#runtime-prerequisites)).

## Scenes in build

Every scene in the project's scenes folder is exported and is a `SceneManager.switchTo` target
([Scenes](/docs/world/scenes/)). The **Scenes in build** list controls the set:

- The **startup scene** is pinned first with a play badge and always ships. Click another scene's play button to move
  the pin, or use **Set as Startup Scene** on a scene's context menu in the Content Browser.
- Unticking a scene excludes it from the build (`packaging.excludeScenes` in `project.esproject`). Excluded scenes
  remain editable and playable in the editor; assets referenced only by excluded scenes are not cooked.
- **Playable** exports the startup scene only. The CLI option `--all-scenes` inlines every scene.

## Build configuration

| Configuration | Behaviour |
|---|---|
| **Development** | Unminified scripts. Pair with source maps for debugging. Development builds of targets that support it can connect to the editor's Frame Debugger (*Frame debugger connection* under Advanced). |
| **Shipping** | Minified scripts (*Minify scripts* in project packaging settings, on by default). Use for release. |

**Include source maps** (Advanced) maps the running bundle to the TypeScript sources. It is offered for targets that
support it (Web and Desktop); turn it off for release builds.

## Compression

Each kind of compression is a separate box under **Compression**. Every box is off by default; an unticked box ships
the assets as they are, and a size budget never turns a box on. The parameters each box applies (a texture's format
and Max Size, a clip's bitrate) are per-asset **Import Settings** in the Inspector, with a tab per platform.

![The Package Project dialog with the Web target, at the Build group: Configuration, the three Compression boxes and the hint under them](@/assets/guides/en/publish-compression.png)
| Box | Targets | Effect |
|---|---|---|
| **Textures by import settings** | All | Applies each texture's Import Settings: the GPU format (KTX2) where the target ships one, and Max Size. A playable ships images, so only Max Size applies there. The viewport draws textures as the build will ship them while this box is ticked. |
| **Pack atlases** | All | Packs each `<name>.atlas/` folder, or each [`atlases` entry](/docs/publishing/hot-update/#esengineasset-groupsjson) in `.esengine/asset-groups.json`, into atlas pages. Textures sampled by meshes keep their own files. |
| **Audio to MP3** | All | Converts WAV clips to MP3 at each clip's Import Settings bitrate; a clip whose settings disable compression stays WAV. |
| **Compress the engine binary** | Mini-games | Ships the engine `.wasm` (and side modules) Brotli-compressed where the host can load it. Same setting as *Compress wasm binaries* on the WeChat page. |
| **Images as WebP** (Off / Lossless / Quality 90 / Quality 80) | Playable | Encodes PNGs as WebP — see [Playable Ads](/docs/publishing/playable-ads/#image-encoding). |

### Compressed textures

KTX2 textures are transcoded by the runtime to the best format the device supports (ASTC, then ETC2, then S3TC,
falling back to RGBA8), with their mip chains.

<Aside type="caution" title="Block-compressed textures need dimensions that are multiples of 4">
Every format a KTX2 transcodes to is block-compressed, and WebGPU rejects a compressed texture whose width or height
is not a multiple of 4. The build ships such a texture uncompressed and names it in a warning:

```
assets/textures/platform.png: shipped raw — 70x70 is not a multiple of 4,
which a block-compressed texture must be
```

Resize or pad the texture to a multiple of 4, or pack it into an atlas (atlas pages are always whole blocks).
</Aside>

### Content addressing and asset packs

- **Content addressing** is on by default for Web, Desktop and the mini-game targets: each file is named by a hash of
  its bytes, so URLs are immutable and identical files are stored once.
- **Asset packs** (Web): the export packs small local assets (meshes, materials, KTX2 textures, timelines, animation
  assets) into a few `packs/*.pack` files, each loaded in one request; the manifest records where each asset sits.
  An export with a [hot update](/docs/publishing/hot-update/) CDN root keeps one file per asset, because an update
  downloads assets individually.

<Aside type="caution" title="Assets referenced only from code are culled">
  The cook ships the assets reachable from the scenes in the build. An asset named only in code — a texture in
  rich-text markup, a clip played by URL, a prefab spawned by path — is culled. The editor reads the project from
  disk, so the omission is visible only in an exported build. Mark such folders **Delivery → Always include in
  builds** in the Content Browser ([Assets](/docs/assets/overview/#shipping-what-only-code-names)).
</Aside>

## Packaging settings

Settings specific to one target are edited on that target's page in **Package Project** (a search in the Settings
dialog links to them):

| Target | Settings |
|---|---|
| **Web** | Web channel (Standalone, Poki, CrazyGames, YouTube Playables — see [Web Portals](/docs/publishing/web-portals/)), Run without WebAssembly, Ask to rotate the device when held the wrong way. |
| **WeChat** | AppID, Compress wasm binaries, Engine in a subpackage, Render through EmscriptenGLX. |
| **Desktop** | Desktop App ID (override), Product name (names the app), Channel (Standalone or Steam). |
| **Android** | Android Version Code, Package as (installable package or Android Studio project), Include the emulator (x86_64), Compress native libraries, Google Play App Bundle (.aab), release signing key. |

Project-wide settings are in **Settings → Project → Build and modules → Packaging** and are saved with the project:

| Setting | Description |
|---|---|
| **Application ID** | Reverse-DNS id of the installed app: the Android manifest package, the iOS bundle id, the desktop installer id. Empty derives an id from the project name. Set it before publishing; stores keep it permanently. |
| **App Icon** | One square PNG used by every installable target. |
| **Achievement IDs** | The achievement ids the game unlocks. Platform-neutral; used by [Steam](/docs/publishing/steam/#achievements) and other stores. |
| **Minify scripts** | Minifies game and engine JavaScript in Shipping builds. Default on. |
| **Compile all systems** | Shipping builds compile every system the compiler accepts to machine code; off compiles only systems marked `@compiled`. Default on. |

![Settings → Project → Build and modules, Packaging section](@/assets/guides/en/publish-packaging-settings.png)
### Screen orientation

Orientation is one project-wide setting: **Settings → Project → Game → Display → Orientation** (portrait or
landscape). Unset, it is derived from the design resolution (width ≥ height gives landscape, otherwise portrait).
Every target applies it:

| Target | Applied as |
|---|---|
| WeChat and mini-games | `deviceOrientation` in `game.json` |
| Web | A best-effort `screen.orientation.lock` |
| Desktop | The window's aspect |
| Android, iOS | `app.config.json` of the native app |
| Playable | Declared to the network only where the network asks for it; the page is not locked ([Playable Ads](/docs/publishing/playable-ads/#orientation)) |

On the web, a phone held in the other orientation shows the game letterboxed. With **Ask to rotate the device when
held the wrong way** (Web target settings) on, a touch device held the wrong way hides the canvas behind a "Rotate
your device" notice until it is turned; desktop browsers always show the game. Manifest form, off by default:

```json
"packaging": { "platforms": { "web": { "rotateHint": true } } }
```

## Preview an export

After a **Web** or **Playable** build, **Preview over http** serves the output folder on a loopback server
(`http://127.0.0.1:<port>/`) and opens it in the browser.

<Aside type="caution">
  A web build requires an **http origin**. Opening `index.html` from disk (`file://`) cannot stream the WebAssembly.
  Use the preview button or a static host.
</Aside>

## Runtime prerequisites

| Target | Runtime | Setup |
|---|---|---|
| Web, Playable | The engine runtime shipped with the editor. A playable inlines it (glue as a blob module, wasm as base64). | None. |
| WeChat and WeChat-runtime mini-games | A separate runtime, because the WebAssembly loader differs, plus WeChat side modules. Shipped with the editor download. | None in an installed editor. In a source checkout, build it once (below). |
| Desktop, Android, iOS | A **runtime template** per editor version. Until it is installed, the target's row in Package Project offers **Download** and **Install from file…**. | iOS also needs macOS with Xcode. A project with `@compiled` systems needs a C compiler (clang or gcc) for Desktop and the Android NDK for Android. |

```bash
# source checkout only, before the first WeChat export
node build-tools/cli.js build -t wechat
```

The dialog distinguishes two kinds of missing prerequisite:

- A missing **engine runtime** (Web, Playable, WeChat) blocks the export. A WeChat export stops and names the build
  command to run. WeChat uses `physics-wechat` for Box2D and either `physics3d-wechat` (Jolt)
  or `physics3d-physx-wechat` (PhysX) for a 3D physics scene. Douyin ships the runtime built without WASM SIMD, which its
  iOS host refuses: the same modules with a `-quickgame` suffix (`physics-quickgame`, `physics3d-quickgame`, …).
  Other optional builds are listed in [WeChat MiniGame](/docs/publishing/wechat/).
- A missing **native toolchain** (iOS) does not block the export. The content is written; only the final assembly
  into an installable app needs the toolchain, and that step can run on another machine.

<Aside type="caution" title="Native targets need a runtime template">
  The Desktop, Android and iOS runtime templates are not part of the editor download. Install each template once per
  editor version from the target's row in Package Project; it must match the editor version exactly. Android needs no
  engine checkout, SDK or JDK. iOS also needs macOS with Xcode. See
  [Android & iOS](/docs/publishing/android-ios/#prerequisites) and [Steam](/docs/publishing/steam/).
</Aside>

## Side modules

Optional engine features ship as WebAssembly **side modules** — an emscripten `<file>.js` glue plus `<file>.wasm` —
loaded on demand:

| Module | Artifacts | Loaded when |
|---|---|---|
| Physics (Box2D) | `physics.js` / `physics.wasm` | The project declares physics or a scene uses 2D physics components. |
| 3D physics (Jolt) | `physics3d.js` / `physics3d.wasm` | A scene uses `RigidBody3D`. Loaded in addition to the 2D module. |
| 3D physics (PhysX) | `physics3d-physx.js` / `physics3d-physx.wasm` | As above, in a project whose 3D solver is PhysX. A package carries one of the two 3D modules. |
| Spine | `spine21`, `spine38`, `spine41`, `spine42`, `spine43` (`.js` / `.wasm`) | A scene uses a Spine skeleton of that format version. |
| DragonBones | `dragonbones.js` / `dragonbones.wasm` | A scene uses a DragonBones armature. One module reads every version. |
| Basis transcoder | `basis.js` / `basis.wasm` | The build ships KTX2 textures. |
| Video decoder | `videodec.js` / `videodec.wasm` | The wasm video path decodes a clip. |

| Target | How side modules are delivered |
|---|---|
| Web, Desktop | Loose files next to `esengine.wasm`, fetched from `wasmBaseUrl` (the directory the engine was loaded from). |
| Playable | Inlined as base64 in the HTML; `initPlayableRuntime` receives an embedded side-module host. |
| WeChat | WeChat-precompiled module factories, hence one `*-wechat` runtime build per feature. |
| Android, iOS, desktop apps | Compiled into the app binary. |

The editor's Play mode boots through the same runtime (`initPlayRealmRuntime`) and fetches side modules from the
editor origin. See [App Setup & Lifecycle](/docs/core-concepts/app/overview/#side-modules) for the runtime API.

## Content a target cannot render

If a target does not compile a subsystem the project uses, the export reports the subsystem (tilemaps, particles,
post-processing, physics, Spine, video, text) and the scenes or files that use it, instead of writing a package that
omits it. No current target has such a gap: the native apps compile the whole engine source list, including the
modules that are separate side modules on the web.

## Browsers without WebAssembly

**Run without WebAssembly** (Web target settings) adds the engine compiled to plain JavaScript,
`wasm/esengine.asm.js`, beside `wasm/esengine.wasm`. The page selects at boot: where `WebAssembly` exists it loads
the wasm engine and never downloads the JavaScript one; where it does not (some locked-down WebViews and embedded
browsers), it loads `esengine.asm.js` and runs the same scenes and scripts. Manifest form:

```json
"packaging": { "platforms": { "web": { "engineJs": true } } }
```

The setting is off by default. It adds about 4 MB to the package, which counts against host upload limits. With it
off, a browser without WebAssembly shows an error naming the setting. Mini-game targets never include the file. To
test the JavaScript engine in a normal browser, export with the setting on and append `?engine=js` to the URL.

| `hello-world` example, headless Chromium | WebAssembly engine | JavaScript engine |
|---|---|---|
| Engine file | 2.1 MB (0.67 MB gzip) | 4.3 MB (0.98 MB gzip) |
| Main-thread time per frame | 9.3 ms | ~11.5 ms |

Not available with the JavaScript engine:

- **WebGPU** — it always renders through WebGL2.
- **Side modules** (2D and 3D physics, Spine, DragonBones, Basis, video) — each logs one error naming the module and
  its features do not run.
- **Compiled (`@compiled`) systems** — they run interpreted, as in an export without AOT.

## Build CLI

The editor packages the game. `build-tools/cli.js` builds the **engine and SDK**; it is needed for the WeChat runtime
in a source checkout, for engine development, and to assemble native apps:

```bash
node build-tools/cli.js build -t web        # build the engine (web target)
node build-tools/cli.js build -t wechat     # the WeChat runtime
node build-tools/cli.js sdk                 # build the SDK only
node build-tools/cli.js watch               # rebuild on change (engine development)
node build-tools/cli.js native --target ios # the native mobile host
```

A project is packaged without the editor by `pipeline/bin/estella.mjs export <projectDir>`; `--help` lists its options
(`--platform`, `--profile`, `--out`, `--json`, `--enforce-budget` and others). See
[Package Size](/docs/publishing/package-size/#gating-a-build-on-size) for a CI example.
