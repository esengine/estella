A **wire** specifies: when this entity receives this event, run this action on that entity. Wires are rows of data on
the emitting entity, stored in the `EventBinding` component; they require no callback or script file.

```
click ─▶ ui.setPage(tabs, settings)      on "This entity"
click ─▶ ui.setPage(badge, on)           on "Card"
```

A row has no branches and no expressions. Logic is delegated to a [state machine](/docs/gameplay/ai/overview/) through
an action such as `fsm.fire`, or written as a [script graph](/docs/gameplay/script-graphs/), whose **On event** node
listens for the same named entity events.

## The Events section

![The Events section of the Details inspector](@/assets/guides/en/events-section.png)

*Two wires on a button. Both fire on `click`; one switches a controller on the button's ancestor chain, the other
targets the `Card` entity by name.*

Selecting an entity that can emit events — a UI node, an `Interactable`, a collider — shows its wires in the
**Events** section of the Details panel. Each row reads left to right:

| Part | Description |
|---|---|
| ☑ | Row enabled. An unchecked row stays in the data and never fires. |
| Event | Event type to listen for (`click`, `change`, `trigger_enter`, …). |
| ↳ Target | Entity the action runs on: *This entity* by default, or another entity **by name**. |
| Action | A registered action name, from the same palette as the state-machine and behaviour-tree editors. |
| Parameters | The parameters the action declares. An action without declared parameters takes one free-text argument. |
| ⚙ | Shows **Condition** (a registered condition that must pass) and **Once**. |

## The `EventBinding` component

Wires are stored in the `EventBinding` component, so they serialize into scenes and travel with
[prefabs](/docs/world/prefabs/) like any other component:

```typescript
import { EventBinding, UIEventType } from 'esengine';

world.insert(button, EventBinding, {
  rows: [
    { event: UIEventType.Click, action: 'ui.setPage', params: { controller: 'tabs', page: 'settings' } },
    { event: 'trigger_enter', target: 'Door', action: 'ui.setVisible', params: { visible: true }, once: true },
  ],
});
```

| `EventBindingRow` field | Type | Description |
|---|---|---|
| `event` | `string` | Event type to listen for. Any string; the built-in types are the predefined set. |
| `target` | `string?` | Name of the entity the action runs on. Omitted: the entity carrying the row. |
| `action` | `string` | Registered action name. |
| `params` | `Record<string, …>?` | The action's declared parameters by name. Takes precedence over `arg`. |
| `arg` | `string?` | The same input in canonical string form (`"tabs:settings"`). |
| `guard` | `string?` | Registered condition that must pass for the row to run. |
| `once` | `boolean?` | Runs at most once, then stays inert until the scene reloads. |
| `enabled` | `boolean?` | `false` keeps the row inert without deleting it. |

Wires fire during play only; the editor does not run actions while authoring.

### Target resolution

`target` is an entity **name**, searched outward from the row's entity: the entity itself, then its subtree, then
each ancestor's subtree, and finally the whole scene. The nearest match is used, so two instances of one prefab do not
resolve into each other: a `Close` button inside dialog A finds dialog A's `Panel`, not dialog B's.

A name that matches no entity is shown in red in the Details panel and logs a warning at runtime.

## Actions

An action is a named function in the shared action registry, which `.esfsm` state hooks and `.esbt` leaves also
resolve against. A registered name appears in all three palettes.

![The action palette, grouped by namespace](@/assets/guides/en/events-palette.png)

*The palette groups actions by `namespace.` prefix; the engine's actions carry a one-line description.*

Built-in actions:

| Action | Effect |
|---|---|
| `ui.setPage` | Switches a [UI controller](/docs/ui/controllers/) to a page. |
| `ui.setVisible` | Shows or hides a UI subtree (`UINode.display`). |
| `property.set` | Writes any component field, addressed as `Component.dot.path`. An optional `entity` parameter writes another entity. |
| `fsm.fire` | Fires a trigger on the target's state machine. |
| `blackboard.set` | Sets a blackboard value (`key=value`; the value is parsed as JSON when valid). |
| `scene.load` · `scene.reload` | Switches to a named scene, or restarts the current one, with an optional fade in seconds. |
| `audio.play` · `audio.stop` | Drives the target's `AudioSource`; `audio.play` can name another clip. |
| `soundEvent.trigger` · `soundEvent.stop` | Drives the target's sound event source. |
| `timeline.play` · `timeline.pause` | Drives a [timeline](/docs/animation/timeline/playback/) on the target. |
| `spriteAnim.play` · `spriteAnim.restart` · `spriteAnim.stop` | Drives a sprite flipbook. |

Importing `esengine/logic` (script graphs) also registers `entity.despawn` and `debug.log`.

### Custom actions

`registerAction(name, spec)` makes a name available in every palette:

```typescript
import { registerAction } from 'esengine';

registerAction('game.award', {
  params: [
    { name: 'kind', type: 'enum', options: [{ label: 'Coin', value: 'coin' }, { label: 'Star', value: 'star' }] },
    { name: 'amount', type: 'number' },
  ],
  run: (ctx, bb, arg, params) => {
    grantReward(ctx.entity, params!.kind as string, params!.amount as number);
  },
});
```

Declared `params` replace the free-text field with typed controls (here a dropdown and a number field). `ctx` is the
same context a state-machine action receives — `entity`, `world`, `commands` — plus the blackboard.

<Aside type="tip" title="Where to register">
  The editor does not execute gameplay code; it reads action names from the project's
  [declaration entry](/docs/scripting/script-modules/#declaration-entry) (`src/components.ts` by default). Actions
  registered there appear in every palette. Actions registered elsewhere still run, but their names must be typed.
</Aside>

## Events

### UI events

Widgets emit the standard set (`UIEventType`). Events **bubble**, so a row on a panel receives events from its
buttons:

`click` · `press` · `release` · `hover_enter` · `hover_exit` · `focus` · `blur` · `change` · `submit` ·
`drag_start` · `drag_move` · `drag_end` · `scroll` · `select` · `deselect` · `pointer_move` · `press_cancel` ·
`shown` · `hidden`

Pointer events (`press`, `release`, `click`, `pointer_move`, `press_cancel`) carry a `UiPointerEventData`:

| Field | Description |
|---|---|
| `pointer` | Pointer id; `-1` for the mouse. |
| `worldX`, `worldY` | Position in the world. |
| `screenX`, `screenY` | Position on the surface in pixels, measured up from the bottom-left. |
| `layoutX`, `layoutY` | Position in UI layout space. |

The entity that was pressed receives `pointer_move` for as long as the pointer is held, wherever it moves.
`UIControlPointers.cancelHold(pointer, to?)` releases a hold: the holder receives `press_cancel`, no click occurs,
and with `to` another entity takes over the rest of the gesture. An entity consisting only of a `ContentRect` and an
`Interactable` can be pressed.

`shown` and `hidden` are emitted when a node appears on screen or leaves it, usually because an **ancestor** was shown
or hidden, as navigation, tabs and dialogs do. Every node in the affected subtree receives them, so an action on a
screen's appearance is a row on that screen:

```
shown ─▶ fsm.fire(enter)  on "MissionPanel"   →   Hidden ──enter──▶ Entering
```

Visibility tracking has no cost until a row listens for `shown` or `hidden`, and none in frames where no UI changed.

### Physics events

[Physics](/docs/gameplay/physics-2d/overview/) contacts are delivered on the same channel (`Physics2DEventType`), so a
[trigger area](/docs/gameplay/markers/) is wired like a button. Both participants receive the event, each with the
other as its counterpart:

`collision_enter` · `collision_exit` · `collision_hit` · `trigger_enter` · `trigger_exit`

### Custom events

The event vocabulary is open. Any name emitted through `EntityEvents` can be listened for by a row:

```typescript
import { EntityEvents } from 'esengine';

app.getResource(EntityEvents).emit(chest, 'looted', { gold: 12 });
```

## Hand-off to a state machine

A row runs one action, without conditions beyond its guard and without sequencing. `fsm.fire` passes the event to the
entity's [state machine](/docs/gameplay/ai/overview/), which decides what it means:

```
click ─▶ fsm.fire(start)  on "Hint"   →   Idle ──start──▶ Running
                                                          onEnter: property.set(…)
```

![A state hook's declared parameters in the state machine editor](@/assets/guides/en/events-fsm.png)

*The same parameter controls in the state-machine editor: `property.set` declares `path` and `value`, so the hook shows
two fields instead of one string.*

An action declares its parameters once, and every authoring surface — event row, state hook, behaviour-tree leaf —
shows them.

## Argument forms

Every action has a canonical string form. `{ controller: 'tabs', page: 'settings' }` and `"tabs:settings"` are
equivalent, and the registry converts between them:

- data authored before an action declared its parameters continues to run unchanged;
- an action that reads only `arg` receives it when a row stores parameters;
- the Details panel shows typed controls for a row that stores a plain string.

The Details panel writes `params`; hand-written data may use either form.

<Aside type="caution" title="Asset and entity parameters are not supported">
  A parameter cannot be an asset reference or an entity handle. The cook's asset discovery and the scene's entity
  remapping do not inspect row parameters, so such a parameter would produce a build with a missing asset. Other
  entities are addressed by `target` name; assets are referenced through a component the cook can discover.
</Aside>
