`defineBehavior` declares per-entity game logic. One call produces:

1. A **component** holding the behaviour's per-entity `state`. It can be attached to any entity and edited in the
   Details panel.
2. A registered **system** that runs the `start` / `update` / `destroy` lifecycle for every entity carrying that
   component.

A behaviour is exactly one `defineComponent` plus one `defineSystem` on the [ECS](/docs/core-concepts/ecs/); there is no
separate scripting runtime.

## Defining a behaviour

`defineBehavior(name, def)` returns the backing component, which is spawned or inserted like any other. The `state`
object becomes the component's per-entity data:

```typescript
import { defineBehavior, Transform } from 'esengine';

export const Patrol = defineBehavior('Patrol', {
  state: { speed: 60 },   // per-entity data, editable in the Details panel
  update(ctx, dt) {
    const t = ctx.get(Transform);
    t.position.x += ctx.self.speed * dt;
    ctx.set(Transform, t);
  },
});
```

| `BehaviorDef` field | Type | Description |
|---|---|---|
| `state` | object | Per-entity data and its defaults; becomes the component's fields. |
| `metadata` | `ComponentMetadata` | Field presentation and component metadata, forwarded to the component ([Editable state](#editable-state)). |
| `schedule` | `Schedule` | Phase the lifecycle system runs in. Default `Schedule.Update` ([Schedule](#schedule)). |
| `touches` | `SystemTouches` | Components reached through `ctx.get` / `ctx.set` ([Declaring accessed components](#declaring-accessed-components)). |
| `start` / `update` / `destroy` | functions | Lifecycle hooks ([Lifecycle](#lifecycle)). |

The behaviour is attached by inserting its component, optionally overriding the initial `state`:

```typescript
import { defineSystem, Commands, Transform } from 'esengine';

const spawn = defineSystem([Commands()], (cmds) => {
  cmds.spawn()
    .insert(Transform, { position: { x: 0, y: 0, z: 0 } })
    .insert(Patrol, { speed: 120 });   // per-instance override
});
```

In the editor a behaviour is added to an entity through **Details → Add Component** (category **Scripts**), and its `state` fields are edited
there. A behaviour appears in the editor only when it is reachable from the project's declaration entry
([Script Modules](/docs/scripting/script-modules/#declaration-entry)).

## Lifecycle

Each hook is optional.

| Hook | When it runs |
|---|---|
| `start(ctx)` | Once, in the frame the behaviour's component first appears on an entity. |
| `update(ctx, dt)` | Every frame, for each entity carrying the behaviour. `dt` is the frame delta in seconds (equal to `ctx.time.delta`). |
| `destroy(ctx)` | Once, when the component is removed **or** the entity is despawned. |

```typescript
export const Enemy = defineBehavior('Enemy', {
  state: { hp: 100 },
  start(ctx) {
    // one-time setup: initialize state, cache lookups, spawn a health bar
  },
  update(ctx, dt) {
    if (ctx.self.hp <= 0) ctx.commands.despawn(ctx.entity);
  },
  destroy(ctx) {
    // runs whether the entity was despawned or the component was removed
  },
});
```

`destroy` is driven by the entity's **presence** in the behaviour's query: it runs in the frame an entity leaves the
query, regardless of which system removed it or in what order.

## The context

Every hook receives a `BehaviorContext` for the entity it runs on:

| Member | Type | Description |
|---|---|---|
| `ctx.self` | `S` | The behaviour's own `state`. Mutations persist. |
| `ctx.entity` | `Entity` | The entity this instance is attached to. |
| `ctx.time` | `TimeData` | Frame timing: `delta`, `elapsed`, `frameCount`, `fixedDelta`. |
| `ctx.input` | `InputState` | Keyboard, mouse, touch and gamepad ([Input](/docs/scripting/input/overview/)). |
| `ctx.commands` | `Commands` | Deferred spawn, despawn and insert; safe during iteration. |
| `ctx.world` | `World` | The world, for access to other entities. |
| `ctx.get(Comp)` | `ComponentData` | Reads another component on **this** entity. |
| `ctx.set(Comp, data)` | `void` | Writes a component on **this** entity. |
| `ctx.has(Comp)` | `boolean` | Whether this entity has `Comp`. |

<Aside type="caution">
  **Engine components are returned as copies.** For a script component (a `defineComponent`, and `ctx.self`),
  `ctx.get` returns the stored object, so mutating it persists. `Transform`, `Sprite`, `RigidBody2D` and every other
  C++-backed component are decoded from the WebAssembly heap on each read; mutating the result has no effect. Read
  the value, change it, and write it back with `ctx.set`.
</Aside>

```typescript
import { defineBehavior, Transform } from 'esengine';

export const PlayerController = defineBehavior('PlayerController', {
  state: { speed: 200, facing: 1 },
  update(ctx, dt) {
    const move = (ctx.input.isKeyDown('KeyD') ? 1 : 0) - (ctx.input.isKeyDown('KeyA') ? 1 : 0);
    if (move !== 0) ctx.self.facing = move;        // mutating self persists
    if (move !== 0) {
      const t = ctx.get(Transform);                // a copy — Transform is C++-backed
      t.position.x += move * ctx.self.speed * dt;
      ctx.set(Transform, t);                       // written back
    }
  },
});
```

<Aside type="caution">
  The `ctx` object is **reused** across entities and frames. It is valid only during the hook call; storing it, or
  its `self`, `time` or `input`, in a closure or collection for later use reads another entity's data. Copy the values
  needed instead.
</Aside>

## Editable state

The `state` object defines the component's fields and defaults. `metadata` controls their presentation in the Details
panel — ranges, steps, units, enums, categories — with the same field metadata as any
[component](/docs/core-concepts/components/#field-metadata):

```typescript
export const Turret = defineBehavior('Turret', {
  state: { range: 300, fireRate: 2, target: 0 },
  metadata: {
    fields: {
      range: { min: 0, unit: 'px', category: 'Targeting' },
      fireRate: { min: 0, unit: '/s', category: 'Targeting', tooltip: 'Shots per second.' },
    },
  },
  update(ctx, dt) { /* … */ },
});
```

The state is a serialized component: per-entity values are saved with the scene and edited live in the Details panel.

## Schedule

The lifecycle system runs in `Schedule.Update`, once per frame, by default. `schedule` selects another phase, for
example `Schedule.FixedUpdate` to step with physics:

```typescript
import { defineBehavior, Schedule } from 'esengine';

export const Thruster = defineBehavior('Thruster', {
  schedule: Schedule.FixedUpdate,
  state: { force: 500 },
  update(ctx) {
    // fixed cadence; ctx.time.fixedDelta is the fixed step
  },
});
```

Available phases: `Startup`, `First`, `PreUpdate`, `Update`, `PostUpdate`, `Last`, and `FixedPreUpdate` /
`FixedUpdate` / `FixedPostUpdate` ([Schedules](/docs/core-concepts/systems/#schedules)).

### Declaring accessed components

Components reached through `ctx.get` / `ctx.set` are not visible to the scheduler. Without a declaration the behaviour
is treated as opaque and conflicts with every other system. `touches` names them so the behaviour can be ordered and
run alongside other systems ([Declared access](/docs/core-concepts/systems/#declared-access)); the behaviour's own state
component is already declared:

```typescript
export const Drifter = defineBehavior('Drifter', {
  state: { speed: 60 },
  touches: { reads: ['Transform'], writes: ['Transform'] },
  update(ctx, dt) { /* … */ },
});
```

## Behaviours and systems

`defineBehavior` suits logic that is naturally **per entity**: a patrol, a projectile, a pickup. A plain
[system](/docs/core-concepts/systems/) suits processing a whole query at once or coordinating several entities.

The hook context — `entity`, `world`, `commands` and `self` — is the same programming model used by the
[Gameplay AI](/docs/gameplay/ai/overview/) actions and behaviour-tree leaves, so logic moves between a behaviour and an
AI action without restructuring.
