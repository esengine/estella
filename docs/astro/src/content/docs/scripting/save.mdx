`SaveManager` stores named save slots as versioned envelopes (`{ version, data, savedAt }`). Each save records the
schema `version` it was written with, so a game can change its save format and still read older saves: on load, older
data is migrated forward.

## Save slots

A game creates one manager with its current schema `version` and reads and writes slots by name:

```typescript
import { SaveManager } from 'esengine';

const saves = new SaveManager({ version: 1 });

saves.save('slot1', { level: 3, score: 1200, hp: 80 });

const data = saves.load<{ level: number; score: number; hp: number }>('slot1');
// -> { level: 3, score: 1200, hp: 80 }   (null if the slot is empty)

saves.has('slot1');       // true
saves.savedAt('slot1');   // epoch ms when the slot was written, or null
saves.remove('slot1');    // deletes the slot
```

| Method | Description |
|---|---|
| `save(slot, data)` | Writes `data` with the current version and time. |
| `saveAsync(slot, data)` | As `save`, and resolves when the write is flushed ([Asynchronous writes](#asynchronous-writes)). |
| `load(slot)` | Returns the slot's data, migrated to the current version, or `null` when the slot is empty or unreadable. |
| `has(slot)` | Whether the slot exists. |
| `remove(slot)` | Deletes the slot. |
| `savedAt(slot)` | Time the slot was written (epoch ms), or `null`. |

| `SaveManagerOptions` | Type | Default | Description |
|---|---|---|---|
| `version` | `number` | — | Current schema version. Required. |
| `migrations` | `Record<number, SaveMigration>` | — | Migration steps ([Schema migration](#schema-migration)). |
| `keyPrefix` | `string` | `'save:'` | Namespace of the manager's slots in the store. |
| `storage` | `SaveStorage` | platform `Storage` | Injected store, for tests. |
| `now` | `() => number` | `Date.now` | Clock for `savedAt`, for deterministic tests. |

## Schema migration

When the save format changes, `version` is incremented and a migration is added for each step. `migrations[n]`
upgrades a save written at version `n` to `n + 1`; on load, every step from the save's version to the current one runs
in order:

```typescript
const saves = new SaveManager({
  version: 2,
  migrations: {
    // v1 stored a flat score; v2 nests it under `stats`.
    1: (old) => {
      const s = old as { level: number; score: number };
      return { level: s.level, stats: { score: s.score, deaths: 0 } };
    },
  },
});

// A v1 save is upgraded to the v2 format on load.
const data = saves.load('slot1');
```

Migration is **forward-only**. Loading a save newer than the current version throws, and a missing step in the chain
throws as well.

`migrateSaveData(version, data, currentVersion, migrations)` exposes the migration chain as a pure function, for
migrating data outside a `SaveManager` (unit tests, one-off imports).

## Key/value storage

`Storage` is a per-platform key/value store with typed helpers, for flags and preferences that need no versioning:

```typescript
import { Storage } from 'esengine';

Storage.setBoolean('muted', true);
Storage.setNumber('volume', 0.8);
Storage.setJSON('keybinds', { jump: 'Space', fire: 'KeyJ' });

Storage.getBoolean('muted', false);   // true
Storage.getNumber('volume', 1);       // 0.8
Storage.has('keybinds');              // true
```

| Group | Members |
|---|---|
| Typed access | `getString` / `setString`, `getNumber` / `setNumber`, `getBoolean` / `setBoolean`, `getJSON` / `setJSON` |
| Keys | `has(key)`, `remove(key)`, `clear()` |
| Flushing | `flush()` |

`SaveManager` is built on `Storage`, so both use the same backing store.

<Aside>
  Reads and staged writes are synchronous. An asynchronous host may keep writes pending until its storage service
  acknowledges them. Saves hold game state, not bulk assets, and must stay within the target's storage limit.
</Aside>

## Asynchronous writes

Where progress must be confirmed as saved, the write is awaited:

```typescript
await saves.saveAsync('slot1', { level: 4, score: 1500, hp: 80 });
// Or after several Storage writes:
Storage.setNumber('completedLevels', 4);
await Storage.flush();
```

- Both reject when staging a write or the host's flush fails. After a failed cloud request the latest in-memory data
  may still be readable; it is not saved until a retried `Storage.flush()` succeeds.
- `SaveManager.saveAsync` writes the same versioned envelope and follows the same migration rules as `save`.
- An asynchronous platform adapter implements `PlatformAdapter.flushStorage()` and must load existing data before
  accepting writes. An adapter that stores one cloud blob serializes requests and preserves newer changes while an
  earlier save is in flight. A failed or unsupported load must not be treated as an empty save.
- On a synchronous adapter, awaiting `flush()` completes the existing write; it does not add cloud storage or confirm
  a provider's cloud backup. CrazyGames SDK Data, for example, schedules its backup separately from `setItem`.

## Backing stores

`Storage` provides no file-system path; the web and mini-game platforms have no path namespace. Each platform's
durable store is used:

| Platform | Backing store |
| --- | --- |
| Web | `localStorage` |
| WeChat and other mini-games | `wx.setStorageSync` and related APIs |
| iOS | `Application Support/estella-storage.json` |
| Android | `files/estella-storage.json` (the app's internal data directory) |
| Node | Memory only; does not persist beyond the process |

On iOS the file is kept in Application Support because the system may empty Caches to reclaim space. Both mobile
locations are private to the app and included in the device backup.

Builds earlier than Estella 0.41 kept the file in the cache directory. On the first launch of a newer build, an
existing file there is moved to the current location.

`platformReadFile()` does not access these stores. It reads files packaged into the build (the APK's `assets/`, the
iOS app bundle) and is read-only.
