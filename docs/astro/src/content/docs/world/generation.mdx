`esengine/worldgen` lays out a world from rules as it is explored: continuous biomes, groups composed by artists,
clearings and roads kept open, large objects placed before small ones. The layout is deterministic: it is the same on
every machine and independent of the order in which its chunks are requested.

Responsibilities are divided as follows:

| Party | Provides |
|---|---|
| Engine | Samples the fields, weighs the biomes, places groups layer by layer, keeps zones clear, gives every placement a stable id and streams the result in chunks. |
| Game | The rules: which biomes exist, what stands in them, what is reserved for a home or a road. |
| Artists | The recipes: a grove, a rock group, a strip of reeds along a shore. |

## The WorldGen component

| Field | Default | Description |
|---|---|---|
| `rules` | `''` | The rules the world is laid out by: a `.esworld` file, or the id of rules registered with `registerWorldRules`. |
| `version` | `1` | The version of the rules the world was made with. A saved world keeps it; rules that no longer have that version fail the world (its status gives the reason) instead of laying out a different one. |
| `world` | `''` | The world (a planet, a level) as the game names it. |
| `seed` | `1` | The world's seed. Another seed lays out another world by the same rules. |
| `paintGround` | `true` | Whether the biomes paint the terrain. |
| `surface` | `Plane` | `Plane` lays the world out over a `Terrain`; `Planet` means the entity is also a `Planet` and the world is laid out over its six faces. |
| `seaLevel` | `0` | Shown for `Planet`: the height of the sea above the planet's radius. Ground below it is under water. |
| `groundStep` | `1.5` | Shown for `Planet`: how far apart the ground is read under placements, in the planet's units. Larger values lay out faster and follow the ground less closely; layout cost falls with the square of this value. |

What the rules place is published as the entity's children around the
[streaming sources](/docs/world/streaming/#streaming-sources) (or the camera), as
[procedural chunks](/docs/world/streaming/#procedural-chunks).

## Rules

Rules are data: biomes, the recipes that stand in them, and the layers they are placed in. They are stored in a
**`.esworld` file** (in the editor, **New → New World Rules**, or open an existing file from the content browser) and
referenced from the WorldGen's `rules` field.

- The World Rules editor lists the file's biomes, recipes and layers, edits each with a form (meshes and materials
  picked like any asset), and reports below them whether the engine accepts the rules as they stand.
- Saving the file lays the open world out again, in the editor and in a running game.
- The file is the JSON accepted by `registerWorldRules` and is validated on load. A file that references a recipe or
  layer it does not define, or omits required content, fails the WorldGen with the location of the error.

{/* SHOT: world-generation-rules-editor | World Rules editor of examples/worldgen with assets/worlds/wilds.esworld open: the biome, recipe and layer lists, one recipe's form expanded, and the validation line below */}

Rules can also be registered from code, which is how a game adds its own fields (functions are not data):

```ts
import { registerWorldRules } from 'esengine/worldgen';

registerWorldRules({
    id: 'mygame:wilds',
    versions: [1],
    biomes: [
        { id: 'forest', conditions: [{ field: 'moisture', min: 0.52, blend: 0.08 }, { field: 'up', min: 0.82, blend: 0.05 }],
          transition: 120, paint: [0.55, 0.45, 0, 0], paintStrength: 0.5,
          recipes: [{ recipe: 'grove', layer: 'groups', density: 0.75 }] },
        // …
    ],
    recipes: [
        { id: 'grove', version: 1, tags: ['tree'],
          anchor: { id: 'elder', mesh: 'assets/models/pine.esmesh', material: 'assets/materials/pine.esmaterial', scale: [1.4, 1.8], footprint: 10, canopy: 35 },
          members: [
              { id: 'pine', mesh: 'assets/models/pine.esmesh', count: [3, 6], ring: [45, 110], scale: [0.9, 1.3], footprint: 8 },
              { id: 'sapling', mesh: 'assets/models/pine.esmesh', count: [2, 5], ring: [110, 170], scale: [0.35, 0.6], footprint: 4, chance: 0.8 },
          ] },
    ],
    layers: [
        { id: 'groups', spacing: 260, drawDistance: 4200, chunkSize: 512 },
        { id: 'detail', spacing: 90, drawDistance: 2400 },
    ],
});
```

### Fields

Every decision is made from **fields**: numbers that can be read at any world position.

| Field | Source |
|---|---|
| `height`, `up`, `slope` | The terrain surface. `up` is how much the ground faces up. |
| `paint.<layer>` | How much of the ground is that terrain layer, named by its file: `paint.grass` for `grass.esterrainlayer`. Without layer files: `paint.grass`, `paint.dirt`, `paint.snow` and `paint.rock`. |
| `waterDepth`, `shoreDistance` | The water. `shoreDistance` is how far a dry point is from the water's edge, negative on the water. |
| `moisture`, `temperature`, `rock` | Seeded noise that varies slowly across the world; their scales are the rules' `noise`. |

A game adds its own fields with `fields: { name: (x, z, at) => number }`, reading the built-in fields from `at`. A rules
file declares additional noise fields in `noise` (`{ "turf": { "scale": 1400, "octaves": 2 } }`), which any condition
can read by name. A zone can set any field over its area. Fields are evaluated lazily: a field no condition reads is
never computed.

### Biomes

A biome is a weight over the fields. Each condition is a band of one field (`min`, `max`) whose edges fade over `blend`;
the conditions multiply.

- Where several biomes hold, their weights are mixed: a candidate takes a biome by the weights at its position, so two
  biomes meet in a mixed band, not a line. `transition` makes the edge wander by that many world units of noise.
- `paint` (grass, dirt, snow, rock) pulls the terrain's own paint toward the biome's, by its weight and `paintStrength`.
- A biome lists its recipes, each with the layer it is placed in and its `density`: the share of that layer's candidates
  it takes.

A candidate takes **one biome by weight, then that biome's recipe in the layer being laid out**. A biome therefore lists
a recipe in every layer it should appear in; a biome with no recipe for a layer leaves the candidates that chose it
empty. Biome weights mix biomes where they overlap but do not thin a biome out; density is set by the recipe's
`density` and the layer's `spacing`.

### Recipes

A recipe is a group: an **anchor** and **members** placed around it. `version` is part of every placement's id;
increment it when a recipe places something different.

| Member field | Description |
|---|---|
| `mesh`, `material` | Asset paths, or handles already loaded. Alternatively `plant` names an entry in the rules' `plants`. |
| `count` | How many to place. |
| `ring`, `arc` | Distance range from the anchor, and allowed angles. |
| `scale` | Scale range. |
| `footprint` | The ground it occupies (a trunk). |
| `canopy` | How far it spreads overhead (a crown), separate from `footprint`. |
| `attach` | Whether it stands upright or follows the ground's slope. A member that names a `plant` follows it too: a stone lies as the slope lies. |
| `minUp` | Steepest ground it may stand on. |
| `waterDepth` | How deep in water it may stand. |
| `chance` | Probability it is placed at all. |
| `tags` | Tags a zone's `excludes` can name. |
| `far` | Its far version: the rectangle of its texture shown on two crossed cards (or a tent of cards for a conifer), drawn beyond its layer's `lodDistance`. |
| `interactive` | Makes the member an entity of its own ([Interactive placements](#interactive-placements-and-changes)). |
| `grounding`, `scaleFootprint` | Base fitting for buildings ([Building bases](#building-bases)). |

A member that cannot stand (no ground, too steep, under water, excluded by a zone, on something placed before it) is
omitted; the rest of the group stands.

### Plants

A member names either a mesh and a material, or a **plant**: an entry in the rules' `plants` for what a mesh and a
material cannot express.

- `parts`: a trunk and a crown are two parts, each with its `mesh`, a cheaper `lod1Mesh`, `material`, `texture`, `tint`,
  whether it is `opaque`, `soft` (for a card standing for a crown: the share by which its normals are turned toward up,
  so it is lit as a rounded crown rather than a flat board), and `castShadows` (`false` for ground cover too small to be
  worth a shadow-map draw).
- `lodDistance`: beyond it the cheaper meshes are drawn. `drawDistance`: beyond it the plant is not drawn as itself.
- `far`: the far version (a tree's crossed cards, baked to an atlas of their own), drawn from `drawDistance` out to
  `farDistance`.

Optional plant fields:

| Field | Description |
|---|---|
| `tints`, `tintScale` | Colourings for the plant (linear multipliers on its colour), and how many world units a stand spans. A position takes one tint by slow noise, so a wood has warm and cool stands without speckle. |
| `farKeep` | Share of the plants the far version draws (above 0 to 1; default 1). The others are omitted and the kept ones enlarged to preserve cover. A plant without cards may use its cheaper mesh as `far` and thin it this way. Far versions are laid out in cells as wide as the shortest distance any of them is shown over allows (up to eight chunks), so distant ground cover is a few draws per cell rather than per chunk. |
| `sink` | Depth sunk into the ground, in world units (a stone's buried underside). |
| `unit` | World units per mesh unit: 100 for plants modelled in metres in a world of centimetres. A recipe's `scale` is then relative to the model. |

Plants are grown a cell at a time by the same machinery as [placed foliage](/docs/graphics/foliage/#placed-plants): a
chunk appears at once and fills in over the following frames, each mesh taking a few milliseconds of the frame budget.
The far versions form a layer of their own, laid out as far as the furthest of them reaches and shown beyond the
distance their kinds draw as themselves. A layer's `drawDistance` is therefore the distance its plants draw as
themselves, not how far the world is visible. A world on a terrain of finite area ends where the terrain ends.

### Layers

Layers are passes run in order, large objects first.

- Each layer takes one jittered candidate per cell of a grid `spacing` apart, with a random priority.
- Of two candidates whose groups would overlap, the higher priority stands.
- Every candidate keeps clear of the footprints of earlier layers, so a fern does not grow through a trunk and a stone
  does not sit inside a boulder.
- A layer is published in chunks of `chunkSize` out to `drawDistance`.
- `occupies: false` makes a layer that later layers may overlap (ground cover).
- `farSpacing` (default 1) plans the far versions of a layer's plants that much further apart. Ground cover whose far
  versions keep a quarter of the plants is planned at 2, so only a quarter of the candidates are evaluated.

## Zones

A zone (the `WorldZone` component) plans an area by hand: a home, a road, a landing site, a building's footprint, a
view kept open. It follows its entity's position and its rotation about the vertical.

| Field | Default | Description |
|---|---|---|
| `kind` | `reserve` | What the zone is for, in the game's own terms (home, road, landing, building, resource, view). |
| `shape` | `Circle` | `Circle` or `Box`. The editor draws the outline. |
| `radius` | `10` | Circle radius, world units. |
| `sizeX`, `sizeZ` | `20`, `20` | Box size along its own x and z; the box turns with the entity about the vertical. |
| `falloff` | `4` | World units past the outline over which the zone fades: what it excludes thins there instead of stopping at a line. |
| `priority` | `0` | Where zones overlap, the higher priority holds the biome. |
| `excludes` | `*` | Tags of what it keeps out, comma-separated: a layer, a recipe, a recipe's or member's tags, `decor`, `interactive`. `*` is everything; empty keeps nothing out. |
| `biome` | `''` | A biome held over the zone's area; empty holds none. |
| `flatten` | `false` | Levels the terrain under the zone to the ground height at its centre, blending back over `falloff`: a plot to build on. In code, `flatten` is a world height or `'ground'`. |

![Details of a World Zone: kind, shape, radius, falloff, priority, excludes, biome and flatten](@/assets/guides/en/details-worldzone.png)

*A **World Zone**: a circle that tells the generator which biome to grow inside it.*

A game adds zones as it plans and as the player builds:

```ts
const gens = app.getResource(WorldGenRes);
gens.zones().set({ id: 'house 1', kind: 'building', shape: { type: 'rect', x, z, halfX: 40, halfZ: 30, yaw },
    falloff: 12, priority: 20, excludes: ['*'] });
```

Only the chunks a zone reaches are remade, each keeping its old version until the new one replaces it.

- **Identity.** Authored zones are identified by the scene name and the document entity id, so reloading the same scene
  with the same seed preserves the falloff pattern. The plugin enables scene-origin recording before scenes load.
  Entities created by game code have a runtime identity; use `gens.zones(world).set()` with a stable `id` when their
  zones must survive a reload.
- **Sharing.** Generators of the same named world share zones and receive changes independently. Authored projections
  are removed when their entities disappear or the world's last generator leaves. Game-added zones and `PlacementDiffs`
  remain available to later generators; terrain flattening and biome paint are released with their last active consumer.
- **Observing.** `zones.subscribe(listener)` and `diffs.subscribe(listener)` observe changes without replacing another
  consumer; call the returned function to stop.

## Building bases

An upright recipe member can set `grounding: { size: [width, depth], samples: 5, mode: 'highest', maxRelief: 2 }`.

- `size` is in model units. Yaw and scale are applied before the corners, edges and interior are sampled. `samples`
  (the grid side) may be 3, 5, 7 or 9.
- Every sample must have ground and satisfy `minUp` and `waterDepth`. `maxRelief` rejects excessive height variation,
  in world units.
- `mode` chooses the base height: `highest` (default), `lowest`, `mean` or `center`; `offset` is then added, in scaled
  model units.
- `Placement.grounding` reports the height range, support depth and burial depth.

This is finite-grid support checking, not terrain flattening: use a foundation deep enough for the accepted relief, or a
flattening `WorldZone` for an authored site.

The reservation always contains the whole fitted base. `scaleFootprint: true` also treats `footprint` and `canopy` as
model-unit radii; without it they are world units. The planner settles overlaps after choosing the deterministic scale
and base height. `stats` and `explain` report `relief` beside the slope, water, zone and overlap rejections. The World
Rules editor exposes these settings.

## Roads

```ts
import { setRoad } from 'esengine/worldgen';
setRoad(gens.zones('valley'), {
  id: 'camp-trail', points: [[0, 0], [40, -20], [80, -10]],
  width: 6, clearance: 2, falloff: 3, excludes: ['tree', 'grass', 'building'],
});
```

- `roadZones(options)` returns serializable rectangle and circle zones with continuous bends and round end caps.
- `setRoad(zones, options)` replaces one road's reservations, removing obsolete segments; `removeRoad(zones, id)`
  releases them.
- `points` are world `[x, z]` pairs (in a 2D world, `[x, y]`). Repeating the first point closes a loop. `width` is the
  travelled surface; `clearance` adds space on each side before the soft `falloff` edge.

These functions reserve space only; road meshes and grading are separate. Place the building layer before forest layers
so trees respect building footprints, and reserve authored building floors and entrances with `WorldZone`s for
`Foliage`.

## Interactive placements and changes

A member with `interactive` (`'ore'`, `'tree'`) becomes an entity of its own, carrying a `PlacedObject` with its
placement id and kind. Other members are decoration. `gens.objectOf(id)` returns the entity of a placement.

Ids are built from the layer, the grid cell, the recipe and the member, with their versions
(`groups@1:12,-3/grove@1/pine.2`), never from a position in a list. They do not change with the order chunks are made
in, or when a layer or a recipe is added later.

Player changes are kept separate from the generated world and applied over it before anything is shown:

```ts
gens.diffs().remove(id);                  // felled, mined: gone for good
gens.diffs().change(id, { yaw: 1.2 });    // moved, turned, scaled
save(gens.diffs().toJSON());              // what a save stores
gens.diffs().load(saved);                 // and reads back
```

A felled tree stays felled when its chunk is released and remade, and after a save is loaded. Structures the player
builds belong to the game; the zone a structure reserves keeps generation off its ground.

## Plan queries

`gens.plan()` answers for any position, loaded or not, with the same result as what is published. Servers, minimaps and
placement checks read it.

| Method | Returns |
|---|---|
| `placementsIn(x0, z0, x1, z1, layers?)` | Every placement whose group's anchor stands in the rectangle. |
| `biomeAt(x, z)` | The biome at the position. |
| `biomeWeights(x, z)` | Every biome's weight at the position. |
| `explain(x, z)` | Everything that decided what stands there: the fields, the biomes, the zones, and each layer's candidate in that cell with its rejection reason (`noBiome`, `density`, `noGround`, `slope`, `water`, `relief`, `zone`, `occupied`, `conflict`). |
| `stats(layer, x0, z0, x1, z1)` | How many candidates were placed, and how many were rejected for each reason. |

## Shipping

A `.esworld` file is followed like a material: the meshes and materials it references ship with the scene that
references it. Rules registered from code reference assets that no scene references, so a package would omit them;
declare their folders as always included in `.esengine/asset-groups.json`:

```json
{ "version": "1.0", "groups": { "recipes": { "folder": "assets/models", "mode": "local", "alwaysInclude": true } } }
```

## 2D worlds

The same rules lay out a 2D world: there is no terrain, the plan is read flat over **x and y**, and the result is
published in chunks around the camera. The engine draws nothing; the game's `publish` callback decides what a placement
looks like (a sprite, a prefab) and how the ground is painted (a tile layer, a shader).

```typescript
import { registerWorldRules, createWorld2D } from 'esengine/worldgen';

registerWorldRules(rules);                        // biomes, recipes and layers, as above
const world = createWorld2D(app, 'island', {
    rules: rules.id, seed: 11, chunkSize: 512, cellSize: 32,
    publish(chunk) {
        // chunk.placements: what stands here (id, recipe, member, biome, x, y, scale, interactive, footprint...)
        // chunk.biomeGrid: the biome of each cell of the ground, indexes chunk.biomes
        const spawned = spawnTilesAndSprites(chunk);
        return () => despawn(spawned);            // taking the chunk away
    },
});

world.diffs.remove(tree.id);                      // felled: only that chunk is made again, and it stays felled
```

- **Chunks follow the camera** (or the streaming sources), nearest first within the frame budget, and are released
  beyond `unloadRadius`. The world is a `ProceduralChunks` layer on the `'xy'` plane, so a world of any size holds a
  bounded number of chunks.
- **Order independence.** A chunk is a function of the seed, the rules and its position, so neighbours made earlier or
  later agree, a server and a client agree, and placement ids are stable across loads. A group (an anchor and its
  members) belongs to the chunk its anchor stands in.
- **Player changes** are a `PlacementDiffs`, applied over the plan before a chunk is shown; `diffs.toJSON()` and
  `diffs.load()` are the save.
- **Zones**: a `ZoneDef` whose `z` is world y keeps an area clear or holds it to a biome (a camp the player built).
- A recipe's `ring` is in world units and `arc` in degrees from +x toward +y. `mesh`, `material`, `attach` and `minUp`
  are 3D properties and are not read.

## Limits

- **Decoration is not instanced per placement.** Plant parts use shared geometry with per-instance level of detail.
  Members that name a mesh and a material are merged per mesh and material in each chunk: the renderer's instance
  records are written every frame, which for thousands of objects would upload megabytes per frame, while merged static
  meshes upload nothing and chunks bound their memory.
- **A game's own fields are code.** A rules file uses the built-in fields and those zones set; a field computed by the
  game is registered with the rules from code.
