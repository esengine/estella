A project is organized into scenes. All loaded scenes share one ECS world. The **`SceneManager`** resource loads,
switches and unloads scenes, records which scene owns each entity, and runs a scene's systems only while that scene is
active.

`sceneManagerPlugin` provides the `SceneManager` and `SceneStreaming` resources, loads the initial scene at startup,
and advances transitions and streaming every frame. The default app bootstrap registers it; an `App` assembled from
individual plugins must add it explicitly.

## Switching scenes

`switchTo` replaces the active scene. It is asynchronous and resolves when the switch, including any transition, has
completed.

```typescript
import { defineSystem, Res, SceneManager } from 'esengine';

const goToLevel2 = defineSystem([Res(SceneManager)], async (scenes) => {
  await scenes.switchTo('level2');
});
```

`switchTo` with the name of the active scene keeps it running. Use `reload(options?)` to restart it.
Both switching and reloading keep the current scene running while the destination
file, prefabs and assets are prepared. An unknown scene name, invalid file or rejected preparation leaves the same
entities, systems and scene-owned assets available. Fix the content and retry the switch or reload.

For a code-defined scene, put fallible reads and validation in `prepare`. When the switch starts a new instance,
successful preparation is followed by outgoing cleanup, creation of the destination entities and then `setup`.
At that point an exception in `setup` happens after the outgoing scene has been retired. If the destination is
already loading additively, the switch waits for that load to succeed before retiring the current scene.

Calling `load` or `loadAdditive` for a destination that is already switching joins the same load. Its progress
callback receives the current asset counts and subsequent updates while preparation continues.

## Transitions

`switchTo`, `reload` and `unload` take `TransitionOptions`.

| Option | Type | Default | Description |
|---|---|---|---|
| `transition` | `'none' \| 'fade'` | `'none'` | Hard cut, or fade through `color`. |
| `duration` | number | `0.3` | Total fade time in seconds: half fading out, half fading in (`RuntimeConfig.sceneTransitionDuration`). |
| `color` | `Color` | opaque black | Overlay colour (`RuntimeConfig.sceneTransitionColor`; the build config takes a hex string). |
| `onStart` / `onComplete` | callback | — | Called when the fade starts / after the fade-in finishes. |
| `keepPersistent` | boolean | `true` | Keep [persistent entities](#persistent-entities) through the unload. `false` destroys them with the rest of the scene. |
| `staggered` | boolean | `false` | Unload over several frames through the scene's retirement: hidden at once, destroyed within the frame budget, assets released afterwards. A load of the same name waits for it. |

A fade runs in three phases:

1. The overlay ramps to opaque over the first half of `duration`.
2. The overlay holds opaque while the destination is prepared and the scenes switch. A slow load extends this phase.
3. The overlay ramps back to transparent over the second half of `duration`.

The returned promise resolves after the fade-in completes and rejects if the load failed. A `switchTo` issued while a
switch is in progress is ignored and logs a warning; `isTransitioning()` reports whether a transition is running.

A load that is superseded before it commits — by an `unload`, or by another load of the same scene — rejects with
**`SceneLoadCancelled`** instead of committing a partially loaded scene. It signals a race, not a failure; handle it
separately from load errors in the `catch`.

### `transitionTo`

`transitionTo(host, scene, config)` performs a `switchTo` with a fade described by a `TransitionConfig`
(`type: 'fade'`, `duration`, optional `color`). `host` is the `App` (bootstrap code, menu handlers) or the
`SceneManager` resource state obtained from `Res(SceneManager)` inside a system.

```typescript
import { transitionTo, type TransitionConfig } from 'esengine';

const fadeToBlack: TransitionConfig = {
  type: 'fade',
  duration: 0.5,
  color: { r: 0, g: 0, b: 0, a: 1 },
};

async function onPlayClicked() {
  await transitionTo(app, 'levels/level1', fadeToBlack);
}
```

`examples/scene-flow` cycles a menu and two levels through `SceneManager` with a different fade on each switch.

## Additive scenes

`loadAdditive` loads a scene on top of the loaded ones without unloading them — a HUD, a pause menu, a streamed
region. It takes an optional progress callback and resolves to the scene's `SceneContext`.

```typescript
await scenes.loadAdditive('pause-menu', (loaded, total) => { /* progress */ });
// …
await scenes.unload('pause-menu');
```

## Ownership and system gating

Every entity a scene owns carries a `SceneOwner` component naming that scene. An entity is owned when it is loaded
from the scene file, spawned through `ctx.spawn()`, or adopted through `ctx.adopt(entity)`. Unloading a scene
despawns the entities it owns.

- An entity created outside any scene context has no owner, and no unload removes it. `ctx.adopt(entity)` assigns it
  to a scene.
- Prefabs instantiated at runtime are adopted by the active scene by default ([Prefabs](/docs/world/prefabs/#instantiate-reference)).
- Systems declared by a scene run only while that scene is active, so an additive HUD and the gameplay scene update
  independently.

A code-defined scene receives its context in `setup(ctx)`. Elsewhere, `getScene(name)` returns the context of a
loaded scene.

The scene manager gives each instance its own `ctx.signal`. Pass it to asynchronous work such as
`fetch(url, { signal: ctx.signal })` to cancel that work when the instance unloads, its setup fails,
or its world resets. Pausing or sleeping the scene keeps the signal live.

Preloading a scene can fetch its 2D or 3D physics module. The first scene to publish with that solver
installs it with its world settings. Discarding a preload releases its acquired scene assets immediately.
Other scenes waiting for the same module can finish using the shared read.

If a 2D or 3D scene binds text to a localization key, `prepare(name)` also reads its string tables.
The current scene keeps its captions and language while those reads run. Once the destination takes
ownership of its entities and assets, it adopts the prepared translations. `discardPrepared(name)`
releases the destination's table references, including when another scene shares the same read.

Two scenes can use the same image with different sampling. For example, a HUD sprite can use nearest
filtering without mipmaps while a 3D mesh uses linear filtering with mipmaps. If the image has no
project importer settings, each scene's `textureImporterSettings` applies to its own prepared assets.
Direct texture loads start using the destination's settings when it takes ownership. Discarding the
preload keeps the current scene's settings.

## Persistent entities

A switch despawns the entities owned by the outgoing scene. `setPersistent` marks an entity to survive the unload of
its scene — a player, a music source, a camera:

```typescript
import { defineSystem, Res, SceneManager } from 'esengine';

const keepPlayer = defineSystem([Res(SceneManager)], (scenes) => {
  const ctx = scenes.getScene(scenes.getActive()!);
  ctx?.setPersistent(player, true);
});
```

The flag is stored on `SceneOwner`, so it applies only to entities the scene owns. `SceneOwner` is an engine-internal
component excluded from the project component schemas; there is no Inspector field for it, and entities placed in the
editor are marked persistent from code at runtime.

On unload, a persistent entity survives and is **promoted to global**: `SceneOwner.scene` is set to `''`, the
"always active" value. Scene-gated consumers — the camera render filter, system gating and draw-callback gating —
therefore keep treating it as active. `keepPersistent: false` on `switchTo` or `unload` destroys persistent entities
as well.

What a promoted entity keeps:

- **Its assets.** Promotion splits the scene's asset references; the entity holds what it draws with and releases it
  when it is despawned, including as part of a parent's subtree. A texture, material, font, mesh or environment stays
  the exact instance the entity is bound to, even after a hot update replaced the file. An anim clip, timeline, state
  machine, behavior tree or animator controller is referenced by name and looked up every frame, so the entity
  follows updates to that entry.
- **Its on-screen placement.** An entity detached from a parent that did not survive keeps its world position.

What it does not keep:

- **The scene's systems.** Every system a scene declares is unregistered on unload. Behaviour of a persistent entity
  must come from systems registered on the `App`.
- **Undeclared assets.** Promotion reads the components' declared `assetFields`. An asset loaded manually and assigned
  outside a declared field is not tracked; hold a reference that outlives the scene (`Assets.preload` at bootstrap, or
  an additive scene that is never unloaded).
- **Non-persistent children.** Persistence applies to the entity, not its subtree. Unmarked children are despawned
  with the scene; a persistent child of a non-persistent parent is detached and survives alone.

Game state that does not need a live entity (score, inventory, quest flags) belongs in
[saves](/docs/scripting/save/).

## Scene streaming

The **`SceneStreaming`** resource loads and unloads **cells** — additive scenes placed in world space — around a focus
point:

```typescript
import { defineSystem, Res, SceneStreaming } from 'esengine';

const setupStreaming = defineSystem([Res(SceneStreaming)], (streaming) => {
  streaming.configure({ loadRadius: 1200, unloadRadius: 1600 });
  streaming.register({ scene: 'cells/forest',  x: 0,    y: 0, radius: 800 });
  streaming.register({ scene: 'cells/village', x: 1500, y: 0, radius: 800 });
  streaming.setFocusEntity(player);          // or setFocus(x, y) each frame
});
```

- Each frame, cells within `loadRadius` of the focus load additively and cells beyond `unloadRadius` unload. The gap
  between the two radii is hysteresis that prevents repeated loads at a border.
- Distances are measured to the **cell edge** (centre distance minus `radius`), so a large cell begins loading while
  its centre is still far away.
- With `policy: 'sleep'`, out-of-range cells are put to sleep instead of unloaded: their entities stay in memory,
  disabled and hidden, and re-entering is immediate at the cost of memory.
- A cell with a load or unload in flight is not issued again. If the focus has left by the time a load resolves, the
  cell is released again.
- Cell scenes are ordinary project scenes referenced by name ([Scenes in a build](#scenes-in-a-build)).

The resource is a `SceneStreamingController`, which orchestrates the `SceneManager` primitives (`loadAdditive`,
`unload`, `sleep`, `wake`) and performs no loading of its own. With no cells registered, `update()` does nothing.

| `SceneStreamingController` | Description |
|---|---|
| `configure({ loadRadius, unloadRadius, policy? })` | Sets the radii (`unloadRadius` is clamped to at least `loadRadius`) and the out-of-range policy: `'unload'` (default) or `'sleep'`. |
| `register(cell)` / `unregister(scene)` / `clear()` | Manage the cell set; a cell is `{ scene, x, y, z?, radius }`. |
| `setFocus(x, y, z?)` | Sets the focus point (call every frame). Distance is measured in 3D; `z` and a cell's `z` default to 0. |
| `setFocusEntity(entity)` / `getFocusEntity()` | Follow an entity; the streaming system reads its `Transform` each tick (play mode only). |
| `getActive()` | Scene names currently held in range. |
| `update()` | Reconciles resident cells against the focus. `sceneManagerPlugin` calls it every frame. |

The threshold computation is exported as the pure function
`computeStreaming(cells, focusX, focusY, loadRadius, unloadRadius, active)` for tests and custom schedulers. Large
worlds built from streamed cells are covered in [World Streaming](/docs/world/streaming/).

## Scenes in a build

Every scene in the project's scenes folder is exported and registered as a `switchTo` target. A scene's **name** is
its path relative to the scenes folder without the `.esscene` extension: `assets/scenes/levels/boss.esscene` is
`switchTo('levels/boss')`. The startup scene loads eagerly; other scenes are fetched on their first load, so they do
not add to the initial download. Play in the editor registers the same set: the entry scene plus every other scene
file, loaded lazily by path.

Scenes unticked in the Package dialog's **Scenes in build** list are excluded from the export and remain editable and
playable in the editor. Playable-ad builds contain the startup scene only. See
[Building & Exporting](/docs/publishing/overview/).
## `SceneManager` reference

| Method | Description |
|---|---|
| `switchTo(name, options?)` | Replace the active scene (async; optional transition). |
| `load(name, onProgress?)` | Load or resume the named scene and make it active. Other loaded scenes stay resident. |
| `reload(options?)` | Switch to the active scene again, from its file (async; optional transition). |
| `loadAdditive(name, onProgress?)` | Load a scene on top of the loaded ones; resolves to its context (async). |
| `unload(name, options?)` | Unload a scene (async; optional transition). |
| `getScene(name)` | A loaded scene's `SceneContext` (`spawn` / `adopt` / `despawn` / `setPersistent` / draw callbacks / post-process binding), or `null`. |
| `getActive()` | The active scene name, or `null`. |
| `getActiveScenes()` | All active scene names, additive scenes included. |
| `pause(name)` / `resume(name)` | Suspend / resume a loaded scene's updates. |
| `sleep(name)` / `wake(name)` | Suspend **and hide** a scene's entities; they stay in memory and waking restores them immediately. |
| `isLoaded(name)` / `isActive(name)` | Whether a scene is loaded / active. |
| `isPaused(name)` / `isSleeping(name)` | The suspension states above. |
| `isTransitioning()` | `true` while a transition is running. |

## Serialization and migration

`SceneData` is plain JSON, and the functions the editor and runtime use to read and write it are exported. Typical
uses: saving a snapshot of the live world (a checkpoint that holds more than the
[save-game API](/docs/scripting/save/)), loading player-generated or downloaded scenes, and serializing components
whose state does not fit their plain fields.

| Function | Description |
|---|---|
| `serializeScene(world, name?)` | Produces a `SceneData` from the live world. Hierarchy is written to each entity record's `parent` / `children` fields. Runtime-only projection entities that their systems re-derive (tile colliders and similar) are excluded. |
| `loadSceneWithAssets(world, data, options?)` | Preloads every referenced asset, then spawns (async). |
| `loadSceneData(world, data)` | Spawns synchronously without asset resolution. |
| `findEntityByName(world, name)` | Finds a spawned entity by name. |

Both loaders return a map from serialized entity ids to live entities.

```typescript
import { defineSystem, GetWorld, Res, Assets, serializeScene,
         loadSceneWithAssets, findEntityByName, MissingAssetsError } from 'esengine';

const checkpoint = defineSystem([GetWorld(), Res(Assets)], async (world, assets) => {
  // Save: snapshot the live world as scene JSON.
  const data = serializeScene(world, 'checkpoint');
  localStorage.setItem('checkpoint', JSON.stringify(data));

  // Load: preload assets, then spawn. Older formats are migrated automatically.
  try {
    await loadSceneWithAssets(world, JSON.parse(localStorage.getItem('checkpoint')!), {
      assets,
      abortOnMissingAssets: true,        // throw instead of spawning with missing assets
      onMissingAssets: (missing) => {    // called once per load (the list may be empty)
        for (const m of missing) console.warn(`${m.ref}: ${m.reason}`);
      },
    });
  } catch (e) {
    if (e instanceof MissingAssetsError) { /* e.missing lists the missing assets */ }
  }

  const player = findEntityByName(world, 'Player');
});
```

### `SceneLoadOptions`

| Option | Description |
|---|---|
| `assets` | The `Assets` resource. Enables asset preloading and prefab-instance expansion before spawning. |
| `assetBaseUrl` | Base URL against which asset paths are resolved. |
| `onProgress` | `(loaded, total)` preload progress callback. |
| `onMissingAssets` | Called once with every reference that failed to resolve or load (`MissingAsset[]`: `ref`, optional `type`, `reason: 'unresolved' \| 'load-failed'`). Called even when the list is empty. |
| `abortOnMissingAssets` | Default `false`: missing assets get handle `0` and the scene loads. `true` throws `MissingAssetsError` after preloading, before anything is spawned. |
| `collectAssets` | Sets to which the load adds the acquired asset keys, so the caller (normally the scene manager) can release them on unload. |

### Format versions

Scene files carry a `version`; the current format is `SCENE_FORMAT_VERSION = 4`. `migrateSceneData(raw)` upgrades
older data to the current format:

- It returns a migrated deep copy and never mutates its input.
- It is idempotent.
- It drops component types retired by engine upgrades.
- It rejects data newer than the engine.

Every loader runs it internally. Call it directly only to inspect `migrated` / `fromVersion`, for example to prompt a
re-save of an upgraded file:

```typescript
import { migrateSceneData } from 'esengine';

const { data, migrated, fromVersion } = migrateSceneData(raw);
if (migrated) console.log(`upgraded scene from format ${fromVersion}`);
```

### Out-of-band component state

A component whose full state does not fit its plain field record registers a **`SceneComponentCodec`**, so the
generic serializer carries the extra state without component-specific code. `TilemapLayer` uses one for its tile
chunks, which live in the C++ core.

```typescript
import { registerSceneComponentCodec } from 'esengine';

registerSceneComponentCodec('MyVoxelChunk', {
  exportData(entity, data) { data.chunks = myStore.serialize(entity); },
  outOfBandFields: ['chunks'],          // stripped before the component is inserted
  importData(entity, outOfBand) { myStore.restore(entity, outOfBand.chunks); },
});
```

| Codec member | Role |
|---|---|
| `exportData(entity, data)` | On save, writes the extra state into the component record. |
| `outOfBandFields` | Record keys removed before the component is inserted on load. |
| `importData(entity, outOfBand)` | On load, receives the removed fields after the component is inserted. |

Registration is idempotent; a plugin registers its codecs at startup.

## `NodeVisibility`

`NodeVisibility.visible` is an animatable visibility gate over a subtree. Setting it to `false` masks the renderer
flag of every registered renderer component on the entity and its descendants; setting it back to `true` restores the
authored values. Scene serialization writes the authored values while the gate is closed. Cameras, physics bodies and
gameplay entities in the subtree remain active.

For a particle emitter the masked flag is `enabled`, so hiding a subtree also stops the emitters in it. An emitter
that must keep running belongs outside the hidden subtree.
