A scene loads whole. That is the right answer until the world is bigger than a
machine wants resident at once — and then the question stops being "what is
drawn" and becomes **"what exists"**. World streaming answers the second one: the
cook cuts an authored world into square cells, and at runtime a cell exists
because something is near it, and stops existing when nothing is.

Nothing about this is a visibility trick. A cell that leaves is destroyed: its
entities, its physics bodies, its navigating agents and its asset references all
go. That is the point — a place that is merely hidden still costs memory, still
collides, and still lets an enemy nobody can see attack the player.

## Declaring a streamed world

Two components, both authored in the scene:

```typescript
// On the world's settings entity: this scene is cut into 1000-unit cells.
world.insert(settings, StreamedWorld, { cellSize: 1000 });

// On everything that must never be streamed away.
world.insert(player, WorldPersistent, {});
world.insert(camera, WorldPersistent, {});
world.insert(sun, WorldPersistent, {});
```

Everything else is placed into a cell by **where its top-level entity stands**.
A scene with no `StreamedWorld` in it is not a streamed world and loads exactly
as it always did.

<Aside type="note">
`WorldPersistent` is not scene persistence. `SceneContext.setPersistent` decides
whether an entity survives a scene *switch*; `WorldPersistent` decides which
cooked scene an entity is written into, and therefore whether residency can
remove it at all.
</Aside>

## Asking for places: streaming sources

A cell exists because a **source** is near it:

```typescript
world.insert(player, WorldStreamingSource, {
    prefetchRadius: 3000, // cells this close are READIED, not brought in
    loadRadius: 2000,     // cells this close are brought in
    unloadRadius: 3000,   // resident cells are kept until past this
});
```

The three radii are in world units and default to the values above; the component also has an `enabled` switch (default on) that takes a source out of the union without removing it. `StreamedWorld.cellSize` defaults to 1000.

Several sources may exist, and what they ask for is **unioned** — a cell any one
of them needs stays resident. That is what makes split screen, a spectator
camera, a cinematic camera and an editor preview the same kind of thing rather
than four special cases. Nothing folds them into a single focus, because a fold
lets the last one written decide, and the frame after a second camera exists it
deletes the world the first is standing in.

Distance is measured to the cell's **box**, not its centre: to a centre, a source
standing on a diagonal corner reads the same as one a whole cell away, which is
where holes open along the diagonals of a grid.

### Readied before it is wanted

A cell inside `prefetchRadius` is **prepared**: its document is fetched, its
prefabs expanded, its assets acquired — and not one of its entities exists. So
nothing can observe it. No query returns it, no renderer draws it, no body
collides with it, no enemy in it decides anything, because there is nothing
there yet. Publication is the only thing that creates entities, and it happens
when a source actually reaches `loadRadius`.

That is worth about twenty milliseconds of a player's time. On Estella's own
fixture, walking into a readied place costs 0.6 ms; walking into an unreadied
one costs the fetching and decoding too.

Preparation is **speculation, never authority**. A cell readied for a player who
turns around is thrown away and its assets given back — never published because
it happened to be ready. And a preparation that finishes asks again whether the
cell is still wanted, rather than assuming the answer from when it started.

`prefetchRadius` is never used as less than `loadRadius`; beyond that it is not
ordered against `unloadRadius` at all. They answer different questions — how
early to get ready, and how late to let go.

### The band between the two radii

A cell comes in at `loadRadius` and only leaves once it is past `unloadRadius`.
The gap between them is the whole reason both exist: a source standing on a
boundary would otherwise spend every frame instantiating and destroying a place.
Set `unloadRadius` comfortably larger than `loadRadius` — half again is a good
starting point.

## What the cook produces

Partitioning happens at **cook time**, not at boot:

```
main.esscene ──cook──▶ main.esscene          the persistent world
                       world/main.world.json the manifest
                       world/main.cell_0_0.json
                       world/main.cell_1_0.json ...
```

The entry scene the package boots is what is left after the cells are taken out
of it — the things residency never removes. Cells are **not** switchable scenes:
they are content residency brings in, and a game never names one.

Cells are cut on one plane. By default that is the ground (world x and z): a cell is a vertical column, so a tower's floors are one place. A 2D world
lies in the screen plane, where every entity has the same z, so set `plane` to **Screen (x, y)** (`StreamPlane.Screen`) and the cells are cut along
world x and y instead; the streaming sources are then read by their x and y too. Without it a 2D world falls into one row of cells along x. The same
field, `plane: 'xy'`, is in the cooked manifest (`WorldManifest.plane`), and a cell's `z` is then world y.

## Far proxies

A cell that is not resident is not in the world, so without more a place past the load radius is not drawn at all. Tick
**Far proxies** on `StreamedWorld` and a build bakes each cell a stand-in: the cell's static, opaque meshes merged into one
draw per material and simplified, shown while the cell is absent.

```typescript
world.insert(settings, StreamedWorld, {
    cellSize: 1000,
    farProxies: true,
    farDistance: 8000,   // a cell this close to a source and not resident shows its proxy
    proxyError: 1,       // how far, in world units, a simplified surface may move
    proxyRatio: 0.01,    // the fewest triangles to aim for; proxyError keeps more wherever it must
});
```

The cook writes `world/<cell>.far.json` and its meshes beside the cell, and names them on the cell in the manifest
(`WorldCell.proxy`, with `WorldManifest.farDistance`). Prefab instances are expanded, so a building placed as a prefab
contributes its meshes. A surface is left out of the proxy when it is disabled or blended, skinned, a billboard, or when it or a
parent moves on its own (a character controller, a body that is not static, an animator). A mesh your own system moves, with none
of those, would be baked where it stands: put `ExcludeFromFarProxy` on it, or on the entity above it, and its whole subtree stays
out of the proxy while it is still drawn whenever its cell is in the world.

`proxyError` is what decides how far a cell simplifies: keep it below what a pixel covers at the distance the proxy starts (past
the sources' load radius). Surfaces that differ only in their colour share one draw, the colour carried by the vertices, and a
proxy carries no lightmap UV. In the `far-proxy-town` example (144 cells, 3.1 million triangles of static meshes), the proxies
keep 2% of the triangles at `proxyError` 0.5, and along its flight a frame draws 122 thousand triangles in 354 draws where the
town fully loaded draws 866 thousand in 620, with 0.3% of the pixels noticeably different.

The streamer hands over in both directions without a gap. Walking towards a cell, its proxy stays until the cell is in the world;
walking away, the cell stays until its proxy is. A proxy that fails to load does not hold its cell. `WorldStreamerStatus.proxyCells`
and the residency report list the cells drawn by their proxy.

Play makes the same proxies from the same cells, simplified by the same code a build uses, and keeps them in memory. It makes
each one when the streamer first asks for it, not before the game starts: in `far-proxy-town`, Play starts after 172 ms of naming
which cells have a proxy, and each proxy costs about 30 ms (at most 190) as it arrives.

## The rules a streamed world has to obey

**A subtree is the unit of residency.** Only top-level entities are placed, so a
door cannot be sorted away from its house even if the door's world position falls
in the next cell. A cell's box grows to cover its content, so a prop hanging over
the edge does not pop in at the boundary.

**Hard entity references may not cross a residency boundary.** Two entities in
one cell may reference each other; so may anything in the persistent world; and a
cell may reference the persistent world, which outlives it. A reference from one
cell into another — or from the persistent world into a cell — fails the build,
because either one points at something residency is entitled to delete.

**Residency owns existence; continuity is asked for.** A cell that unloads loses its
runtime state, and reloading rebuilds it from what was authored: an enemy you wounded
and walked away from comes back at full health. Put `RememberState` on what should not:

```typescript
world.insert(enemy, RememberState, {});                     // its health and where it stood
world.insert(chest, RememberState, { keepTransform: false }); // opened stays opened
```

As a remembered entity is taken out with its cell, its game components (the ones your
project defines, such as `Health` or a chest's `opened` flag) and its Transform are written
down under the id it was authored with. When the cell is brought in again its document is
changed before anything spawns, so it arrives as it was left, never for a frame as authored.
A remembered entity destroyed while its cell is in (a boss killed, an ore mined, a building
torn down) is written down as gone, with everything under it, and its cell never brings it
back. The engine's own components are not kept: they hold asset handles and state a cell
rebuilds. Entities spawned at run time have no authored id and are not remembered.

The memory is the `WorldMemoryRes` resource. Carry it through a save with
[save slots](/docs/scripting/save/):

```typescript
const saves = new SaveManager({ version: 1 });
const memory = app.getResource(WorldMemoryRes);
saves.save('slot1', { player, world: memory.toJSON() });   // when saving
const loaded = saves.load<{ world: WorldMemoryData }>('slot1');
if (loaded) memory.read(loaded.world);                     // when loading, before the world streams in
```

`read` replaces what is remembered; cells already in the world keep how they are, and the
next one brought in reads the new memory. `clear()` forgets everything, for a new game.

## Procedural chunks

What a game makes as it runs (the ground's collision round what moves, plants round the eye, and whatever a game generates itself) is
not a cooked cell but a chunk of a **layer**, and `ProceduralChunks` is the one owner of their lifetime, as the streamer is of cells. A
layer says how it is cut, how far round its sources it is wanted and how one chunk is made, published and released:

```typescript
import { chunksOf } from 'esengine';

chunksOf(app).set('ruins', {
    label: 'Placing ruins',
    originX: 0, originZ: 0, sizeX: 64, sizeZ: 64, extent: null,
    loadRadius: 256, unloadRadius: 320,
    generation: `${planet}:${generatorVersion}`,     // what the chunks are made from
    make: (cx, cz, signal) => generateRuins(cx, cz, signal), // a value, null for "not yet", or a promise
    publish: (cx, cz, ruins) => spawnRuins(ruins),
    release: (cx, cz, ruins) => despawnRuins(ruins),
});
```

- **One set of sources.** A layer is wanted round the same `WorldStreamingSource`s the streamer reads (or the eye, where there are
  none), unless it names its own: terrain collision follows every moving 3D body and character.
- **A 2D world is cut on x and y.** A layer is cut on the ground by default (world x and z), and a 2D camera never leaves z, so it would stream nothing as it walks up
  or down. Say `plane: 'xy'` and the layer is cut along world x and y, and the sources are read the same way; every "z" a layer names
  (`originZ`, `sizeZ`, the chunk's `cz`, `stateAt`'s second coordinate) is then world y. A layer's own `sources()` answer in the layer's plane already.
- **One budget.** Every frame the wanted chunks of every layer are made nearest first: the ones a source stands in at once, the rest
  while the frame's budget lasts. The budget is `Bakes.budgetMs`, shared with the bakes and the terrain's pages.
- **Bounded.** A chunk past every source's `unloadRadius` is released, with everything it published, so walking for ever holds a fixed
  number; stepping back and forth inside the band makes nothing again.
- **Generations.** `generation` names a layer's inputs. When it changes every chunk is made again, and its old version stays published
  until the new one replaces it, so nothing standing on it falls. An answer that arrives for an older generation (a teleport to another
  planet while a worker was still busy with the last) is thrown away, and the chunk's `AbortSignal` is aborted.
- **Readable.** `status(id)` counts a layer's chunks (ready, stale, pending, making, failed, with the first failure's reason), and
  `stateAt(id, x, z)` says where the chunk at a point stands. Layers still making chunks show with their progress in the editor's status
  bar, through the same list as the bakes.

## Reading what is resident

```typescript
const report = worldResidencyReport(app);
report.residentCells;        // ['main.cell_1_0', 'main.cell_2_0']
report.cellEntityCounts;     // live entities each resident cell owns
report.loadCount;            // places brought in since boot
```

Counts rather than a picture, because a cell that is not drawn and a cell that
does not exist look the same from a camera.

## In the editor

In the edit view, terrain detail, foliage, generated worlds and voxels grow around the viewport, 2D and 3D alike; a `WorldStreamingSource` in the scene only counts while the game runs.

A scene with `StreamedWorld` opens with only its `WorldPersistent` entities in the view, and the textures and meshes of its cells are not loaded. The World panel loads and unloads cells one at a time or all at once, the viewport marks the loaded ones, and the next session opens with the same cells loaded. The document always holds every entity: an unloaded cell is saved as it is, and Play and export see the whole world.

## Clearing or replacing a world

Disable or remove the streaming sources, then await `streamer.clear()`. It releases
prepared assets and waits for pending preparation, publication and unloading to
finish. Registrations remain reusable: a later source update can request the cells again.

Await `streamer.loadManifest(manifest, sceneConfig)` when replacing a world. It drains
the old cells before registering the replacement, including when both manifests reuse
the same cell names. The latest concurrent replacement request wins; an explicit
`clear()` cancels pending replacement requests. Failed teardown rejects the operation
so the replacement cannot take ownership of a name that still has live content.

## What this version does not do

Cells load asynchronously through the same scene loading a game already uses.
They are ordered (a cell a source is walking into goes before one it only might,
nearest first) and can be readied ahead by `prefetchRadius`, but there is no
admission budget: a large cell arriving is still a hitch. A cell's far proxy
(above) carries its static meshes only: what moves, blends or is not a mesh
(sprites, particles, lights) is not drawn while the cell is absent, and a
proxy has one level, not a chain of coarser ones further out. Some content has a far version of its own:
the ground ([Terrain](/docs/graphics/terrain/) is a distance-based quadtree out to
`drawDistance`; tiled ground draws its distance from an overview that is always
in memory and reads full-detail tiles only near the view; a planet is drawn down
to its horizon), and plants (the far cards of [Foliage](/docs/graphics/foliage/)
and `PlacedFoliage`, and of a generated world's plants) stand over a whole area
at once. Mesh textures are held at the size their views need
([texture streaming](/docs/performance/quality-levels/), a quality setting).
Navigation is baked a tile per square and follows residency (see
[Navigation](/docs/gameplay/ai/navigation/#in-a-streamed-world)), but agents walk only where the world is loaded; and
the world origin is never rebased (`setRenderOriginStep` keeps *drawing* precise
far from zero, see [Camera](/docs/graphics/camera/)).
