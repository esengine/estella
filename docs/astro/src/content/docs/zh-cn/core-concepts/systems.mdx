**系统**是调度每帧运行的函数。其参数列表声明系统接收的数据——组件查询、资源、命令与事件——系统以恰好这些值被调用。

```typescript
import {
    defineComponent, defineSystem, addSystem,
    Query, Mut, Res, Time, Transform
} from 'esengine';

const Speed = defineComponent('Speed', { value: 200 });

addSystem(defineSystem(
    [Res(Time), Query(Mut(Transform), Speed)],
    (time, query) => {
        for (const [entity, transform, speed] of query) {
            transform.position.x += speed.value * time.delta;
        }
    }
));
```

`defineSystem(params, fn, options?)` 返回一个 `SystemDef`。回调按相同顺序为每个参数接收一个实参。

## 参数

| 参数 | 回调接收 |
|---|---|
| `Query(...)` | 可迭代对象，遍历拥有全部所列组件的每个实体。每一项为 `[entity, ...components]`。 |
| `Mut(Component)` | 用于查询内：系统写入的组件。未包裹的组件为只读。 |
| `Res(Resource)` | 资源值本身，用于读取（例如 `Time`）。 |
| `ResMut(Resource)` | 包裹资源的句柄：`.get()`、`.set(v)`、`.modify(fn)`。 |
| `Commands()` | 延迟的结构性改动（生成、销毁、添加、移除）。在声明它的系统返回时应用，因此同一帧中稍后运行的系统可以看到这些改动。 |
| `EventReader(E)` / `EventWriter(E)` | 用于读取或发送的类型化事件流（[事件](#事件)）。 |
| `GetWorld()` | `World` 本身（[声明访问](#声明访问)）。 |
| `Removed(C)` | 失去组件 `C` 的实体（[过滤](#过滤与变更检测)）。 |

<Aside type="caution">
  仅当系统写入某个组件时才以 `Mut` 包裹它。只读访问会跳过变更检测的开销，而且调度器依据参数列表判断两个系统是否冲突
  （[声明访问](#声明访问)）。
</Aside>

## 选项

| 选项 | 类型 | 说明 |
|---|---|---|
| `name` | `string` | 供排序边引用、并显示在耗时统计中的名称。 |
| `runBefore` | `string[]` | 系统在每个指定的系统或集合之前运行。 |
| `runAfter` | `string[]` | 系统在每个指定的系统或集合之后运行。 |
| `runWhenPaused` | `boolean` | 应用暂停时仍在 `First`、`PreUpdate`、`Update` 与 `PostUpdate` 中运行。`Last` 始终运行；固定步长保持停止。 |
| `touches` | `SystemTouches \| () => SystemTouches` | 通过 `GetWorld()` 访问的组件（[声明访问](#声明访问)）。 |

## 调度

系统注册到由有序阶段组成的**调度（schedule）**中：

| 阶段 | 运行时机 |
|---|---|
| `Startup` | 首帧之前运行一次。 |
| `First` → `PreUpdate` → `Update` → `PostUpdate` → `Last` | 每帧按此顺序运行。 |
| `FixedPreUpdate` → `FixedUpdate` → `FixedPostUpdate` | 按固定步长运行，每帧零次或多次。 |

| 函数 | 注册到 |
|---|---|
| `addSystem(system)` | `Update` |
| `addStartupSystem(system)` | `Startup` |
| `addSystemToSchedule(Schedule.X, system)` | 任意阶段 |

这些顶层函数在模块作用域中排队登记注册；`App` 上的同名方法注册到特定的 app
（[App API](/docs/zh-cn/core-concepts/app/app-api/#系统与事件)）。一帧之内，各阶段按
[帧循环](/docs/zh-cn/core-concepts/app/app-api/#帧循环)中所列的顺序运行。

由场景注册的系统仅在该场景处于激活状态时运行，因此多个场景可以共用一个世界。

## 排序

同一阶段内，系统按**注册顺序**运行。阶段之间的顺序是固定的：在 `PreUpdate` 中读取输入、在 `Update` 中移动、
在 `PostUpdate` 中让相机跟随，无需额外排序。

### 排序边

`runBefore` 与 `runAfter` 确定一个系统相对于同一阶段中其他系统的顺序。排序边引用系统**名称**。
在 `defineSystem` 上声明的排序边随定义一起传递，通过顶层 `addSystem`（不接受选项）注册的系统即以此方式排序：

```typescript
const move = defineSystem([...], moveFn, { name: 'move' });
const camera = defineSystem([...], cameraFn, {
  name: 'camera',
  runAfter: ['move'],
});

addSystem(move);
addSystem(camera);
```

`app.addSystemToSchedule(schedule, system, options)` 接受同样的排序边，外加 `runIf` 与 `activeWhen`。
注册时给出的排序边**追加**到定义上已声明的排序边之上：

```typescript
import { Schedule } from 'esengine';

app.addSystemToSchedule(Schedule.Update, camera, {
  runAfter: ['input'],         // in addition to the 'move' edge
  runIf: () => isPlaying,      // the system is skipped while this returns false
});
```

| 注册选项 | 说明 |
|---|---|
| `runBefore` / `runAfter` | 附加的排序边。 |
| `runIf` | 每帧检查的运行条件；为 `false` 时跳过该系统。 |
| `activeWhen` | 系统工作所依赖的组件。没有任何实体带有其中任一组件时跳过该系统；最后一个被移除后，系统再运行一帧。 |
| `profileDomain` | 性能剖析器归档该系统开销的领域（[性能剖析](/docs/zh-cn/performance/profiling/overview/#性能剖析器面板)）。默认取在其 `build()` 中注册它的插件的领域。 |

指向本阶段中不存在的系统的排序边会被忽略。排序边成环时，调度器抛出带有成环路径的错误，
例如 `Circular system dependency: move → camera → move`。

<Aside type="note">
  顶层的 `addSystem` / `addSystemToSchedule` 不接受选项；`name`、`runBefore` 与 `runAfter` 在 `defineSystem`
  上声明。运行条件没有定义处的写法：它只能传给 `app.addSystemToSchedule` 或所属的系统集。
</Aside>

### 运行条件

运行条件是一个 `() => boolean`，每帧在系统将要运行前检查。返回 `false` 时本帧跳过该系统；条件第一次返回 `true`
的那一帧，系统恢复运行。`runIf` 在注册时或在[系统集](#系统集)上接受一个运行条件。引擎导出了它自己使用的条件：

| 条件 | 何时返回 `true` |
|---|---|
| `playModeOnly` | 编辑器外始终为 `true`；编辑器内只在试玩（Play）期间。 |
| `isPlayMode` | 编辑器处于试玩期间。 |
| `isEditor` / `isRuntime` | 在编辑器内 / 编辑器外。 |

```typescript
import { Schedule, playModeOnly } from 'esengine';

app.addSystemToSchedule(Schedule.Update, spawnWaves, { runIf: playModeOnly });
```

引擎的模拟类插件（物理、动画、速度、AI、时间轴）都用 `playModeOnly` 控制自己的系统。正因如此，编辑器的编辑模式下
游戏是静止的，而渲染、变换与布局仍在更新正在编辑的场景。项目自己的脚本只加载到编辑器的试玩世界中，因此无需加条件；
[编辑器插件](/docs/zh-cn/extending/editor-plugins/)加到编辑世界中、会推进游戏的系统，需要用 `playModeOnly`。

有三个选项会跳过系统，原因各不相同：

| 选项 | 何时跳过系统 |
|---|---|
| `runIf` | 条件返回 `false` 时。 |
| `activeWhen` | 没有任何实体带有所列组件中的任一个时。插件可为其全部系统声明它（[插件](/docs/zh-cn/core-concepts/plugins-resources/#插件)）。 |
| `runWhenPaused` | 应用暂停时，除非该选项为 `true`。 |

### 系统集

`defineSystemSet(name, options)` 将多个系统归入一个名称下。集合的 `runIf` 与排序边作用于每个成员，
任何系统或集合都可以相对于该集合的名称排序。

| 选项 | 类型 | 说明 |
|---|---|---|
| `systems` | `SystemDef[]` | 成员，按列出的顺序运行。 |
| `runIf` | `() => boolean` | 每帧检查；为 `false` 时跳过全部成员。 |
| `runBefore` / `runAfter` | `string[]` | 作用于每个成员的排序边。 |

```typescript
import { Schedule, defineSystemSet } from 'esengine';

const physics = defineSystemSet('physics', {
  systems: [applyForces, integrateVelocity, resolveContacts],
  runBefore: ['render'],
  runIf: () => !paused,
});

app.addSystemSetToSchedule(Schedule.FixedUpdate, physics);

// One edge orders against every member of the set:
app.addSystemToSchedule(Schedule.FixedUpdate, debugDraw, { runAfter: ['physics'] });
```

`app.addSystemSet(set)` 将集合注册到 `Update`。

### 数值优先级

没有数值优先级选项。注册顺序即默认顺序，因此数值方案通过在注册前排序实现：

```typescript
const ordered = [
  { order: 100, system: input },
  { order: 200, system: move },
  { order: 300, system: camera },
];
for (const { system } of ordered.sort((a, b) => a.order - b.order)) {
  app.addSystemToSchedule(Schedule.Update, system);
}
```

## 过滤与变更检测

```typescript
// Presence filters — components required or excluded but not read:
Query(Transform, Mut(Velocity)).without(Frozen).with(Enemy)

// Boolean combinations:
import { Query, With, Without, Or, Not } from 'esengine';
Query(Transform).filter(Or(With(Player), With(Ally)))

// Change detection — entities whose component was added or changed since this system last ran:
import { Query, Added, Changed } from 'esengine';
Query(Added(Health))
Query(Changed(Transform))
```

| 过滤器 | 匹配 |
|---|---|
| `.with(C)` / `.without(C)` | 带有 / 不带有 `C` 的实体。 |
| `.filter(expr)` | 由 `With`、`Without`、`Or` 与 `Not` 构成的布尔表达式。 |
| `Added(C)` | 自系统上次运行以来添加了 `C` 的实体。 |
| `Changed(C)` | 自系统上次运行以来写入过 `C` 的实体。 |

`Removed(C)` 是单独的参数，产出失去了 `C` 的实体：

```typescript
import { defineSystem, Removed } from 'esengine';

defineSystem([Removed(Health)], (removed) => {
  for (const entity of removed) { /* cleanup */ }
});
```

查询结果除 `for…of` 外还提供以下方法：

| 方法 | 返回 |
|---|---|
| `single()` | 第一个匹配，或 `null`。用于单个玩家或相机。 |
| `count()` | 匹配数量。 |
| `isEmpty()` | 是否没有匹配。不会将 `Mut` 组件标记为已变更。 |
| `toArray()` | 以数组返回全部匹配。 |
| `forEach((entity, ...components) => …)` | 对每个匹配调用回调。 |

## 声明访问

系统的参数列表声明其访问：`Query(Mut(Transform))` 写入 `Transform`，`Res(Time)` 读取 `Time`。
调度器据此判断两个系统能否同时运行，以及二者的相对顺序是否已被指定。

`GetWorld()` 提供不受限制的访问，因此使用它的系统与所有其他系统冲突。`touches` 选项按组件名声明此类系统实际读取和写入的内容：

```typescript
defineSystem([GetWorld()], (world) => { /* ... */ }, {
  name: 'Perception',
  touches: {
    reads: ['Perceiver', 'Transform'],
    writes: ['Perception'],
  },
});
```

| `SystemTouches` 字段 | 说明 |
|---|---|
| `reads` | 系统读取的组件名。 |
| `writes` | 系统写入的组件名。 |
| `opaque` | `true` 表示访问无法完整列出。处理方式与省略 `touches` 相同（与一切冲突），但属于显式声明。 |

组件以字符串指名，因为通过世界访问数据的系统通常会访问在它之后才注册的类型。`touches` 可以是函数，每次读取访问信息时重新求值；
运行创作数据的系统借此报告实际加载数据的访问——状态机系统报告已加载的 `.esfsm` 图所指名叶节点的并集。
`defineBehavior` 出于同样目的接受 `touches`（[脚本](/docs/zh-cn/scripting/overview/#声明访问的组件)）。

### 异步系统

系统按调度顺序启动，同步系统运行完毕后下一个系统才启动。**async** 系统挂起于 `await` 期间，
如果下一个系统既不依赖它、也不访问相同数据，调度器可以启动下一个系统。因此两个加载无关数据的 async 系统会同时等待。
二者之间的必要顺序应以排序边表达，而不是依赖注册顺序。

### 未排序的冲突

同一阶段中访问相同数据、但彼此之间没有排序边的两个系统，按注册产生的顺序运行，该顺序会随系统或插件的增加或重排而改变。
app 会报告这样的系统对（两个方法均为 `@beta`）：

```typescript
app.scheduleAmbiguities(Schedule.Update);
// [{ a: 'Move', b: 'Cull', over: ['Transform'] }]

app.scheduleBatches(Schedule.Update);
// [['Move', 'Spin'], ['Cull']]
```

| 方法 | 返回 |
|---|---|
| `scheduleAmbiguities(schedule)` | 访问相同数据且彼此间没有排序边的系统对，以及二者共享的数据。 |
| `scheduleBatches(schedule)` | 将阶段划分为可同时运行的系统批次；用于衡量该阶段中有多少部分天然串行。 |

消除歧义的方法是添加排序边，或消除访问重叠。

## 事件

事件是系统之间的类型化消息流，系统彼此无需直接引用。`defineEvent<T>(name)` 定义事件，`app.addEvent` 注册事件，
系统以 `EventWriter` / `EventReader` 为参数：

```typescript
import { defineEvent, defineSystem, EventWriter, EventReader, Commands } from 'esengine';

const Damaged = defineEvent<{ entity: number; amount: number }>('Damaged');
app.addEvent(Damaged);

// Producer
addSystem(defineSystem([EventWriter(Damaged)], (damaged) => {
  damaged.send({ entity: 12, amount: 5 });
}));

// Consumer — reads what was sent since it last ran
addSystem(defineSystem([EventReader(Damaged), Commands()], (damaged, cmds) => {
  for (const evt of damaged) { /* evt.entity, evt.amount */ }
}));
```

事件通道采用双缓冲，每帧交换。reader 可迭代，并提供 `isEmpty()` 与 `toArray()`。**event-system** 示例展示了完整的生产者/消费者模式。
在编辑器中创作的、以实体为目标的事件见[事件绑定](/docs/zh-cn/scripting/events/)。
