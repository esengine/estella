import { Aside } from '@astrojs/starlight/components';

导航把 agent 沿着一条绕开所有障碍的路线送到某个世界坐标。路线是在 **`Nav`** 资源当前的
*surface* 上规划的,而 surface 有两种:

- **`NavGrid`** —— 由可走/阻挡格子构成的矩形掩码。瓦片地图本来就是这个形状,而且它是唯一
  能在游戏运行时改一格的。
- **`NavMesh`** —— 从场景自己的碰撞几何**烘焙**出来的凸多边形。它能跟着倾斜和堆叠的地面走,
  这是任何单张网格都做不到的。

它们之上的一切——agent、调试叠加层、`nav.findWorldPath`——对两者问的是同样的问题,所以
游戏里没有任何地方需要知道自己拿到的是哪一种。

### 构建网格

```typescript
import { defineSystem, Res } from 'esengine';
import { Nav, NavGrid } from 'esengine/ai';

export const setupNav = defineSystem([Res(Nav)], (nav) => {
  nav.setSurface(new NavGrid({
    width: 60,          // 列数
    height: 44,         // 行数
    cellSize: 20,       // 每格的世界像素
    origin: { x: -600, y: -440 },  // 格子 (0,0) 中心的世界坐标
  }));
}, { name: 'SetupNav' });
```

| `NavGrid` 选项 | 类型 | 说明 |
|---|---|---|
| `width` | number | 格子列数。 |
| `height` | number | 格子行数。 |
| `cellSize` | number | 每格的世界像素(正方形)。 |
| `origin` | `{ x, y, z? }` | 格子 `(0,0)` 中心的世界坐标。它的 `z` 就是每个路点返回时所在的深度。默认 `(0,0,0)`。 |
| `walkable` | `ArrayLike<number>` | 可选的行主序 `width*height` 掩码,`1` = 可走,`0` = 阻挡。省略则全部可走。会被拷贝进去,不保留引用。 |

若想从已绘制的瓦片地图推导网格,而不是手写掩码,用 `navGridFromTilemapLayer`(把某图层的
实心瓦片视作阻挡)或 `navGridFromTiles`。`grid.setWalkable(x, y, false)` 随时可以关掉一格
——门关上了、塔造起来了——下一次规划就会绕开它。

格子上的路线在交出去之前会先**拉直**:A\* 是一格一步作答的,只有路线真正需要转弯的那些格
留了下来。抄近道只走搜索本身能走的线——线经过的每一格都容得下这个身体,而对角线要求它
两侧的正交格都通——所以拉直后的路线和它替换掉的那条阶梯一样合法,并且和网格给出的是同一
种形状的路线。

### 异步工作完成后替换导航表面

`nav.beginSurfaceUpdate()` 返回带版本号的 `NavSurfaceUpdate`。单独构建替换表面后调用
`update.commit(surface)`;只有最新且仍待提交的请求能成功。过期、已取消或已完成的句柄
返回 `false`。`nav.setSurface(...)` 和赋值 `nav.surface` 也会取消待提交请求。
`update.cancel()` 保留旧表面并恢复原有路线。

`nav.surfaceUpdatePending` 为真时,导航驱动保留代理目标并停止自己的转向;角色重力仍生效。
资源查询暂不返回路线,`queryWorldPath` 报告 `unavailable / building`,编辑器路线诊断显示
导航正在更新。规划计数也包含等待替换表面的代理。

```typescript
import { Navigation, NavGrid, type NavGridOptions } from 'esengine/ai';

async function replaceTerrain(nav: Navigation, load: () => Promise<NavGridOptions>) {
  const update = nav.beginSurfaceUpdate();
  try {
    const data = await load();
    if (update.pending) update.commit(new NavGrid(data));
  } finally {
    update.cancel(); // 失败时释放请求;已提交后再取消不会改变结果。
  }
}
```

请求所属对象销毁时也应取消。取消撤销提交资格,底层 I/O 或 worker 由构建器负责停止。
这套协议不启动后台线程,也不会把同步 mesh 烘焙变成异步。准备替换结果时不要修改正在
使用的表面;取消无法回滚这些修改。庭院工坊使用实际 JSON 资产演示重载/取消,并在成功、
失败、过期或取消后释放对应的资产引用。

### 3D 场景的网格

3D 场景有的是几何而不是瓦片掩码,所以它的 surface 是从**它本来就在碰撞的那些刚体**上
**烘焙**出来的。在一个实体上放 **`NavVolume`**,导航插件就会把它描述的那个盒子填满:

| `NavVolume` 字段 | 默认 | 说明 |
|---|---|---|
| `halfExtents` | `1000, 500, 1000` | 要烘焙的盒子半尺寸,单位世界像素;实体的 Transform 是盒子中心。 |
| `cellSize` | `50` | 地平面上的体素尺寸。越小越贴合几何,烘焙也越慢。 |
| `cellHeight` | `10` | 垂直方向的体素尺寸——决定阳台和它下面的地板算两层还是一层的就是它。 |
| `maxSlopeDegrees` | `45` | agent 能站住的最陡地面。比这更陡的就是墙。 |
| `agentHeight` | `180` | agent 需要的头顶空间。不够的地面是爬行空间不是走廊。 |
| `agentRadius` | `30` | agent 有多宽。网格会按这个尺寸从每一面墙上缩回来。 |
| `stepHeight` | `40` | agent 能直接爬上去、而不必绕开的台阶高度。 |
| `layers` | `0` | 地面取自哪些物理层;`0` = 所有层。 |

烘焙把盒子里的碰撞三角面体素化,留下这个尺寸的 agent 站得住的那些面,再把剩下的变成凸多边形。
世界的每一列都保留了它**全部**的楼层,所以桥和桥下的路是两个地方,路线两个都能用。

<Aside type="note">
  **一个场景一个体积。**一个场景只有一个可走世界,所以被烘焙的是第一个体积,其余的会在日志里
  被点名。盒子决定的是**往哪看**;可走性来自盒子里的几何,所以用一个大到装得下整个关卡的盒子
  只是多花体素,不会损失正确性。
</Aside>

<Aside type="note">
  **只烘焙静态刚体。**一个马上要被推走的箱子不是地板,在它上面烘出来的网格只在没人碰它的
  这段时间里成立。任何应该被踩上去(或被绕开)的东西,都给它一个 body type 为 **Static**
  的 `RigidBody3D`。
</Aside>

每个体积只烘焙一次,在它的几何可用的第一帧——网格碰撞体在资产加载完之前贡献不了任何三角面,
烘焙会等它。想按自己的方式烘焙的游戏可以直接调 `buildNavMesh(verts, indices, options)`,
而 `collectNavGeometry(world, { min, max, layers? })` 就是收集三角面的那一步。

<Aside type="caution">
  **一张网格只对应一种 agent 尺寸。**`agentRadius` 是烘进去的,不是查询时才应用的:这张网格
  **就是**那么宽的身体可以站的所有位置的集合。比所在体积更宽的 `NavAgent` 会按较窄的那个
  规划路线,并在日志里说一次。
</Aside>

### 地面没有提供的路

网格是从 agent **能走**的地方烘出来的,所以中间隔着空的两层楼就是两个地方——这是诚实的答案,
但不是全部答案。场景知道地面不知道的事:这道沿可以跳下去、这架梯子能爬、这块板搭到了屋顶。
**`NavLink`** 就是场景说这些事的地方。

| `NavLink` 字段 | 默认 | 说明 |
|---|---|---|
| `start` | `0, 0, 0` | 这条路从哪开始,是实体自身坐标系里的偏移。 |
| `end` | `0, 0, 150` | 从哪出来。 |
| `bidirectional` | `true` | 是否双向可走。从沿上跳下去不是。 |
| `radius` | `50` | 两端多远范围内的地面还算得上被它连起来。 |
| `enabled` | `true` | 这条路现在存不存在。 |

两端都是实体坐标系里的偏移,所以链接会跟着承载它的东西移动和旋转——预制体里的一架梯子,
放到哪都还是梯子。**一端够不到任何地面的链接什么也不连**:一条走到半空中结束的路线,
比没有路线更糟。

移动或开关一个链接的代价是一次**查找**,不是一次烘焙——它连的是已经存在的多边形。
这就是它和障碍的区别,也是为什么一个能便宜地动、另一个不能。

<Aside type="note">
  **路线在链接的两端断开。**把绳子拉直会从梯子旁边的空气里穿过去,所以路点里一定包含链接
  连起来的那两个点,跟随的 agent 会经过它们。**正在跨越链接的时候,agent 根本不站在可走世界上**
  ——在那里问重规划是没有答案的,所以 agent 会继续走它已经有的那条路线,而不是把自己
  搁在半路上。
</Aside>

### 有代价的地面

网格回答的是 agent **能**走哪。**`NavArea`** 是场景说「它更愿意走哪」的地方:

| `NavArea` 字段 | 默认 | 说明 |
|---|---|---|
| `halfExtents` | `200, 100, 200` | 盒子的半尺寸,单位世界像素;实体的 Transform 是它的中心。它会跟着实体转。 |
| `cost` | `3` | 盒子里每单位距离的代价,开阔地面是 `1`。 |
| `enabled` | `true` | 这个价现在算不算数。 |

小于 1 会被优先选择,大于 1 会被躲开——半价的路值得绕远去走,四倍价的沼泽只要有路绕就绕开。
它**永远不阻挡**:无处可去的 agent 会趟过去,这就是沼泽和栅栏的区别。

移动或改变一块地的尺寸会重建可走世界,和障碍一样。改它的 `cost` 不会:网格记住的是多边形
属于哪一块地,而那块地值多少钱是每次搜索现读的。

<Aside type="note">
  **拉直也认它。**格子上的路线事后会被拉直,而把一条刚绕开泥地的路线又拉直回泥地里,
  等于把它绕路的唯一理由撤销了——所以抄近道不能跨过和起点价格不同的地面。
</Aside>

### 门、闸,以及被放在路上的东西

任何带碰撞体的东西本来就会挡路——网格就是从场景的碰撞几何烘出来的。**`NavObstacle`**
是给「**不是几何**却要挡路」的东西,或者「不动地方却要停止挡路」的东西准备的:

| `NavObstacle` 字段 | 默认 | 说明 |
|---|---|---|
| `halfExtents` | `50, 100, 50` | 阻挡盒的半尺寸,单位世界像素;实体的 Transform 是它的中心。和体积不同,它会跟着实体转。 |
| `enabled` | `true` | 它现在挡不挡。会开的门就是这个字段。 |

阻挡是**烘焙的输入**,不是对答案的过滤:障碍在可走区域被腐蚀**之前**就把地面拿走,
所以路线离它的距离是完整的 agent 宽度,而不是贴着它的面蹭过去。改动一个障碍——移动、
改尺寸、开关——都会重烘焙网格,两次烘焙至少间隔 200 毫秒。2D 格子在下一次导航更新时
立即重标记障碍,不等待这段烘焙节流;刚关闭的通道会在代理规划和移动之前排除。

```typescript
// 门打开了,在任何能访问 world 的系统里:
const door = world.get(entity, NavObstacle);
door.enabled = false;
world.set(entity, NavObstacle, door);
```

两种 surface 都认它:网格重新烘焙,格子把盒子底下的格标掉。格子自己的可走性是分开存的,
所以门关上再打开,还给你的正是原来那片地。

<Aside type="caution">
  **不要给会一直移动的东西用。**障碍是给「挡一下然后停住」的东西准备的——门、闸、
  刚造好的塔。一直在动的障碍会让世界每秒重建好几次,它会在日志里说出来;
  会移动的物体该交给和它碰撞的角色控制器,不是交给烘焙。
</Aside>

### 看见烘出来的东西

体积的线框说的是烘焙**往哪看**。想在还在编排场景的时候就看见它**找到了什么**,打开
**视图 → 显示导航网格**(或视口工具栏上的「导航」按钮):编辑器会烘焙场景里的体积,
把可走的面画在它们实际所在的位置,并把它们终止的那些边挑出来。场景一变它就重烘,
所以把 `agentRadius` 调宽时,网格是当着你的面从墙上缩回去的。

同一张图在运行中的游戏里由 `NavDebugDraw` 资源给出:

```typescript
import { NavDebugDraw } from 'esengine/ai';

app.getResource(NavDebugDraw).enabled = true;
```

`showFaces`、`showBorders`、`showLinks`(默认都是 `true`)分别开关面轮廓、红色的终止边和 `NavLink` 连线。

每个可走的面都画在它实际所在的位置——网格画在地面高度上,格子画在场景自己的平面上——而
可走世界**终止**的每一条边都标成红色。那些边是唯一能解释「路线为什么绕远」的东西。默认关闭
(一个 surface 是每帧几千个环),而且画到 4096 个面就停:想看清更大的世界,调 `cellSize`。

<Aside type="tip">
  `Nav` 资源也能直接回答一次性查询:`nav.findWorldPath(from, to)` 返回一组世界空间路点,
  无需 `NavAgent`。

  **到不了的目标**——门关着、在另一座岛上、根本不在网格上——回答的是「到它**最近**的那个
  到得了的地方」的路线:被派往一个到不了的地方的 agent,应该走到门口,而不是站在原地。
  它到没到是**你**该看的:目标是你给的,最后一个路点要么在它上面,要么不在。返回 `null`
  只有一种意思——**agent 自己不在任何地方**,一个不在可走世界上的点没有任何路线可言。
</Aside>

### 解释路径结果

需要区分“尽量靠近”与真正到达时，调用 `nav.queryWorldPath(from, to, { radius })`。
它返回 `{ path, status, reason }`：

| 状态 / 原因 | 含义 |
|---|---|
| `complete` / `none` | 到达导航面解析后的目标，包括原有端点吸附。 |
| `partial` / `disconnected` | 路线止于断开的区域或关闭通道的可达一侧。 |
| `partial` / `insufficient-clearance` | 点能通过格子，但指定宽度的角色无法通过。 |
| `unavailable` / `no-surface` | 尚未安装导航面。 |
| `unavailable` / `building` | 有一次导航面替换正在进行(`nav.surfaceUpdatePending`)。 |
| `unavailable` / `start-unavailable` | 找不到可用起点。 |
| `unavailable`(格子)或 `partial`(网格)/ `target-unavailable` | 找不到可用终点；网格仍会给出靠近它的部分路线。 |
| `unavailable` / `radius-mismatch` | 角色半径超过导航网格烘焙时的半径。 |
| `unknown` / `diagnostics-unavailable` | 自定义导航面仅实现了原有路径接口。 |

```typescript
const result = nav.queryWorldPath(from, target, { radius: 20 });
if (result.status !== 'complete') console.info(result.reason);
// result.path 仍可能包含一条有用的靠近路线。
```

`findWorldPath` 保留原有的尽量靠近行为。诊断查询只描述当前已安装的导航面，不触发重建。
格子通行状态通过 `setWalkable`、`setObstructed` 和 `clearObstructions` 修改，确保净空和连通性
缓存一起失效。动态障碍也计入角色宽度所需净空；区域价格变化无需重建连通性。

重复格子查询会复用工作内存；返回的路线仍各自独立，可保留或修改，不会影响后续查询。
路线代价、端点吸附和尽量靠近的部分路径行为保持一致。

编辑器中，在**运行**时选择 `NavAgent`，展开详情里的该组件，点击**诊断当前路线**。
它按代理半径，从当前世界位置到已存目标查询一次，显示原因、查询端点、路径点数与耗时。
结果为快照，门、障碍或目标变化后需要重新点击；详情面板定期刷新不会触发寻路。
该功能需要已就绪的本地运行会话，暂不支持连接设备的诊断。它描述当前安装的导航表面，
不代表尚未提交的重建状态或代理缓存的移动路线。

可复现的 CPU 语料使用无头 Chromium，在 32/64/128 格地图中开关门、放置建筑并同时重算
64 个代理的路径：

```sh
node tools/navigation-rebuild-benchmark.mjs output/navigation-current.json
node tools/navigation-rebuild-benchmark.mjs output/navigation-reference.json --search-reference=48631844c53113825a15493afeb8e6e2b972900c
```

对照只替换旧寻路实现，两侧均使用当前的动态障碍净空。报告包含源码与 bundle 标识、原始
构建/查询耗时和帧间隔。该计时不含物理几何收集、避让、渲染及完整游戏帧的其余工作。

### 移动 agent

`NavAgentSystem` 按先进先出顺序，跨帧处理规划请求。默认每帧最多 **16 次查询**，
规划时间采用 **2 毫秒软预算**。至少允许一次查询；时间只在同步查询之间检查，单次查询
仍可能超时。这通过增加路线等待时间来分摊峰值，不会消除总工作量。
直接调用 `findWorldPath` / `queryWorldPath` 仍是同步查询，不经过该队列。

```typescript
const nav = app.getResource(Nav);
nav.planningBudgetMs = 2;
nav.maxPlansPerFrame = 16;
// 某项限制设为 0，表示关闭该项限制。
console.info(nav.planningStats); // 上一帧的 completed、pending、elapsedMs
```

排队期间的目标修改会合并，实际处理时读取最新位置、目标和半径。没有有效路线的代理暂停；
普通周期刷新排队时继续沿有效缓存路线移动。暂停时角色控制器停止水平操舵，但保留重力速度。
更换导航表面、修改内置格子拓扑或代理半径后，
旧路线会失效，包括关闭周期重规划的代理。原地修改自定义表面、区域价格或连接后，
请调用 `nav.invalidatePaths()`。未改变的表面临时查询失败时，可保留跨连接中的既有路线；
已失效的路线不会恢复使用。

编辑器的**诊断当前路线**会同时采样上一帧规划完成量、待处理数、耗时和预算。
这是队列快照，不是手动诊断查询或导航重建的耗时。

```sh
node tools/navigation-planning-benchmark.mjs output/navigation-planning.json
```

加一个 `NavAgent`,然后给它指一个目的地。内置的导航插件会规划路径并每帧沿路径推进 agent——
你只管设目标。

```typescript
import { NavAgent, setNavDestination, stopNavAgent } from 'esengine/ai';

cmds.spawn()
  .insert(Transform, { position: { x: 0, y: 0, z: 0 } })
  .insert(NavAgent, { speed: 140, arriveRadius: 8 });

// 从任何能访问 world 的系统/动作里——每帧调用都安全:
setNavDestination(world, entity, { x: 320, y: -120 });
// ……以及原地停下:
stopNavAgent(world, entity);
```

| `NavAgent` 字段 | 默认 | 说明 |
|---|---|---|
| `speed` | `120` | 移动速度(世界像素/秒)。 |
| `radius` | `0` | 身体有多宽(像素)。在格子上,寻路会绕开它挤不过去的地方;在网格上,这件事由体积的 `agentRadius` 决定。 |
| `arriveRadius` | `6` | 距最终目标的停止距离。 |
| `repathInterval` | `0.5` | 周期重规划间隔；`0` 关闭周期刷新，目标/拓扑变化和受阻恢复仍会重规划。 |
| `hasTarget` | `false` | 是否已设目的地。由 `setNavDestination` 置真;到达时和调用 `stopNavAgent` 时清除。 |
| `targetX`、`targetY`、`targetZ` | `0` | 当前目的地(世界像素)。 |
| `arrived` | `false` | agent 到达目标时被置真,直到下一次 `setNavDestination` 才清除。 |

`setNavDestination` 每帧调用都安全,可用于追一个移动的目标——只有当目标真的移动、或
`repathInterval` 到点，或拓扑变化/受阻恢复时，agent 才重新规划。读 `agent.arrived`(或 `Perception`)来判断何时
切换行为。

对内置表面，走到**部分路线**的尽头不会清除目标：`hasTarget` 保持真，`arrived` 为假。
代理在障碍附近等待；即使关闭周期刷新，表面改变后也能继续前进。调用 `stopNavAgent`
才取消这个意图。未实现 `queryWorldPath` 的自定义表面无法说明完整性，保留原来的到达行为。

`surface.isNavigable(point, { radius })` 可检查身体是否站得下：格子按圆形身体检查格子边缘与
地图边界，网格拒绝超出烘焙半径的身体。格子规划把半格宽度计入净空换算，避免小数半径挤过
比身体更窄的门。运动学格子跟随器会采样实际移动段；受阻或停滞时从当前状态重新规划。
这是导航操舵，不能代替物理碰撞求解器。

## 有身体的 agent

如果 agent 所在实体同时带着 **`CharacterController3D`**,插件就**操舵**它而不是搬动它:
把控制器的水平速度指向下一个路点,由角色自己的求解器去走——于是它会和世界碰撞、爬得上去的
台阶就爬、该掉下去的地方就掉。垂直轴永远不写,那个轴是世界的,正是它让「下一级台阶」是掉
下去而不是滑下去。

```typescript
cmds.spawn()
  .insert(Transform, { position: { x: 0, y: 200, z: 0 } })
  .insert(CharacterController3D, { radius: 30, halfHeight: 50 })
  .insert(NavAgent, { speed: 400, arriveRadius: 90 });
```

这种 agent 的距离都在地平面上量,因为角色是**胶囊中心**悬在路线所在的地面之上的。把体积的
`agentRadius` 设成控制器的 `radius`(`agentHeight` 大致设成 `halfHeight` 的两倍加半径),
网格才是「这个身体站得下的所有位置」。

没有控制器时,agent 的 Transform 会被直接沿路径推进——平面游戏要的就是这个,3D 游戏在还没有
身体之前拿到的也是这个。

## agent 之间互相让路

路线是对着一个不动的世界规划的。agent 会动,而十几个被派往同一个地方的 agent 会规划出同一条
路线,然后像一个整体一样走过去。`radius` 大于零的 agent 就是在声明「我是一个**身体**」,
从此它会绕开走在同一片地上的其它身体:

```typescript
cmds.spawn()
  .insert(Transform, { position: { x: 0, y: 0, z: 0 } })
  .insert(NavAgent, { speed: 300, radius: 40, arriveRadius: 60 });
```

每个 agent 都假设其它 agent 也在让,所以各让一半——迎面相遇的两个会分开,而不是同时往一边
躲然后又撞上。当对称到连这也分不出高下时(完全的镜像),约定是**靠右**。

侧身的那一步在迈出去之前会先对着可走世界检查一遍,所以让路永远不会把 agent 让进墙里。
因此**两个宽到在同一条走廊里错不开的身体就是错不开**:等着才是诚实的答案,穿墙不是。

`radius` 留在 `0` 的 agent 按质点寻路,既不给谁让路也没人给它让路——这就是所有平面游戏
在此之前的行为,也是一个被脚本驱动的移动物体仍然想要的。

## agent 是有宽度的

在**格子**上,把 `radius` 设成身体的实际半宽,寻路就会绕开它挤不过去的缝隙。留在 `0` 表示
按质点寻路——没有碰撞体的东西就该这样;而这也正是那个经典画面的成因:敌人信心十足地走进
门洞然后永远停在那里,因为它被规划到的那一格是可走的,而挂在隔壁那一格上的半个身子不是。

在**网格**上,同一件事在烘焙时就由 `agentRadius` 解决了——所以在它上面规划出来的路线本来
就离墙足够远,规划器什么都不用做。

身体站不下的目标(墙角里的拾取物)两种情况下都依然到得了:路径规划到身体站得下的最近处
为止,剩下的交给 `arriveRadius`。
