import { Aside } from '@astrojs/starlight/components';

同一个项目要能在旗舰手机和六年前的手机上都跑起来。**画质档位**就是做这件事的办法：**低、中、高**三份配置，每份说明渲染器在
该档位下花多少。项目选一个（或交给设备选），而对档位来说太慢的游戏会自己把分辨率降下来。

## 选择档位

**设置 → 项目 → 渲染 → 设备画质 → 画质档位：**

| 模式 | 含义 |
|---|---|
| 默认 | 未选择：**手机和平板上为中档**，其他设备为关闭。小游戏保留自己的默认值。 |
| 关闭 | 在所有设备上都不做画质管理，项目按原样渲染。 |
| 低 / 中 / 高 | 所有设备都用该档位。 |
| 自动 | 档位由设备决定：第一条匹配的[设备规则](#设备规则)，否则看内存和核心数。 |

**动态分辨率**在 GPU 吃紧时降低场景分辨率，最低降到该档位的*最小渲染比例*，有余量时再升回来；UI 保持显示分辨率。低于屏幕大小绘制的场景会用一个被周围纹素夹取的 Catmull-Rom 重采样器拉伸回来,边缘比双线性拷贝更陡,又不会画出光晕;整数倍的拉伸则是精确拷贝。
**目标帧率**是它要维持的帧时间。

## 一个档位里有什么

一个档位花在哪里分成十二组，每组是一张表：每行一个设置项，每列一个档位，**低、中、高三档并排**，每一格都能直接改。

![项目设置的渲染页：画质档位按组成表，低、中、高三档并排](@/assets/guides/zh/settings-quality-levels.png)

| 分组 | 设置 |
|---|---|
| 分辨率与抗锯齿 | 渲染比例、最小渲染比例、抗锯齿方式（MSAA 或时间性）、MSAA |
| 视距与绘制 | 深度预通道、Draw call 预算 |
| 光源与着色 | 3D 光照（完整或直接） |
| 阴影 | 阴影图集尺寸、阴影单元尺寸、级联数、阴影距离、2D 软阴影采样数（只有 2D 光读它） |
| 全局光照与遮蔽 | 环境光遮蔽分辨率、屏幕空间 GI 分辨率、体素 GI 收集分辨率、动态 GI 降配；环境光遮蔽、GTAO、屏幕空间 GI、体素 GI、动态 GI 和接触阴影这几个效果 |
| 反射 | 平面反射的比例、最大尺寸和每秒更新次数；屏幕空间反射效果 |
| 天空与体积 | 静态天空走全景图、雾体积分辨率、雾光步数、雾的云遮挡采样、云步数、高层云步数、云影采样、大气散射步数、大气光学深度步数；天空、雾、光束和天气类效果 |
| 后处理 | 总开关、镜头光晕分辨率、景深采样、光柱采样、运动模糊采样、次表面散射采样、泛光级数；其余所有效果 |
| 特效与粒子 | 粒子上限、2D 雨遮罩尺寸、折射模糊采样、粒子碰撞查询与事件上限、GPU 粒子深度网格 |
| 地形与植被 | 细节距离 |
| 水体 | 水体波数（1 到 8）、水体涟漪格数，位移、镜面、焦散三个开关；水下效果。构建里带水体模块时才显示 |
| 纹理与显存 | 贴图流式加载及其预算 |

每组的效果是一张"效果 × 档位"的勾选矩阵，勾上表示该档运行这个效果。改过的格子会着色并带一个恢复箭头，箭头的提示写着该档自己的默认值，
点一下就恢复。某个档位下不起作用的格子会变暗：比如用时间性抗锯齿的档位上的 MSAA，关了后处理的档位上的效果分辨率。

![一张档位表里有一格改过：低档的水体镜面打开，着色并带恢复箭头](@/assets/guides/zh/settings-quality-changed.png)

<Aside type="note">
每一格只跟自己那一档的默认值比，所以同一个数字在低档可能是默认、在中档却是改动：0.75 是低档的渲染比例，放在中档和高档就是改动。
</Aside>

设置窗口窄到放不下三列时，页面退回一次编辑一个档位：**画质档位设置 → 正在编辑的档位**决定下面各行显示并修改哪个档位，
在该档位下不起作用的行会隐藏。

每个档位从引擎自己的值起步，**只有你改过的才会保存**到 `project.esproject` 的
`features.rendering.quality.profiles.<档位>` 下。引擎以后改进的默认值会传给从没碰过它的项目；改回该档位默认值的行也不再算差异。

**抗锯齿方式**可选 MSAA 或时间性(TAA)。时间性按 1 个采样绘制,由 TAA 通道用之前的帧来平滑:1080p 下便宜得多,画面略软,需要相机上有后处理体积;选它时该档的 MSAA 格会变暗。**深度预通道**把不透明场景画两遍,先只画深度,让每个像素只为最前面的表面着色一次。表面大量重叠(树林、成片植被)且 GPU 对光栅化出的像素立即着色时划算;对把着色推迟到分块末尾的 GPU,等于几何多付一遍。低档默认关,中、高档默认开。默认抗锯齿方式：低档 MSAA(1 个采样)、高档 MSAA(4 个采样)、中档时间性。预通道和颜色通道在 WebGL2 与 WebGPU 上都把顶点位置声明为 invariant,所以表面的颜色总能通过与自己深度的等深测试,Metal 上也一样;Mac 上开着预通道时地形出现暗色三角形,只需更新到新的构建。

**3D 光照**可选完整或直接。直接按 `#pragma lighting direct` 编译所有受光网格:同一套光照模型,只有光源块里的十六盏灯和硬阴影,没有十六盏之外的灯、软阴影和头发阴影。手机上铺满全屏的受光地板成本约减半(见[手机上的光照](/docs/zh-cn/graphics/lighting/#手机上的光照))。低档和中档是直接,高档是完整;精灵的 2D 光照两种都不变。

**细节距离**是一档里放置的植物保留多少比例的距离：0.5 时，原本 60 米换成更省网格、150 米外不再画本体的树，会在 30 米和 75 米处这样做，远景卡片也更早接手。低档保留 0.5、中档 0.8、高档全部，所以同一个世界在手机上画的三角形只有一小部分。

**Draw call 预算**是这一档每帧最多应向 GPU 发出的 draw 数:低档 150、中档 400、高档 1500。所有 pass 都算,不只是场景自己的绘制列表:每个阴影级联都要把投影物再画一次,深度预通道要把不透明场景再画一次,后处理每个 pass 也要一次 draw。不会为了达标而少画什么。Profiler 的**渲染**模块显示这一帧的 GPU draw 数和预算,并按 pass 拆开;统计浮层在超出时把数字标红。一次 draw 花在 CPU 和驱动上的比花在 GPU 上的多,在手机和小游戏里,3D 场景最先用完的就是它。要降下来,不同网格很多时看[静态合并](/docs/zh-cn/performance/static-batching/),阴影那部分则减少级联数。

**贴图流式加载**把只被网格使用的贴图按视图实际需要的尺寸常驻。被 MeshRenderer 用到的贴图(它的贴图、法线贴图,或者经过它的材质)第一次加载时边长最多 256 纹素,所以场景刚出来时只占一小部分显存;之后,渲染器对视图里画的每个网格,根据网格自身的 UV 密度、尺寸和距离,算出它的贴图需要多少纹素宽才能做到一个纹素约等于一个像素,每秒四次把尺寸不对的贴图从文件按刚好够用的 2 的幂重新解码,放回同一个句柄后面。需要变大时立刻变大;需要变小时,要持续三秒才会缩;五秒没有被任何视图画到的贴图缩到 64 纹素。低档和中档默认开、高档默认关;**贴图流式预算**限制被流式管理的贴图合计占用(低档 128 MB,中档 256 MB,0 表示不设上限),超出时整体降一级清晰度。

在编辑器 Play 里用低档实测(`texture-streaming` 编辑器检查,数字是引擎自己的显存估计):

| 示例 | 关流式 | 开:首帧 | 开:十秒后 | 稳定后两次画面 |
|---|---|---|---|---|
| `dusk-fort` | 285.6 MB | 33.6 MB | 31.0 MB | 平均差 0.28/255 |
| `bistro` | 1293.5 MB | 321.1 MB | 449.6 MB(228 张贴图,149 次缩放) | 平均差 1.1/255;0.04% 的像素有明显变化 |

**下载。** Web 构建会为每张被网格当表面使用、边长超过 512 纹素的贴图另存一份小副本:边长不超过 256,格式不变(KTX2 按原模式重新编码,PNG、JPEG 原样格式写出),从打包的文件用和构建自身 mip 链相同的盒式滤波缩小。流式加载先从小副本开始,只有视图需要的比副本大时才去下载原文件;没有任何东西靠近的贴图永远不会被完整下载。按低档导出 Web 版,在无头浏览器里运行(软件渲染,文件按 immutable 提供):

| 示例 | 不带副本的贴图下载 | 带副本 | 被完整下载的文件 |
|---|---|---|---|
| `dusk-fort`,20 秒 | 44.8 MB | 14.9 MB(其中副本 0.4 MB) | 12 张中 3 张 |
| `bistro`,20 秒 | 35.3 MB | 16.1 MB(其中副本 3.4 MB) | 155 张中 4 张 |
| `bistro`,120 秒 | — | 18.8 MB | 155 张中 15 张 |

无头浏览器用软件渲染,一秒一两帧,长大贴图比 GPU 慢得多:`bistro` 到两分钟时还在每五秒左右下载一张原文件,所以这些是到那时为止下载的量,不是最终稳定的量。在编辑器里用 GPU 跑十秒,`bistro` 有 40 张贴图长到超过副本,它们的原文件合计 8.9 MB:加上 3.4 MB 副本,大约要下载 12.4 MB 贴图,不带副本的构建要 35.3 MB。副本本身会增加包体(`dusk-fort` 42.6 MB 贴图旁多出 430 KB)。小游戏是整包下载,不生成副本;被网格以外的东西使用的贴图也不生成。

它做不到的:在视图要求更大之前,贴图按起始尺寸绘制:场景开头的一两秒可能比之后模糊;一次缩放要在它落地的那一帧付出解码和上传,场景稳定之前会有一两帧几十毫秒。同时被精灵、UI、瓦片地图、粒子或拖尾使用的贴图会恢复原尺寸并保持不变。KTX2 文件直接从某一级截取,不用重新解码;宿主自己转码 KTX2 的平台(原生打包)做不到这一点,这类贴图保持原尺寸。

## 去掉一些效果

引擎有的每个后处理效果都按所属的组、按档位打勾，该档位运行的打勾。没勾选的效果在这个档位被跳过，不管相机的体积是否要求它——而且是整个跳过：
有多个 pass 的效果，比如环境光遮蔽或自动曝光，会被整体移除。清单里按类型保存被去掉的效果：

```json
"quality": { "mode": "auto", "profiles": { "low": { "skipEffects": ["ssr", "taa", "depthOfField"] } } }
```

默认情况下，低档去掉反射、时间性抗锯齿、景深、光束、运动模糊、镜头光斑、环境光遮蔽（SSAO 和 GTAO）、次表面散射、体素 GI 和动态 GI；
中档去掉反射和景深；高档什么都不去掉。这些默认值依据每个效果每像素的工作量，**不是**在弱设备上量出来的。编辑器的 `fx-cost`
检查能量出每个效果在当前机器上的开销，可以在决定某个档位跳过什么之前先看看你的机器上它们要多少。

环境光遮蔽跑不跑，只由这份清单决定。之前写的配置里可能有 `"ssao": false`，读进来等于清单里有 `ssao` 和 `gtao`；`"ssao": true`
等于把 `ssao` 从清单里拿掉。下次在编辑器里勾选该档的效果时，写回的就是清单。玩家设置里的 `quality.setPreferences({ ssao: false })` 也这样读。

## 效果分辨率

有些效果本来就在画面一半的尺寸上算，再铺回画面，因为它们算出来的东西是平滑的。每个这样的效果都有自己的分辨率，放在效果所属的组里，
是这个尺寸的倍率：1 按原样画，边长为画面的一半；0.5 是四分之一，0.25 是八分之一，降到该效果自己的最小尺寸就不再降，再小画面就会碎。
其他都不动：色调映射、FXAA、调色以及其他作用于整幅画面的通道始终按全尺寸跑，否则整帧都会变糊。

| 设置项 | 效果 | 分组 | 最小 |
|---|---|---|---|
| 环境光遮蔽分辨率（`aoResolution`） | SSAO 和 GTAO | 全局光照与遮蔽 | 四分之一 |
| 屏幕空间 GI 分辨率（`ssgiResolution`） | 屏幕空间 GI | 全局光照与遮蔽 | 八分之一 |
| 体素 GI 收集分辨率（`voxelGIResolution`） | WebGL2 上体素 GI 的收集 | 全局光照与遮蔽 | 四分之一 |
| 雾体积分辨率（`fogResolution`） | 高度雾里的光 | 天空与体积 | 八分之一 |
| 镜头光晕分辨率（`lensFlareResolution`） | 镜头光晕 | 后处理 | 八分之一 |

每项都是低档 0.25、中档 0.5、高档 1：低档时环境光遮蔽和体素收集停在四分之一，其余画到八分之一；中档全部为四分之一；高档按原样。

```json
"quality": { "profiles": { "medium": { "aoResolution": 0.25, "fogResolution": 0.25 } } }
```

游戏自己的设置界面可以在档位之上改它们，和渲染比例一样：对 `Quality` 资源调用 `quality.setPreferences({ fogResolution: 0.5 })`，
`setPreferences(null)` 恢复档位的值。

每个效果停在哪里、为什么停在那里，是看 `third-person-3d`、`terrain-water` 和 `bistro` 在手机尺寸（390 × 844，像素比 2.5）下的截图定的：

| 效果 | 最小 | 再小时的样子 |
|---|---|---|
| 环境光遮蔽（SSAO、GTAO） | 四分之一 | 八分之一时平面上的遮蔽成块，并渗到投下它的箱子上 |
| 雾里的光、屏幕空间 GI、镜头光晕 | 八分之一 | 十六分之一时 `bistro` 门上的反弹光变成一片平滑的光晕 |
| 体素 GI 收集（WebGL2） | 四分之一 | 没有测，和环境光遮蔽取同一处 |
| 天空的云 | 保持二分之一 | 四分之一时云的边缘出现竖向条纹；没有设置项改它的尺寸 |
| 泛光 | 保持二分之一 | 第一级用固定的一组采样读整幅画面，画到四分之一反而更贵（`bistro` 中档 0.12 ms 对 0.15 ms）；没有设置项改它的尺寸 |

遮蔽项按深度铺回画面，两个深度差多少仍算同一个面，会随遮蔽项画得多小而放宽，所以四分之一尺寸的遮蔽在掠射角看到的地面上不会出条带。

在 Windows 盒子上的无头 Chromium 里测（RTX 3060，ANGLE 走 D3D11），画面 975 × 2110，每个通道的显卡时间来自计时查询，
每档都拿原来的样子（每个效果分辨率都是 1）和新默认值比。盒子的毫秒数不是手机的；能带过去的是每个通道画多少像素，每减半一次就降到四分之一。

| 场景、档位 | 变小的通道 | 像素 改前 → 改后 | 这些通道，毫秒 | 整帧，毫秒 |
|---|---|---|---|---|
| `bistro`，中 | 屏幕空间 GI、SSAO 及其模糊、雾里的光 | 每个 513,785 → 128,061 | 4.57 → 1.55 | 11.7 → 8.5 |
| `bistro`，低 | 屏幕空间 GI、雾里的光 | 每个 288,715 → 17,927 | 1.42 → 0.19 | 9.8 → 8.9 |
| `terrain-water`，中 | 雾里的光、GTAO、镜头光晕 | 每个 513,785 → 128,061 | 2.26 → 0.84 | 11.7 → 10.4 |
| `terrain-water`，低 | 雾里的光 | 288,715 → 17,927 | 0.77 → 0.06 | 6.0 → 5.4 |
| `third-person-3d`，中 | SSAO 及其模糊 | 每个 513,785 → 128,061 | 0.43 → 0.17 | 1.02 → 0.76 |
| 任意场景，高 | 无 | 不变 | 不变 | 不变 |

`third-person-3d` 低档不跑环境光遮蔽，所以没有变化。盒子的显卡和别的工作共用，单帧总时间在两次之间会差一毫秒以上；通道时间取中位数。


## 步数与采样数

有些效果沿光线步进，或者在一圈里取样，取多少个是效果所属组里的一项设置。每个着色器按高档的数编译，跑到档位的数就停：步数少时每步更长、
走的距离不变，所以云一样厚、光柱一样长、模糊一样宽，损失的是平滑——抖动步进的步数太少时露出颗粒，天空的空气分的段少时地平线颜色差一点。

| 设置项 | 数的是什么 | 分组 | 低 | 中 | 高 |
|---|---|---|---|---|---|
| 雾光步数（`fogVolumeSteps`） | 高度雾里阳光的步数 | 天空与体积 | 8 | 16 | 24 |
| 雾的云遮挡采样（`fogCloudSamples`） | 每一步向上穿过云层取的点数 | 天空与体积 | 2 | 3 | 4 |
| 云步数（`cloudSteps`） | 天空视线穿过主云层的步数 | 天空与体积 | 12 | 14 | 16 |
| 高层云步数（`cloudUpperSteps`） | 穿过高层云的步数 | 天空与体积 | 3 | 4 | 6 |
| 云影采样（`cloudShadowSamples`） | 求云在地上的影子时沿阳光取的点数 | 天空与体积 | 3 | 4 | 6 |
| 大气散射步数（`skyScatterSteps`） | 天空颜色分几步累加 | 天空与体积 | 8 | 12 | 16 |
| 大气光学深度步数（`skyLightDepthSteps`） | 天空一点到太阳分几步 | 天空与体积 | 3 | 3 | 4 |
| 景深采样（`dofSamples`） | 模糊像素取的邻居数 | 后处理 | 16 | 32 | 64 |
| 光柱采样（`lightShaftSamples`） | 像素朝太阳看的点数 | 后处理 | 16 | 24 | 40 |
| 运动模糊采样（`motionBlurSamples`） | 运动像素抹开的点数 | 后处理 | 6 | 10 | 16 |
| 次表面散射采样（`subsurfaceSamples`） | 两个通道里每侧取的点数 | 后处理 | 3 | 4 | 6 |
| 折射模糊采样（`refractionSamples`） | 粗糙透射表面读背后场景的点数 | 特效与粒子 | 4 | 6 | 8 |

高档就是着色器原来写死的数，所以高档画面不变。低档默认去掉景深、光柱、运动模糊和次表面散射，它们的低档数对重新勾上这些效果的项目才有用。

**泛光级数**（`bloomLevels`，后处理）是泛光把亮处缩小几次再逐级放大回来：高档 5 级（缩到画面的六十四分之一），中档 4 级，低档 3 级。
少一级就去掉最小的那一级下采样和对应的上采样，光晕扩散得没那么远；留下的各级开销不变，所以低档省下的是四个很小的通道。

在 Windows 盒子上的无头 Chromium 里测（RTX 3060，ANGLE 走 D3D11），手机尺寸（390 × 844，像素比 2.5），每个通道的显卡时间来自计时查询，
同一时段里每档的旧数和新数对比，两次取平均。盒子的毫秒数不是手机的；能带过去的是每个像素走的步数和通道数。

| 场景、档位 | 通道 | 旧 → 新，毫秒 | 每个像素少了什么 |
|---|---|---|---|
| `terrain-water`，低 | 云（365 × 791） | 1.02 → 0.81 | 云步数 16 → 12，高层云 6 → 3 |
| `terrain-water`，低 | 天空合成（731 × 1583） | 0.45 → 0.28 | 散射 16 → 8 步，光学深度 4 → 3 步 |
| `terrain-water`，低 | 云影贴图（1024²） | 0.39 → 0.16 | 6 → 3 个采样 |
| `terrain-water`，低 | 雾光（91 × 197） | 0.056 → 0.009 | 24 → 8 步 |
| `terrain-water`，低 | 泛光全部通道 | 0.17 → 0.16，12 → 8 个通道 | 少两级 |
| `terrain-water`，低 | 整帧 | 5.6 → 4.9 | |
| `terrain-water`，中 | 云、天空合成、雾光 | 1.60 → 1.41、0.72 → 0.59、0.35 → 0.21 | 14 步、12/3 步、16 步 |
| `terrain-water`，中 | 泛光 | 12 → 10 个通道 | 少一级 |
| `terrain-water` 加景深，低 | 景深收集（731 × 1583） | 1.21 → 0.31 | 64 → 16 个采样 |
| `terrain-water` 加景深，中 | 景深收集（975 × 2110） | 2.15 → 1.07 | 64 → 32 个采样 |
| `bistro` 加次表面散射，低 | 两个散射通道 | 0.20 → 0.15 | 每侧 6 → 3 个采样 |
| `bistro` 加次表面散射，中 | 两个散射通道 | 0.33 → 0.27 | 每侧 6 → 4 个采样 |
| `bistro`，低 | 泛光全部通道 | 0.18 → 0.17，12 → 8 个通道 | 少两级 |

中档的云影贴图两次都是 4 个采样比 6 个慢（0.88 → 1.04 毫秒，3 个时 0.80）；中档计时器每次只读到一个值，这一点还不能定论。低档云步数少于 12 时，步进抖动会在云上留下一层网纹，
低档没有时间性抗锯齿来掩盖，所以低档保留 12；光学深度只走 2 步时天空偏蓝约 4%，所以低档保留 3。

材质不从自己的参数读这个数，而是从引擎读：帧常量 `u_quality`，第一格是折射采样数。表项用 `materialSlot` 占一格；质量系统关闭时这一格是 0，表示取最多。

**粒子碰撞**也受档位限制：**粒子碰撞查询上限**是一帧最多发多少条射线（低 1,024、中 2,048、高 4,096），**粒子碰撞事件上限**是一帧最多向游戏报告多少次碰撞
（256、512、1,024）。游戏自己用 `Particle.setCollisionBudget` 设的预算按字段优先于档位，因为依赖这些事件的游戏已经说了自己要多少。
**GPU 粒子深度网格**是 GPU 模拟的粒子碰撞用的场景深度副本横向多少格（320、480、640，只在 WebGPU 上）。

## 设备规则

模式为自动时显示。每行写一个档位和设备必须满足的条件：**型号包含**、**GPU 包含**、**内存上限**、**核心上限**，全部成立才算。
第一条匹配的规则决定档位。没有任何条件的规则会匹配所有设备，所以必须至少有一个条件。

## 着色器编译与按需渲染

同一页还有两组设置,管的是游戏*如何交付*,而不是它跑在哪个档位。它们与画质档位无关,模式为**关闭**时同样生效,保存在 `features.rendering.quality` 下。

![项目设置的渲染页:着色器编译、按需渲染、省电和抗锯齿四个分组](@/assets/guides/zh/settings-shader-compilation.png)

**着色器编译**

| 设置 | 作用 |
|---|---|
| **后台编译着色器**(`asyncShaderCompile`) | 浏览器还在编译着色器的绘制会先跳过,游戏立刻打开,画面随着色器就绪逐步补全。关闭时,第一次用到某个着色器的绘制会等它编完:每一帧都完整,但首次访问可能卡住数秒。需要 `KHR_parallel_shader_compile`,没有该扩展时仍按原方式编译。 |
| **在启动页后面预热**(`prewarmShaders`) | 在启动页后面把第一个场景画到没有着色器在编译为止,再打开成完整画面。开启后台编译后才显示。 |
| **预热超时** | 启动页最多等多久(秒,默认 30);超时后不管有没有编完都直接打开。开启预热后才显示。 |

**按需渲染**

| 设置 | 作用 |
|---|---|
| **只绘制会变化的帧**(`renderOnDemand`) | 静止的画面只花游戏逻辑的开销。有人请求绘制、玩家有操作、画面尺寸变化、实体被创建或销毁、或仍有着色器在编译时,才会画一帧。 |
| **变化后继续绘制的帧数**(`renderOnDemandTail`) | 最后一次绘制原因之后继续画的帧数,让淡出或收尾动作能走完。默认 30。 |

引擎看不到脚本自己改了什么(颜色、动画):用 `RenderDemand.request()` 请求画一帧,或用 `RenderDemand.hold()`(返回释放它的函数)声明某样东西在自己运动,否则这类变化要等别的原因唤醒画面才会画出来。所以这个开关默认关闭。

## 省电与降温

手机上玩得久,就是发热和耗电,而这两样都花在画面这一帧上。打开 **电量低或设备发烫时降低开销**(`QualityConfig.power`)后,引擎每隔几秒看一眼设备:处于省电状态时,降低帧率上限并给画质档位设一个上限,设备恢复后再放回。关闭(默认)时不监测设备,什么都不变。

| 设置 | 作用 |
|---|---|
| **电量低于**(`lowBattery`) | 电量低于该比例且没在充电时省电。默认 20%;0 表示不因电量省电。 |
| **发热压力**(`thermal`) | 平台报告压力达到该级别或更高时省电:严重(默认)、危急、不因发热。 |
| **省电时的帧率上限**(`fps`) | 省电时每秒最多画多少帧,默认 30。游戏已设得更低的上限保持不变。 |
| **省电时的画质上限**(`ceiling`) | 省电时画质不超过该档;本来更低的档位不动。默认中。 |

发热压力达到危急时更进一步:帧率上限减半(不低于 15),画质固定为低(`severe: 'never'` 可关闭这一步)。平台没报告的项不会触发任何事:没有电池接口的浏览器不会因电量省电,多数浏览器完全不报告温度(Chromium 报告电量和处理器压力;微信小游戏平台报告电量)。`Device.power()` 把同样的数字给游戏(`level`、`charging`、`thermal`,平台没说的为 `null`),`Quality` 的报告在压低档位期间会在限制里列出 `power-saver`。帧率上限只在游戏自己没有改动过它的情况下才放回。

静止的画面(菜单、牌桌)更好的省法是什么都不画:见编辑器同一页设置里的"按需渲染"。

## 在代码里

同样的设置就是 `QualityConfig`——`QualityController`、`parseQualityConfig`、`resolveQualityProfile` 和 `defaultQualityProfile`
构建并读取它——运行中的档位是 `Quality` 资源。

每个按档位的设置项都是 `QUALITY_SETTINGS` 里的一条，声明在 `sdk/src/render/qualitySettings/` 下它所属分组的文件里。一条写明键名、
类型（带范围的数字、开关、几个固定数字之一、几个名字之一）、三档默认值、分组，以及中英文的名称和说明；配置的类型、默认值、解析、
允许时的玩家偏好和编辑器里的那一行都由它生成。
