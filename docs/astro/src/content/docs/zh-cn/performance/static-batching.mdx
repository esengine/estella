---
title: 静态合并
description: 把许多共用材质的静态网格合成一次绘制 —— 该标记什么、哪些会被留下以及原因、以及它要花多少内存。
---

渲染器本来就会把**同一个网格的多份拷贝**合成一次实例化绘制。它做不到的是把**不同的网格**
合成一次:每个网格在 GPU 里都是自己的一段内存,所以用五十种不同道具搭出来的关卡,每种材质
要花五十次绘制。

**`StaticBatch`** 就是为这个准备的。给一个不会动的网格加上它,游戏运行时,材质、贴图、
颜色和层都相同的网格会按区域合并成一个网格。

```typescript
world.insert(wall, MeshRenderer, { mesh: 'builtin:cube', material });
world.insert(wall, StaticBatch, {});
```

在编辑器里,选中网格后在大纲的菜单里选**静态合并**。

## 会发生什么

- 网格按一次绘制拥有的全部状态分组 —— 材质、贴图、法线贴图、颜色、层、剔除与光照开关 ——
  还可以用组件上的**分组**把两个房间分开。
- 每一组再按世界里的格子切开,所以一个批是一小片区域,剔除仍然有东西可剔。
  格子默认边长 1600 世界单位,一个格子里的顶点不超过 262,144 个。
- 被标记的实体保持原样:脚本照样能找到,碰撞体照样碰撞,编辑器照样能选中。只是它们的绘制
  移到了合并后的网格上,那是另一个实体。
- 被合并之后,标记的网格**不能再动**。销毁是支持的(这个批会去掉它重新合并);移动不支持,
  而且没有任何办法发现。

## 哪些会被留下

合并不了的网格保持原样,并说明原因 —— 游戏运行时写在组件上,也写在性能分析器的**静态合并**
一节里。

| 原因 | 为什么 |
|---|---|
| 带骨骼 | 一次绘制只能处于一个姿态。 |
| 带形变 | 一次绘制只能处于一个形状。 |
| 细节层级 | 渲染器在运行时选择用哪一级。 |
| 公告牌 | 它朝每个视图转,合并后的网格却固定在烘焙时的位置。 |
| 半透明 | 结果取决于绘制顺序,而合并就是丢掉顺序。 |
| 会动 | 动态刚体或角色控制器:合并把网格站的位置烘进了顶点。 |
| 烘焙光照 | 场景有探针或烘焙,合并后的网格留不住每个部件各自的那一份。 |
| 还没有网格 | 句柄后面还没有几何(仍在加载,或网格失败),没有东西可复制。 |
| 已关闭 | 本来就不画,没有东西可合并。 |
| 顶点布局 | 位置或法线不是 32 位浮点,合并无法变换。 |
| 同组只有一个 | 只合并一个网格什么也省不了,还多占内存。 |

## 它的代价

合并会把每个部件的顶点复制进合并后的网格,所以它是**拿内存换绘制**。一个原本代表一百个实例的
部件,会变成一百份拷贝。性能分析器会为每个合并网格显示:它含多少部件、这些部件原本花多少
次绘制、这份拷贝占多少内存 —— 请把两个数字放在一起看。

同一个网格的许多拷贝用实例化,许多不同的网格用静态合并。

## 一个实测例子

`dusk-fort` 示例(39 个网格、17 种形状、5 种材质),全部标记,在编辑器 Play、WebGL2 下:

| | 不标记 | 标记 |
|---|---|---|
| 每帧绘制次数 | 18 | 13 |
| 三角形 | 51,313 | 51,313 |
| CPU 帧耗时 | 1.18 ms | 1.16 ms |

36 个网格合并成了 9 个批(另有 3 个在自己的组里只有一个)。这 9 个批在实例化之前对应 32 次绘制,
复制的顶点占 2.05 MB。这个场景里实例化已经省了大部分,合并多省的是最后 5 次:由许多不同部件
拼成的场景,比由少数几种重复部件拼成的收益更大。

两帧在 1.1% 的像素上有差别,其中 96% 只差 1 级(共 255 级),最多差 5 级,都在几何边缘,来自合并后的顶点在 CPU 上以 32 位浮点
变换;同一场景两次运行之间只差 0.003%。

## 会移动的组合模型:`CompositeBatch`

静态合并把每个部件烘焙在它在世界里的位置,所以由甲板、栏杆和道具拼成的船、车辆或移动平台用不了它。
改为在模型的**根节点**上加 **`CompositeBatch`**,部件本身什么都不用加。

```typescript
const ship = world.spawn('Ship');
world.insert(ship, Transform, {});
world.insert(ship, CompositeBatch, {});
// ……甲板、柱子和道具都挂在 `ship` 下面,各自带 MeshRenderer。
```

游戏运行时,部件按**根节点自己的空间**合并,绘制它们的网格是根节点的子实体:

- 移动、旋转或缩放根节点,整个模型跟着动,不会重新合并任何东西。
- 重复出现至少 **Instance at** 次(默认 4)的网格,比如甲板和栏杆柱,保持为一份常驻网格,
  作为一个实例化集合绘制,不复制任何顶点。
- 其余部件按绘制状态合并成根节点空间里的若干块。增加、删除、换网格或挪动一个部件,半秒内只重新合并它所在的那一块。
  要立刻检查,调用 `app.getResource(CompositeBatchingRes).refresh(root)`。
- 在模型内部一直在动的部件(门、轮子)看几次之后会被放开,由它自己绘制,不会每帧都触发一次合并。
- 静态合并的规则仍然适用:蒙皮、变形、LOD、公告板、半透明部件和动态刚体由自己绘制。
  组合模型下的部件不会再被静态合并。

根节点上会显示合并结果:**Batched parts**、**Instanced parts**、**Draws**、**Draws before** 和 **Moving parts**。

在编辑器 Play、WebGL2 下实测,一个根节点下 2,004 个部件(1,600 块甲板、400 根柱子、4 个道具):

| | 不加 | `CompositeBatch` |
|---|---|---|
| 每帧交给渲染器的网格 | 2,003 | 5 |
| 每帧绘制次数 | 7 | 5 |
| CPU 帧耗时(3 轮,每轮 180 帧) | 3.33–3.35 ms | 1.20–1.36 ms |

绘制次数变化不大,因为渲染器本来就会把重复的网格实例化。组合合并省下的是每帧逐个收集、剔除和排序部件的开销,
部件越多省得越多:108 个部件的小船两种方式差不多(不加 0.65–0.67 ms,加 0.68–0.90 ms),
这个规模下合并过程每秒两次检查部件的开销,和它省下的差不多大。

编辑器检查 `composite-batch` 用这艘小船锁定了这些结论:关掉网格阴影时,合并后的画面与不加时的差别在场景自身逐帧差别之内;
移动根节点不会重新合并;加一个部件只重新合并一块。开着网格阴影时,约 2% 的画面上阴影边缘会差一个像素左右,原因还没有确认。
