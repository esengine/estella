import { Aside } from '@astrojs/starlight/components';

场景是整体加载的。在世界大到一台机器不愿意一次性常驻之前,这都是对的答案;越过那条线
之后,问题就不再是"什么被画出来",而是**"什么存在"**。世界流送回答后者:cook 把作者
编排的世界切成方形格子,运行时一个格子之所以存在,是因为有东西靠近它;没有任何东西需要
它时,它就不再存在。

这里没有任何"隐藏"的把戏。离开的格子是被**销毁**的:它的实体、刚体、导航代理、资源引用
全部交回。这正是重点——只是被隐藏的地方仍然占内存、仍然会碰撞,也仍然允许一个谁都看不见
的敌人攻击玩家。

## 声明一个流送世界

两个组件,都在场景里编排:

```typescript
// 挂在世界设置实体上:这个场景按 1000 单位的格子切分。
world.insert(settings, StreamedWorld, { cellSize: 1000 });

// 挂在任何绝不允许被流送掉的东西上。
world.insert(player, WorldPersistent, {});
world.insert(camera, WorldPersistent, {});
world.insert(sun, WorldPersistent, {});
```

其余一切按**它所在顶层实体的位置**落入某个格子。没有 `StreamedWorld` 的场景不是流送
世界,加载方式和以前完全一样。

<Aside type="note">
`WorldPersistent` 不是场景持久化。`SceneContext.setPersistent` 决定一个实体能否活过
一次场景**切换**;`WorldPersistent` 决定这个实体被写进哪一份 cooked 场景,也就决定了
residency 到底能不能移除它。
</Aside>

## 请求地方存在:流送源

一个格子之所以存在,是因为有**源**靠近它:

```typescript
world.insert(player, WorldStreamingSource, {
    prefetchRadius: 3000, // 距离在此以内的格子被**准备好**,但不进入世界
    loadRadius: 2000,     // 距离在此以内的格子被带进来
    unloadRadius: 3000,   // 已常驻的格子在越过这个距离前一直保留
});
```

三个半径的单位是世界单位,默认值就是上面的数字;组件还有一个 `enabled` 开关(默认开),关掉就把这个源从并集里拿掉而不必移除组件。`StreamedWorld.cellSize` 默认 1000。

可以同时存在多个源,它们的请求是**并集**——只要任意一个源需要,格子就继续常驻。这正是
分屏、观战相机、过场相机和编辑器预览可以是同一类东西、而不是四个特例的原因。这里不会把
多个源折叠成一个焦点:折叠意味着最后写入的那个说了算,于是第二个相机出现的下一帧,它就
把第一个相机正站着的那片世界删掉了。

距离量到格子的**包围盒**,而不是中心点:按中心量,站在对角角落的源和隔了整整一格的源
读数相同,而网格的对角线正是"洞"出现的地方。

### 在被需要之前就准备好

落在 `prefetchRadius` 以内的格子会被**准备**:文档取回、预制体展开、资产获取——
而它的实体一个都还不存在。所以没有任何东西能观察到它:查询查不到、渲染器不画、
刚体不碰撞、里面的敌人不做任何决策,因为那里根本还没有东西。**只有发布才创建实体**,
而发布发生在某个源真正进入 `loadRadius` 的时候。

这大约值玩家二十毫秒。在 Estella 自己的 fixture 上,走进一个已准备好的地方要等
0.6ms;走进一个没准备的,还要连取回和解码一起等。

准备是**推测,不是权威**。为一个掉头走开的玩家准备好的格子会被丢弃、资产交回——
绝不会因为"都准备好了"就塞进世界。而且一次准备完成时会**重新问**这个格子是否仍被
需要,不会拿开始时的答案当结论。

`prefetchRadius` 的取值永远不会低于 `loadRadius`;除此之外它和 `unloadRadius`
之间**没有**任何大小关系要求——它们回答的是两个不同方向的问题:多早开始准备,和
多晚才放手。

### 两个半径之间的带

格子在 `loadRadius` 处进来,直到越过 `unloadRadius` 才离开。两者之间的空隙就是它们都
必须存在的全部理由:否则一个站在边界上的源会每一帧都在实例化和销毁同一个地方。把
`unloadRadius` 设得比 `loadRadius` 明显更大——多出一半是个不错的起点。

## cook 产出什么

切分发生在 **cook 时**,不在启动时:

```
main.esscene ──cook──▶ main.esscene          持久世界
                       world/main.world.json 清单
                       world/main.cell_0_0.json
                       world/main.cell_1_0.json ...
```

包体启动的入口场景,是把格子取走之后剩下的东西——residency 永远不会移除的那部分。格子
**不是**可切换的场景:它们是 residency 带进来的内容,游戏永远不会点名其中任何一个。

格子只在一个平面上切。默认是地面(世界 x 与 z):一个格子是一根垂直柱体,所以一座塔的各层是同一个地方。2D 世界躺在屏幕平面里,所有实体的 z 都一样,这时把 `plane` 设为 **Screen (x, y)**(`StreamPlane.Screen`),格子就沿世界 x 与 y 切,流送源也按 x、y 读取。不设的话,2D 世界会落进沿 x 的一行格子里。烘焙后的清单里也有同一个字段(`WorldManifest.plane`,值为 `'xy'`),此时格子的 `z` 就是世界 y。

## 远景代理

不常驻的格子不在世界里,所以加载半径以外的地方本来什么都不画。在 `StreamedWorld` 上勾选 **Far proxies**,构建时就会给每个格子烘一个替身:
把格子里静态、不透明的网格按材质合并成每种材质一次绘制,再做简化,格子不在时画它。

```typescript
world.insert(settings, StreamedWorld, {
    cellSize: 1000,
    farProxies: true,
    farDistance: 8000,   // 离某个流送源这么近、又不常驻的格子显示代理
    proxyError: 1,       // 简化后的表面最多偏离原来多少世界单位
    proxyRatio: 0.01,    // 最少保留的三角形比例;proxyError 需要时会多留
});
```

cook 会在格子旁边写出 `world/<格子>.far.json` 和它的网格,并在清单的格子上记下(`WorldCell.proxy`,以及 `WorldManifest.farDistance`)。
预制体实例会先展开,所以用预制体摆的建筑也会贡献网格。以下表面不进代理:禁用的、半透明的、蒙皮的、公告板,以及自己或某个父节点会自己动的
(角色控制器、非静态刚体、动画器)。只由你自己的系统移动、又不带这些组件的网格,会按它摆放的样子烘进代理:给它或它上面的实体加上 `ExcludeFromFarProxy`,整棵子树就不进代理,格子在世界里时照常画出来。

简化到什么程度由 `proxyError` 决定:让它小于代理开始出现的距离(流送源的加载半径以外)上一个像素覆盖的大小。只有颜色不同的表面共用一次绘制,
颜色烘进顶点;代理不带光照贴图 UV。在 `far-proxy-town` 示例里(144 个格子,静态网格共 310 万三角形),`proxyError` 为 0.5 时代理只保留 2% 的三角形;
沿它的飞行路线,每帧画 12.2 万三角形、354 次绘制,全部加载时是 86.6 万三角形、620 次绘制,画面上明显不同的像素占 0.3%。

流送器两个方向的交接都不留空档:走向一个格子时,它的代理一直留到格子进入世界;走开时,格子一直留到它的代理进来。代理加载失败不会拖住格子。
`WorldStreamerStatus.proxyCells` 和常驻报告会列出当前由代理来画的格子。

Play 用同样的格子、和构建同一套简化代码做出同样的代理,放在内存里。每个代理在流送器第一次要它时才做,不是在游戏开始前全部做完:
在 `far-proxy-town` 里,Play 只花 172 毫秒标出哪些格子有代理就开始,之后每个代理到来时花约 30 毫秒(最多 190 毫秒)。

## 一个流送世界必须遵守的规则

**子树是 residency 的最小单位。** 只有顶层实体会被定位,所以即使一扇门的世界坐标落在
隔壁格子里,它也不会被从自己的房子里分出去。格子的包围盒会扩张到覆盖它的内容,因此悬在
边缘外的道具不会在边界处突然弹出。

**硬实体引用不允许跨越 residency 边界。** 同一个格子里的两个实体可以互相引用;持久世界
内部也可以;格子引用持久世界也可以,因为持久世界比每一个格子都活得久。而从一个格子指向
另一个格子、或者从持久世界指向格子内部——都会让构建失败,因为它们指向的东西 residency
有权删除。

**Residency 拥有"存在","延续"需要声明。** 卸载的格子会丢掉运行时状态,重新加载会按编排内容重建:
你打伤后走开的敌人,回来时是满血的。不该这样的东西,加上 `RememberState`:

```typescript
world.insert(enemy, RememberState, {});                     // 记住血量和位置
world.insert(chest, RememberState, { keepTransform: false }); // 开过的宝箱保持打开
```

被记住的实体随格子卸载时,它的游戏组件(项目自己定义的组件,比如 `Health`、宝箱的 `opened`)和 Transform
会按它的编排 id 记下来。格子再次加载时,在任何东西生成之前先改好文档,所以它回来时就是离开时的样子,
一帧都不会以编排时的样子出现。被记住的实体在格子加载期间被销毁(Boss 被打死、矿被采完、建筑被拆),
会连同它下面的一切记为"已消失",格子不会再把它带回来。引擎自己的组件不保留:它们持有资源句柄和格子会自己重建的状态。
运行时才生成的实体没有编排 id,不会被记住。

记忆存放在 `WorldMemoryRes` 资源里。用[存档槽](/docs/zh-cn/scripting/save/)带进存档:

```typescript
const saves = new SaveManager({ version: 1 });
const memory = app.getResource(WorldMemoryRes);
saves.save('slot1', { player, world: memory.toJSON() });   // 存档时
const loaded = saves.load<{ world: WorldMemoryData }>('slot1');
if (loaded) memory.read(loaded.world);                     // 读档时,在世界流入之前
```

`read` 会替换现有记忆;已经在世界里的格子保持原样,下一个加载的格子读取新的记忆。`clear()` 清空一切,用于新游戏。

## 程序化区块

游戏在运行中生成的东西(运动物体周围的地面碰撞、视点周围的植被、游戏自己生成的任何东西)不是 cook 出来的格子,而是某个**层**的区块,`ProceduralChunks` 是它们生命周期的唯一所有者,就像流送器之于格子。一个层说明自己怎么切分、在它的源周围多远内需要、一个区块怎么生成、发布和释放:

```typescript
import { chunksOf } from 'esengine';

chunksOf(app).set('ruins', {
    label: 'Placing ruins',
    originX: 0, originZ: 0, sizeX: 64, sizeZ: 64, extent: null,
    loadRadius: 256, unloadRadius: 320,
    generation: `${planet}:${generatorVersion}`,     // 区块由什么生成
    make: (cx, cz, signal) => generateRuins(cx, cz, signal), // 一个值、表示"还不行"的 null,或一个 Promise
    publish: (cx, cz, ruins) => spawnRuins(ruins),
    release: (cx, cz, ruins) => despawnRuins(ruins),
});
```

- **同一组源。** 层围绕流送器读取的同一批 `WorldStreamingSource`(没有时是视点)被需要,除非它指定自己的源:地形碰撞跟随每个运动的 3D 刚体和角色。
- **2D 世界按 x、y 切分。** 层默认按地面(世界 x 与 z)切分,而 2D 相机的 z 不变,上下走动时什么也不会流入。写 `plane: 'xy'`,层就沿世界 x、y 切分,源也按这个读;层里所有叫 "z" 的量(`originZ`、`sizeZ`、区块的 `cz`、`stateAt` 的第二个坐标)此时指世界 y。层自己的 `sources()` 本来就按层所在的平面回答。
- **同一份预算。** 每帧所有层需要的区块由近及远生成:源所在的区块立刻生成,其余在本帧预算内生成。预算是 `Bakes.budgetMs`,与烘焙作业和地形页共用。
- **有上限。** 超出所有源 `unloadRadius` 的区块连同它发布的一切被释放,所以一直走下去持有的区块数是固定的;在带内来回走不会重复生成。
- **代次。** `generation` 标识层的输入。它变化时每个区块重新生成,旧版本保留发布直到新版本替换它,站在上面的东西不会掉下去。为旧代次返回的结果(worker 还在算上一个星球时就传送到了另一个星球)被丢弃,区块的 `AbortSignal` 被中止。
- **可查询。** `status(id)` 统计一个层的区块(ready、stale、pending、making、failed,以及第一个失败的原因),`stateAt(id, x, z)` 说明某点所在区块的状态。仍在生成区块的层会和烘焙作业一起、带着进度显示在编辑器状态栏里。

## 读取当前常驻状态

```typescript
const report = worldResidencyReport(app);
report.residentCells;        // ['main.cell_1_0', 'main.cell_2_0']
report.cellEntityCounts;     // 每个常驻格子当前拥有的实体数
report.loadCount;            // 启动以来带进来过多少个地方
```

给的是计数而不是画面,因为"没有被画出来的格子"和"根本不存在的格子",从相机看是一样的。

## 在编辑器里

编辑视图下,地形细节、植被、世界生成和体素都围绕视口生成,场景里的 `WorldStreamingSource` 只在运行时才起作用,2D 和 3D 视图都是如此。

打开带 `StreamedWorld` 的场景时,视图里只有 `WorldPersistent` 实体,其余格子的贴图和网格也不加载。在世界面板里可以逐格或全部加载、卸载,视口会标出已加载的格子,下次打开时保持同样的格子。文档始终保留全部实体:未加载的格子照常保存,运行和导出看到的都是完整世界。

## 清空或替换世界

先禁用或移除流送源,再等待 `streamer.clear()`。它会释放已经预加载的资源,并等待尚未完成的准备、发布和卸载结束。
格子的注册信息会保留,后续更新流送源时仍可以重新请求这些格子。

替换世界时,等待 `streamer.loadManifest(manifest, sceneConfig)`。它会先清理旧格子,再注册新清单,
两个清单使用相同格子名称时也遵守这个顺序。并发替换以最后一次请求为准;显式调用 `clear()` 会取消尚未完成的替换请求。
如果卸载失败,操作会拒绝完成,防止新世界接管仍有旧内容存活的名称。

## 这一版不做什么

格子通过游戏本来就在用的场景加载路径异步到达。它们有先后(来源正要走进的格子先于只是可能走进的,近的先)
,也可以用 `prefetchRadius` 提前准备,但没有准入预算:一个大格子到达时仍然是一次卡顿。
格子的远景代理(见上文)只带它的静态网格:会动的、半透明的、不是网格的东西(精灵、粒子、灯光)在格子不在时不画;
代理也只有一级,没有越远越粗的多级。
有些内容自带远景版本:地面([地形](/docs/zh-cn/graphics/terrain/)是按距离切分的四叉树,画到 `drawDistance`;
分块的地面远处用常驻内存的概览来画,只在视野附近读入全精度的块;星球一直画到地平线),以及植物
([植被](/docs/zh-cn/graphics/foliage/)和 `PlacedFoliage` 的远景交叉面片,还有生成世界里植物的远景版本),
它们让整片区域一次就立起来。网格的纹理按视图需要的尺寸保留([纹理流送](/docs/zh-cn/performance/quality-levels/),一项画质设置)。
导航网格按格子分块烘焙并跟随加载状态(见[导航](/docs/zh-cn/gameplay/ai/navigation/#在流送世界里)),但智能体只在已加载的地方行走;世界原点也从不重定基准(`setRenderOriginStep` 让远离原点处的*绘制*保持精确,见[相机](/docs/zh-cn/graphics/camera/))。
